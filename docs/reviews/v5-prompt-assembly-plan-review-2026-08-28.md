# Review: v5 prompt assembly plan vs Oracle export baseline

- **Date:** 2026-08-28
- **Plan under review:** `docs/plans/v5-prompt-assembly-2026-08-28.md`
- **Baseline:** `prompt-exports/oracle-plan-2026-08-28-183005-pg-agent-v5-prompt-a-7bb9.md`, generated-plan response only (from `# v5 prompt assembly: POML-inspired SQL slots`)
- **Overrides applied (not critiqued):** (1) v3/v4 SQL loaded as read-only paths, no 12-file copy; (2) generate-missing is a visible first `llm_requests` turn, no hidden `prompt_part_requests` queue; (3) named `action=wb_*` stage in scope before generate-missing; (4) generated parts are recipe-global, first-writer-wins.

## Scope

This critique covers only: (1) implementation-bearing export content lost or weakened beyond what the four overrides require; (2) under-specified seams, contradictions, incorrect references, missing dependencies; (3) plan/export details the code disproves or a simpler design replaces; (4) requirements, edge cases, lifecycle, failure, and testability gaps absent from both documents; (5) open questions that would still change design or order. Code references were spot-checked against `v3/pg_agent_pgmq.sql`, `v4/load.py`, and `v4/observability_budget/worker.py`.

## 1. Findings: export content missing or weakened after the overrides

1. **Worker-side generation validation disappeared without a replacement.** The export specified that the worker normalizes and validates generator output (empty content, wrong roles, oversized values, component-shape mismatch) *before* SQL apply. Under the visible-turn design the model writes parts through `wb_store_prompt_part`, so validation moved into SQL — but the plan only carries over the size bounds (8,000 chars; ≤16 example messages). The export's role validation for `value_kind='messages'` (only `user`/`assistant`, non-empty content per message) and the text/example `value_kind`-vs-`component_type` consistency check are not restated anywhere in the plan's store-tool contract (§3.8). The named-dispatch arg check ("type mismatches using the COMMENT `args` map") cannot cover this: `p_value` is `jsonb`, so all structural validation must be hand-specified in the tool body. Restate the full validation list in §3.8.

2. **Generation-payload hygiene rules were dropped.** The export enumerated what a generation payload must not contain (API keys, auth headers, full prior prompts, full provider responses, filesystem paths, unbounded recipe/user data). The plan retains only a single test assertion ("no API key in `agent_steps.meta`"). The bootstrap recipe now deliberately includes the user question (override 2), which makes the *negative* list more important, not less: the bootstrap message set (generate instructions + missing list + question + history) should have an explicit bounded-content statement, and `wb_store_prompt_part` should state that the raw provider response is never persisted — only the extracted `value`.

3. **Bootstrap-recipe self-consistency guard is missing.** The export's hidden-queue design could not recurse; the plan's visible-turn design can. `agent_system_generate` has its own stored slots (`generate_role`, `generate_task`). If one of those parts is missing, `assemble_prompt_messages` on the bootstrap recipe itself returns `missing`, and the plan does not say what `prepare_llm_request()` does then (bootstrap-for-bootstrap is nonsense). The plan should state: bootstrap recipe slots are all `generation_policy='never'`, are seeded atomically with the recipe, and a `missing` status on the bootstrap recipe is a hard `PROMPT_ASSEMBLY_ERROR`, not another bootstrap.

## 2. Findings: under-specified seams, contradictions, stale references

1. **Stale export leftovers contradicting override 2 (hidden queue removed):**
   - §4 `v5/README.md` bullet still says "generation queue" — no queue exists.
   - §4 `v5/load.py` bullet "refresh points after taxonomy, recipe retriever, and **generation queue-handler** files" — there is no queue-handler file; the refresh point is still needed but it is for the `wb_store_prompt_part` `llm_tool` COMMENT and the `prompt_live_missing` `prompt_slot` COMMENT in W6.
   - §3.11 migration step 7: "Create the generation tables and queues" — no generation tables or queues remain.
   - §3.6 `prompt_live_history` bullet "Ignores `prompt_generation`, `budget`, `wait` … events" and §7.5 "`prompt_generation` steps do not appear in folded conversation history" — the `prompt_generation` step kind no longer exists; both should reference only the real non-`llm`/`tool` kinds (`budget`, `wait`).
   - §4 `v5/generate_missing/README.md` bullet "Document **queue payloads**, storage, **wait/resume semantics**" — there are no queue payloads or wait/resume; the README should document the bootstrap payload shape and the premature-`final_answer` suppression rule.
   - W4 gate text "missing envelope is not sent to `llm_requests`" is export wording; the parenthetical ("missing still `request_type=llm` after W6; W4 may expose assemble status only") rescues it, but the gate sentence itself should be rewritten so a W4 implementer does not build the removed routing branch.

2. **W4 missing-state behavior is unspecified.** §7.5 requires asserting "ready payload shape and missing payload shape" at W4, but bootstrap messages do not exist until W6. The plan never says what `prepare_llm_request()` returns at W4 for a `missing` assembly (raise? return without `messages`?). State the interim contract explicitly, e.g. "at W4, `status='missing'` raises `PROMPT_ASSEMBLY_ERROR`; W6 replaces that branch with bootstrap assembly."

3. **`prompt_live_missing` recursion seam is unspecified.** The bootstrap recipe's `missing_list` slot needs the missing-slot list of the run's *pinned user* recipe, computed while assembling the bootstrap recipe. The plan does not say how `prompt_live_missing(p_run_id, p_config)` obtains this — presumably by calling `assemble_prompt_messages(p_run_id)` and reading its `missing` array (safe only because the user recipe never contains a `missing_list` slot). State the mechanism and the non-recursion invariant, and pin down which recipe `slot_trace`/`prompt_recipe` in the bootstrap payload refers to (the user recipe, the bootstrap recipe, or both).

4. **Premature-`final_answer` suppression mechanism is unstated.** §3.8 says apply must detect that "the pinned user recipe still has required generatable parts missing" but never says how — the only available mechanism is re-running `assemble_prompt_messages()` (or a cheaper `EXISTS` probe over `prompt_slots`/`prompt_parts`) inside the `apply_llm_response()` overlay. Specify which, and note the per-apply cost.

5. **Named-argument runtime type checking is hand-waved.** §3.1 says apply rejects "type mismatches using the COMMENT `args` map." The v4 taxonomy validates the args map against the function signature at `refresh_plugins()` time; nothing in v4 validates JSON values against PG type names at call time. The plan must define the coercion rule (e.g. jsonb-type-to-PG-type matrix, or attempting the `EXECUTE ... USING` and mapping a cast error to the structured validation observation) — this is new code, not an existing behavior to preserve.

6. **Prompt-slot retriever volatility is unconstrained.** `assemble_prompt_messages()` is declared `STABLE` but invokes retrievers via dynamic dispatch. A `VOLATILE` retriever (or one that writes) would silently break the contract. The §3.3 COMMENT contract should require retrievers to be declared `STABLE` (or `IMMUTABLE`) and `refresh_plugins()` should validate `provolatile`.

7. **`content_hash` is indecisive.** "MD5 or SHA-256 digest of the canonical JSONB value" — pick one (SHA-256), and define "canonical" (e.g. digest of `value::text`, which is deterministic for jsonb). Similarly, `prompt_parts.updated_at` is dead schema under first-writer-wins (`ON CONFLICT DO NOTHING` never updates); either drop it or state what touches it.

8. **The "configured prompt-size bound" has no home.** §3.6 step 4 enforces a serialized-size bound but neither document names the GUC, constant, or table column that configures it.

9. **`slot` → `position` mapping in the compiler is unspecified.** §3.5 says slots derive from `xpath('/poml/*', p_source)` order, but the seeded tables use sparse positions (10, 20, 30, …). State whether the compiler assigns `position = 10 * ordinal` (and what happens past 32 slots given the §3.6 cap), or positions are dense.

## 3. Findings: details the code disproves, or a simpler design replaces

1. **`parse_llm_output()` does not need an overlay.** §3.7 and the W5 file impact hedge with "(and `parse_llm_output()` if needed)". The code settles this: `llm_decision.sql` is `text` and `parse_llm_output()` stores the raw `action_input` verbatim (`v3/pg_agent_pgmq.sql`, `d.sql := j ->> 'action_input'`). Named dispatch can parse `action_input` as jsonb inside the `apply_llm_response()` overlay. **Correction:** W5 touches only `apply_llm_response()`; remove the `parse_llm_output()` hedge from §3.7 and the W5 file-impact bullet. (Note the field is named `sql`, so the plan's phrase "`llm_decision.sql` continues to hold the raw `action_input` text" is already accurate.)

2. **Export's generation infrastructure is correctly deleted — say so explicitly.** The export's `prompt_generation_requests`, `prompt_generation_waits`, `prompt_part_requests(+_dlq)` queues, `prompt_generate` queue kind, `apply_prompt_part_result()`, and the `run_state()` durable-wait overlay are all made unnecessary by override 2: bootstrap turns are ordinary `llm` steps, so the existing `apply_llm_result` budget path records them for free, `run_state` stays `RUNNING` truthfully, and exactly-once resume reduces to the existing apply loop. The plan deletes the machinery but never states this simplification; §3.12 ("No extra generate queue") comes closest. Adding one explicit "export superseded items" note would prevent an implementer from reintroducing the tables from the export's file-impact section.

3. **Export residual-gate #1 was verified, not a risk.** Plan §3.13 item 1 conditions W1 on whether `v4/observability_budget/worker.py` exists and subclasses the queue_kinds worker. It does: `v4/observability_budget/worker.py` line 8 `from v4.queue_kinds.worker import AgentWorker as BaseWorker`, line 27 `class AgentWorker(BaseWorker)`. The plan already states this as fact (good); the export's fallback ("reconstruct the snapshot from the final available v4 worker") is dead and correctly gone. No action — recorded so the W1 gate isn't re-litigated.

## 4. Findings: gaps absent from both documents

1. **Cross-run prompt-injection persistence (compounds overrides 2+4).** Generated `role`/`task`/`output_format` parts are recipe-global system content (override 4) and the generator sees the current user question (override 2). One run's adversarial or merely odd question can therefore shape system instructions served to every later run of that recipe version. Neither document names this. §5.3 covers "quality" and suggests SQL inspection; it should explicitly cover the trust boundary and state the mitigation stance (e.g. `source='generated'` parts require review before a recipe version is activated for new runs, or at minimum are queryable/auditable by `generator_request_id`).

2. **Generation consumes the task budget/steps with no separate allowance.** Bootstrap turns burn `max_steps` and the run's budget. The plan handles exhaustion (`missing_prompt_parts` error) but never asks whether generation should get its own step/budget slice; as written, a recipe with N missing parts costs N+ turns before the task starts. This may be intended, but it is a requirement-level silence in both documents.

3. **Recipe/part lifecycle is one-way.** No statement about: deleting or deactivating a recipe version that has pinned runs; deleting `prompt_parts` rows outside tests (the W6 test itself `DELETE`s a required part — permitted for any operator?); or what `active=false` with zero active versions does to `agent_start()` (the trigger selects the active recipe — the no-active-recipe error exists, but the operational path to recover is undescribed).

4. **Loser-turn semantics of first-writer-wins.** When two concurrent runs bootstrap the same slot, the losing turn's `wb_store_prompt_part` returns `stored=false, replayed=true`, and that observation enters the run's visible history. Neither document says whether the model is expected to tolerate this (it should be a non-error observation the seeded bootstrap task text mentions), nor whether the losing run re-assembles mid-turn or only on the next turn.

5. **Observability of bootstrap mode.** `prompt_mode='generate_missing'` exists only in the PGMQ payload; nothing records it on the resulting `llm` step (`agent_steps` shape is frozen). Debugging "why is this run generating instead of answering" requires reading step payloads. A one-line note that the bootstrap `llm` step is identifiable via payload inspection (or an explicit decision to keep it that way) is absent.

6. **Testability of the taxonomy negative path.** The plan requires "failed refresh leaves `plugin_packages`/`plugin_bindings` byte-for-byte unchanged" but neither document mentions that `refresh_plugins()` failure modes must be exercised per new validation rule (`source=live` + `generation=if_missing`, prompt-slot with `llm_tool` sibling key, bad `component_types`), not just once generically.

## 5. Open questions that would still change design or order

1. **Who re-seeds `agent_system` when W5 changes the protocol?** §2.4 says pre-W5 seeds describe the `execute_sql` wrap "so W4 tests can run." After W5, the seeded role/task/output-format text must describe named `wb_*` actions (W6's bootstrap instructions already assume named calls). Options: (a) W5 ships `agent_system` v2 and flips `active` — then W3's seeded text is knowingly temporary and W4 tests pin v1; (b) W3 seeds named-action text from the start and W4 tolerates a prompt/runtime mismatch. This affects W3 seed content and W5 scope, i.e. it is an ordering question, not a detail.

2. **Does generation get a separate step/budget allowance?** If yes, W6's apply overlay changes (generation turns not counted against `max_steps`) and §7.6 test 12 changes. If no, the plan should say so explicitly. This must be decided before W6, and arguably before W3 fixes `max_steps` seed text ("bounded result rows … one SQL statement per round" is silent on generation turns).

3. **Is one global bootstrap recipe sufficient, or per-recipe?** `agent_system_generate` reads hints from slot `config`/`hint`, so one recipe probably suffices — but if a second user recipe ever needs different generator instructions (e.g. a non-SQL agent), the bootstrap recipe name must become derivable from the pinned recipe. Decide now whether `agent_system_generate` is hard-coded in the W6 `prepare_llm_request()` overlay or named by convention (`<recipe>__generate`), since that choice is baked into the overlay.

4. **What configures the assembly bounds?** The 32-slot / 128-message / serialized-size caps (§3.6 step 4) and the 8,000-char part bound (§3.4) need a named source (GUC with default, or constants). If they are GUCs, the freeze gate must snapshot them like `model`/`api_uri`.

## Summary

The plan correctly absorbs all four mid-flow overrides and the visible-turn design is genuinely simpler than the export's hidden-queue machinery — the export's generation tables, queue kind, wait rows, and `run_state` overlay should stay deleted. The remaining work is mop-up and hardening, not redesign: (a) restore the export's validation/hygiene specifics into `wb_store_prompt_part` and the bootstrap payload contract; (b) purge six stale export references (queue/handler/`prompt_generation` wording in §3.6, §4, §3.11, §7.5, W4 gate); (c) pin down four seams the plan currently gestures at (`prompt_live_missing` recursion, premature-final detection, named-arg type coercion, retriever volatility); (d) resolve the W5 recipe re-seeding question before W3, since it changes what W3 seeds. One new risk emerges from combining overrides 2 and 4 — recipe-global prompt injection via the user-question hint — that neither document names and that deserves an explicit mitigation stance.
