# 第 11 章：崩溃与混沌——kill-at-every-boundary

> 前置：第 2、3、5 章。产出：G5/G6 的 chaos 注入器（`v13/fakes.py` 的 crash 开关）。
> 对照上游：`v8` P0B 的 kill-at-every-boundary 验收（全仓库最具迁移价值的工程仪式）。

## 11.1 这一章要做什么

前十章的正确性全是「声明」——本章把它变成「测量」。

极简化的真正风险是**砍过头的可恢复性**（Oracle 风险 R1）：并发 claim 竞争、
响应丢失双计费、unknown 失明，这些事故在 happy path 测试里永远不出现。
v8 留下的最有价值遗产不是任何一张表，而是一个测试纪律：

> **在每个边界上杀死进程，然后证明系统恢复且外部副作用至多一次。**

## 11.2 边界清单（chaos 矩阵）

一个 effect 的生命周期有五个可杀点，加上三个系统级故障源：

```text
effect 生命周期：
  B1 创建后、消息发送前     → 同事务已保证不存在（第 3 章）
  B2 claim 后、外部调用前   → 无外部副作用，recover 回 ready
  B3 外部调用中             → provider 侧未知 → unknown 的主场
  B4 外部成功后、结算前     → 最痛窗口：本地不知、外部已发生
  B5 结算后、archive 前     → 消息重投，claim 拿不到，无害

系统级故障源：
  S1 消息丢失（整队列 DROP）   → 扫描恢复（第 3 章）
  S2 消息重复（archive 失败）  → claim 过滤 + replay 出口
  S3 lease 到期但旧 worker 活着（网络分区） → fence CAS 拒迟到者
```

对每个 B/S 组合，gate 断言三件事：

```text
✓ 外部副作用计数（FakeTool/FakeLLM 全局计数器）≤ 1
✓ 恢复路径可推导：查哪张表哪一行、跑哪条命令即可继续（不允许手工改表）
✓ 事件日志完整：每个边界上的状态转移都有事件可考
```

## 11.3 逐段解释

- **B4 是全部设计的试金石**：外部已成功、DB 未落账。此时唯一安全动作是
  进入 unknown，等人工/策略 resolve（第 12 章）——**绝不自动重试**，
  因为重试 = 第二次副作用。provider 幂等键（`idempotency_key` 列）存在时
  才允许重试复用身份。四件套里的 unknown 为什么是一等状态，B4 就是答案。
- **B3 与 B4 的区分靠 worker 申报证据**：worker 拿到 provider 回执（receipt id）
  → B4；网络异常无回执 → 可能 B3 也可能 B4——**不可证明即 unknown**，
  分类规则在 SQL（第 2 章「申报不裁决」），三种出口都有事件。
- **崩溃语义 ≠ 控制语义中断**：本章 kill-at-every-boundary 杀的是 worker
  自身——进程失联，谁也不控制杀点；第 8 章第四务的 cancel 是控制语义
  ——handler 主动订阅本 session 的 cancel 事件、中断自己拉起的子进程、
  settle cancelled/unknown。前者靠恢复扫描收尾，后者靠合同履约，核心在
  两种语义里都不杀进程。chaos 矩阵只测前者；后者的断言在 G6（第 8 章）。
- **恢复扫描不见 `kind='sql'` 工具行**：sql 档的全部效果是数据库自身状态
  （第 6 章），崩溃即回滚——没有「外部已发生、本地未落账」的窗口，G3 的
  恢复面（claimed + lease 过期 → 重入队）对它不适用。库内动作的回执是
  同事务的事件 + 行，不是 claim/settle（第 14 章 spawn 同款）。
- **「查哪行 + 跑哪条命令」审计法**：为十类最痛事故（双扣费、用户消息丢失、
  lease 卡死、毒消息循环……）各写一条 runbook 断言。
  任何一条的答案是「手工 UPDATE 表」→ 砍深了，说明该机制该回来。
- **浸泡测试（可选）**：72 小时，worker 每 30s 随机被杀 + fake provider
  会重复投递/丢响应/超时后才提交。事后只查三个数：副作用计数、
  unknown 存量、扫描恢复延迟。

## 11.4 硬性规定与 gate

```text
G5/G6 chaos 节选断言：
✓ B2×10 连杀：session 不卡死，最终 succeeded，外部计数 1
✓ B4 注入：状态=unknown，事件带申报证据；自动重试路径不存在（断言其被拒）
✓ S3 双 worker 网络分区模拟（旧 worker sleep 过 lease）：迟到结算 stale
✓ 毒 effect（必失败）× max_attempts：failed 终态 + DLQ，不无限循环
✓ 全队列 DROP → requeue_stale → 全部 ready effect 补发 → 正常推进
```

## 11.5 检查点练习

1. 给 fakes 加「B4 注入开关」：外部成功后、complete 前 `os._exit(1)`。
   写 gate 断言恢复流。
2. 构造 lease 卡死：claim 后把 worker 挂起超过 lease，断言接管 + 旧 fence 拒绝。
3. 写你自己的第十一个事故场景并给出 runbook（查哪行+跑哪条命令）。
   如果写不出来——这是设计问题，不是文档问题。

## 11.7 内在合理性：前因后果

**作用力。** 先列事实——它们关于运行环境，不关于任何设计偏好：**崩溃
可以落在任何指令边界**——断电、OOM、kill 不挑时机，操作系统不承诺
让你跑完一段处理流程。**外部 IO 与 DB 事务之间没有原子性**：HTTP 调用
与 commit 之间不存在能同时覆盖两者的事务，于是「外部已成功、本地
未落账」的窗口物理上关不死。**重试对外部副作用是再执行而非重放**：
对外部而言重跑一次就是再发生一次，钱会扣两遍。**竞态与时序缺陷
只在特定交错里现形**：单线程顺序执行永远走不出 lease 过期、网络
分区、消息重复投递这些组合。**事故现场会消失**：进程死了内存就
没了，日志只留下活着的那一半。

**推导。** 这些力逼出本章的 chaos 纪律。崩溃可落在任意边界 ⇒ 声明的
正确性不等于测量的正确性，唯一可信的途径是穷举边界注入：把一次
外部动作（effect）的生命周期切成五个可杀点 B1–B5，再叠上 S1–S3
三个系统级故障源，即 chaos 矩阵。副作用窗口关不死 ⇒ B4 这个最痛
窗口只能被**命名**为 unknown（与 ready、failed 平级的一等状态），
唯一合法出口是显式 resolve（第 12 章）——**不可猜测、不可吞掉**；
自动重试路径被断言为不存在，provider 幂等键（`idempotency_key`
列）在场时才允许重试复用身份。交错缺陷只在交错里现形 ⇒ gate 只信
被注入的交错，每次注入后查三件事：外部副作用计数 ≤ 1；恢复路径
可推导——查哪张表哪一行、跑哪条命令即可继续，不允许手工改表；
事件日志完整——每个边界的状态转移都有事件可考，worker 拿到
provider 回执（receipt id）即 B4 证据，无回执即申报为 unknown，
证据落库，分类交给 SQL。

**反事实。** 撤掉 chaos 注入器、只留 happy path 测试，失败时序：
第 1 步，上线第三周，一个 worker 恰好死在 B4——测试从没走过这条
路，恢复代码里「顺手」写的 catch-and-retry 把外部扣款又打了一遍，
双计费；第 2 步，同一周，另一 worker 在网络分区后挂起超过 lease
——接管从未被测过，迟到结算没被 fence CAS 拒绝，这行也无人能再
接管，lease 卡死；第 3 步，B3/B4 的区分无人做——窗口被静默吞成
failed，unknown 失明，外部已成功的那笔永远对不上账；第 4 步，
数周后事故爆发才去排查：现场已消失，日志只剩正常的那一半，不可
归因——runbook 一条也写不出来，因为没人知道该查哪一行。

**被拒替代。** 其一，**只跑单测**：单线程路径对交错缺陷免疫，绿灯
意味着「没测到」而不是「没有」——双计费与 lease 卡死都住在单测
永远造不出的交错里。其二，**拿生产当测试场**：不注入，等真实事故
来当考题——爆炸半径是真实数据与真实用户，双扣费赔的是真钱；而
fakes.py 的 FakeTool/FakeLLM 全局计数器把同一套断言搬进零成本的
环境里反复跑。其三，**形式化证明**：对并发与崩溃模型做验证，成本
与本章目标错配，覆盖也错配——模型本身就会漏掉 B4 这类窗口，证明
只护住写进模型的故障，穷举注入测的却是系统本身。
