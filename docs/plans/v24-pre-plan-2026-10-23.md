## 2. 阶段与 gate 映射

### 2.1 为什么不是 G1→G7 直接对应 8 个阶段

设计稿 §9 的 G1–G7 是**覆盖清单**，不是施工顺序：

1. `start` 只绑定已激活 episode（§4.2 L219–225；§7.2 L394–396），所以能力面 S2 必须先于六动词 S3。
2. G3 的 run-pin 断言需要 `start` 生成的 run pin（§9 L437），只能在 S3 收口；S2 只能证明 activation-pin 半部。
3. G2 的 cancel×T2 双序需要真实 loop settlement（§7.2 L398–400；§5.3 L287–291），只能在 S4 收口；S3 只能证明控制面半部。
4. G6 的 spawn 负例需要真实 spawn 解释器，因此 S8 必须先于 S7。

因此 G2、G3 各拆两个子门；父门只在**两个子门 + 父级负例**全部通过后标记完成。

### 2.2 子门与父门规则

- 子门命名：`G2a`（控制面）/`G2b`（loop 面）、`G3a`（激活面）/`G3b`（run-pin 面）。
- conformance matrix **保留 G2、G3 父行**，证据列分别链接两个子门；父行状态只允许“未验证 / 部分（子门 X 绿） / 完成”。
- 子门通过不等于父门通过；父级负例（设计稿 §9 列出的全部负例）必须逐条有证据。
- 该拆分属于施工口径，不改设计语义；在 deviation ledger 记一条“G2/G3 子门拆分”，不记规格偏差。

### 2.3 映射总表

| 设计 gate | 子门 | 收口阶段 | 收口判据（摘要） |
|---|---|---|---|

- S2 必须先于 S3：`start` 只绑定已激活 episode；无可用 episode 时 start 必须失败且零 run（§7.2 L394–396）。
- S3 必须先于 S4：loop 的 model_call 由 start 创建；G2b 需要 S3 的 generation/interaction 合同。
- S4 必须先于 S5：完整 drain 消费 S4 的静默/unknown/pin 合同。
- S5 必须先于 S7：三面矩阵的“dispose/close × 六动词”格需要完整闭包。
- S6 必须先于 S8：G5 的 recovery/replay 语义是 child 首个 model_call 的基线。
- S8 必须先于 S7：G6 的 spawn 负例（同 key 同/异 bytes、父 terminal、quota 不足）需要真实 spawn 解释器；S7 仍是最终验收。

### 5.2 可并行边界

- **计划细化可并行**：S8、S7 的合同级占位可在 S6 实施期间细化；S7 的矩阵用例可提前编写，但 **G6 只能在 S5/S6/S8 全绿后收口**。
- **代码写权串行**：同一时间只允许一个 stage 修改 `v24/` 下的 SQL/Python；并行只发生在“读、评审、计划、测试用例设计”，不发生在共享文件写入。
- 收口顺序串行：S6 → S8 → S7；S8/S7 的合同占位可在 S6 期间并行细化，但 G6 不得先于 G7 收口。
- 若 S6 发现并修订共享语义，S7 对应证据必须重跑；不得用旧证据结项。

### 5.3 每阶段收尾（AGENTS.md 硬约束）

1. 该 stage 全部 gate 实跑、退出码 0（含此前所有 stage 的 gate，防回归）。
2. 新增 SQL 已追加进 `v24/load.py` 的 `SQL_LOAD_ORDER`；loader 拒绝非声明前缀、symlink 与未登记文件（不做数字缺口检查，缺口由有序清单与逐文件登记约束）。
3. 对应 stage README、conformance matrix、deviation ledger 更新完毕。
4. 按路径逐项 `git add`（禁止 `git add -A`），提交信息 `<v24>: <祈使句摘要>`，推送目标分支。
5. 任何 gate 红即停，不得以“下阶段修”结项。

## 6. 验证与证据口径

### 6.1 Fake-only 与隔离

- 全部 gate 为独立脚本（`uv run python v24/<stage>/test_<name>.py`），退出码 0 = 通过；不使用 pytest。
- 每个 stage 的 `setup_db.py` 建唯一名临时库（`v24_<stage>_<pid>_<hex>`，TEMPLATE template0），按 `v24/load.py` 的 `SQL_LOAD_ORDER` 累计加载，结束时以 OID 复核后 `DROP DATABASE ... WITH (FORCE)`；**不 DROP 既有库**。测试用 FakeHost/FakeLLM/FakeTool，不开网络、不调真实 provider。
- 外部 IO 一律在数据库事务外；FakeHost 保留持久 IO journal 以支撑 G5。

### 6.2 并发证据

- 必须用两个真实连接 + 屏障制造相反意图；用 `pg_blocking_pids()` 证明谁在等谁；断言无死锁、无锁序外等待、赢家由 G 决定。
- 禁止用 `sleep` 猜顺序；禁止用单进程线程代替双连接。
- v99 的线程屏障只能作参考，不能直接复用为 v24 证据（见研究备忘录的复用边界）。

### 6.3 gate 证据粒度

- 不只断言最终 status：必须同时断言 effect 唯一结算、后继条数、request 首次 response、事件条数与关键列 diff。
- 读请求（poll/wait/resolve）断言调用前后库 diff 为空。
- 未实现/未运行/未绿的 gate 在 matrix 中显式标“未验证”；不得用“设计已 SATISFIED”代替 gate 证据。

### 6.4 工件

- `docs/reviews/v24-conformance-matrix-*.md`：G1–G7 父行 + G2a/G2b/G3a/G3b 子行 + 设计 § 覆盖。
- `docs/reviews/v24-deviation-ledger-*.md`：子门拆分、T1/T2 术语统一、kill 点数口径、任何实现期裁决。
- `v24/<stage>/README.md`：该 stage 的对象、入口、gate 命令、已知债务。
