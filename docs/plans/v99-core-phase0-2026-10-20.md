## 2.1 v13 的现有架构

`v13/load.py:18-59` 在当前 v99 工作树中定义 41 项累计 `SQL_LOAD_ORDER`，`registry` 是第 41 项；`STAGE_THROUGH['registry']=41` 位于 `v13/load.py:61-102`。每个 stage 从空库重放所有前缀，早期函数体仍是 stage gate 的验收对象。重复审计 `docs/investigations/v13-duplicate-capabilities-audit-2026-10-20.md:41-43` 已确认 53 个重复函数名涉及 162 次声明，其中 45 个同签名覆盖族，因此删除 v13 历史 SQL 或把新实现追加到 v13 loader 都会破坏历史契约。

`v13/schema/v13_core.sql` 提供 sessions/events/effects、append-only events、effect attempt/fence、幂等 enqueue、`FOR UPDATE SKIP LOCKED` claim、session→effect 锁序和 unknown wall。它的单活跃 effect 索引、CAS completion 和 replay 逻辑是可参考的协议证据，但 v99 不复用这些表、函数或角色。

`v13/ce_run/v13_ce_run.sql` 已有五张 CE 表和六个控制入口，包含 request digest、wake cursor、active steer、terminal steer、human interaction、scoped claim 和 receipt。其 v13_ce_wake（`v13/ce_run/v13_ce_run.sql:194-212`）先插入持久 wake，再发送 NOTIFY；wait_check（同文件 :418-479）查询表。这支持“持久状态为事实、通知仅唤醒”的设计，而不是说 wake 函数只发通知。其 cancel 只取消 ready effect，claimed effect 仍可迟到结算，并在严格 closeout 不满足时自行构造取消 seal；Phase 0 将把这些分叉收敛成一个 closeout 规则。

`v13/loop_driver/driver.py:302-380` 先执行 Fake/provider IO，之后才 claim+complete；这与 Phase 0 的 claim→COMMIT→IDLE→IO→T2 顺序相反，只能作为反例。`v13/ce_run/test_ce_run.py:172-424` 的 `CeWorker` 已证明适合作为时序参考：discover→claim→COMMIT、连接 IDLE、Fake IO、单事务 accept+successors+publish；同文件 native_receipt_fences（:1250）与 native_unknown_vs_archive（:1394）有崩溃、丢 COMMIT 响应、stale token 和 unknown 的断言。本轮只读了测试代码，没有实跑这些断言。

`v13/ce_run/setup_db.py:1-130,290-650` 证明了临时数据库 name/OID 身份、非超级用户角色、schema/database ACL 收紧、before/after catalog 差分和精确清理的验证方式。`v20/alpha/setup_db.py:20-29` 要求 DSN host 以 `/` 开头；`server.py:17-19` 仅是 pgembed 启动入口，不足以保证连接本地性，Phase 0 必须自行验证运行时 DSN。

# 3. Design

## 3.1 路径、包布局与命名裁决

采用工作树根下的逻辑路径：

```text
v99/core/
├── __init__.py
├── README.md
├── load.py
├── setup_db.py
├── test_core.py
└── sql/
    ├── 00_extensions.sql
    ├── 10_schema.sql
    ├── 20_ledger.sql
    ├── 30_ce.sql
    └── 40_permissions.sql
```

Python 包名为 `v99.core`；不创建 `v99/v99/core`。`v99` 可作为 namespace package，`v99/core/__init__.py` 只保存版本元数据和无副作用导出。脚本从仓库根执行：

```text
uv run python v99/core/setup_db.py
uv run python v99/core/test_core.py
```

对象放在独立 schema `v99_core`。SQL 签名区为可读性省略 schema；实现和宿主调用必须使用完整限定名。关系名使用 `core_*` 前缀，函数、约束、索引、触发器使用 `v99_core_*` 前缀，例如：

- `v99_core.core_runs`
- `v99_core.core_effects`
- `v99_core.v99_core_start(...)`
- `v99_core.v99_core_effect_claimed`

这样即使测试数据库误加载其他版本，也不会与 `public.sessions`、`v13_ce_runs` 或同名函数冲突。

拒绝把新 SQL 放进 `v13/load.py`：那会把 Phase 0 变成 v13 stage overlay，并重新引入历史覆盖链。拒绝使用工作树目录名作为包路径：`.claude/worktrees/v99` 是 checkout 位置，不是仓库内的 `v99/v99` 目录。

## 3.2 独立数据库、schema 和扩展

Phase 0 使用专用临时数据库，每次 setup 创建唯一名称：

```text
v99_core_<pid>_<random>
```

数据库内只创建 `v99_core` schema。`00_extensions.sql` 只允许：

- 在新建 v99_core schema 内 `CREATE EXTENSION IF NOT EXISTS pgcrypto WITH SCHEMA v99_core`，用于 digest；UUID 使用 pg_catalog.gen_random_uuid()；若环境已在其他 schema 装 pgcrypto，setup 必须 fail-closed 并报告，不能隐式搬迁既有扩展；
- 不安装、不引用 `pgmq`、`typesafe`、`stannum` 或任何 v13 扩展。

`load.py` 只读取 `CORE_SQL_LOAD_ORDER`，顺序固定为 extensions → schema → ledger → CE → permissions。不得导入或读取 v13/v8 loader。

拒绝复用 v13 表和函数，即使字段形状相似；否则无法证明 Phase 0 的独立生命周期、ACL 和回滚边界。

## 3.4 SQL 对象与持久化合同

### 3.4.1 `core_runs`

`v99_core.core_runs` 是 run、session 和 canonical lifecycle 的同一行。

字段：

- `run_id uuid PRIMARY KEY DEFAULT gen_random_uuid()`
- `registration_generation bigint NOT NULL DEFAULT 1 CHECK (=1)`
- `current_epoch_ordinal bigint NOT NULL DEFAULT 1 CHECK (>0)`
- `continuity_generation bigint NOT NULL DEFAULT 1 CHECK (=1)`
- `turn_ordinal bigint NOT NULL DEFAULT 1 CHECK (>0)`
- `status text NOT NULL CHECK IN ('running','waiting_for_input','completed','failed','cancelled','blocked_unknown')`
- `interaction jsonb`
- `failure_reason jsonb`
- `revision bigint NOT NULL DEFAULT 1 CHECK (>0)`
- `context_revision bigint NOT NULL DEFAULT 1 CHECK (>0)`
- `driving_operation_id uuid NULL`
- `driver_owner text NULL`
- `driver_lease_until timestamptz NULL`
- `driver_fence bigint NOT NULL DEFAULT 0 CHECK (>=0)`
- `updated_at timestamptz NOT NULL DEFAULT now()`

`interaction` 非 NULL 时必须是闭集对象 `{id,kind,channel}`：id 为合法 UUID 字符串，kind 为非空字符串（instruction 有特殊 steer 语义），channel 只能是 human 或 ce。Phase 0 不建 parent/child/goal 表。

### 3.4.2 `core_epochs`

字段：

- `epoch_id uuid PRIMARY KEY`
- `run_id uuid NOT NULL REFERENCES core_runs(run_id)`
- `ordinal bigint NOT NULL CHECK (>0)`
- `continuity_generation bigint NOT NULL CHECK (=1)`
- `registration_generation bigint NOT NULL CHECK (=1)`
- `transition_kind text NOT NULL CHECK IN ('initial','steering')`
- `created_at timestamptz NOT NULL DEFAULT now()`
- `closed_at timestamptz NULL`

约束：

- `UNIQUE(run_id, ordinal)` 和 `UNIQUE(run_id, epoch_id)`；
- 对 `run_id WHERE closed_at IS NULL` 建部分唯一索引，每个 run 最多一个开放 epoch。

Phase 0 只产生 `initial` 和 `steering`；不预建没有 producer 的 transition kind。

### 3.4.3 `core_operations`

字段：

- `operation_id uuid PRIMARY KEY`
- `request_id text NOT NULL UNIQUE`
- `run_id uuid NOT NULL REFERENCES core_runs`
- `epoch_id uuid NOT NULL REFERENCES core_epochs`
- `verb text NOT NULL CHECK IN ('start','steer','respond','cancel','admit_turn','admit_tool')`
- `turn_ordinal bigint NOT NULL CHECK (>0)`
- `attempt_seq bigint NOT NULL CHECK (>0)`
- `status text NOT NULL CHECK IN ('pending','completed','archived','closed')`
- `payload jsonb NOT NULL DEFAULT '{}'`
- `payload_digest text NOT NULL`
- `result jsonb NULL`
- `archive_reason text NULL`
- `created_at timestamptz NOT NULL DEFAULT now()`
- `completed_at timestamptz NULL`

约束：

- `request_id` 最大 512 字节且非空；
- `(run_id, attempt_seq)` 唯一；
- `UNIQUE(run_id, operation_id)`；
- `(run_id, epoch_id) REFERENCES core_epochs(run_id, epoch_id)`；
- 四类控制 verb 必须 `status='completed'` 且 `completed_at IS NOT NULL`；只有 admit_turn/admit_tool 可 pending；
- operation 不保存反向 effect FK；由 effect 单向引用，消除循环关联；
- payload 序列化大小最多 1 MiB；
- `admit_tool` 必须包含 `source_operation_id`, `tool_call_index`, `tool`, `params`。

### 3.4.4 `core_effects`

字段：

- `effect_id uuid PRIMARY KEY`
- `run_id uuid NOT NULL REFERENCES core_runs`
- `operation_id uuid NOT NULL`，以 `(run_id, operation_id)` 引用 core_operations
- `kind text NOT NULL CHECK IN ('llm','tool','human')`
- `tool_name text NULL`
- `request jsonb NOT NULL`
- `request_digest text NOT NULL`
- `idempotency_key text NOT NULL`
- `epoch_ordinal bigint NOT NULL`
- `turn_ordinal bigint NOT NULL`
- `attempt_no integer NOT NULL DEFAULT 0 CHECK (>=0)`
- `fence bigint NOT NULL DEFAULT 0 CHECK (>=0)`
- `claim_driver_fence bigint NULL`
- `cancel_requested boolean NOT NULL DEFAULT false`
- `status text NOT NULL DEFAULT 'ready' CHECK IN ('ready','claimed','succeeded','failed','unknown','cancelled')`
- `result jsonb NULL`
- `error jsonb NULL`
- `created_at timestamptz NOT NULL DEFAULT now()`

约束和索引：

- `kind='tool'` 时 `tool_name` 非 NULL；
- `UNIQUE(run_id, idempotency_key)` 和 `UNIQUE(run_id, effect_id)`；
- `(run_id, epoch_ordinal) REFERENCES core_epochs(run_id, ordinal)`；
- `UNIQUE(operation_id) WHERE kind IN ('llm','tool')`，每个 admission 最多一个主要 effect；
- `UNIQUE(operation_id) WHERE kind='human'`，同一 llm admission 最多一个后续 human effect；
- 约束触发器验证：admit_turn 只能关联 llm 和可选 human；admit_tool 只能关联 tool；控制 operation 不直接关联 effect；effect 与 operation 的 run/epoch/turn 一致；
- `UNIQUE(run_id) WHERE status='claimed'`，保证一个 run 同时最多一个外部 IO；
- ready llm/tool effects 可排队多个，但只能按 operation attempt_seq 顺序 promotion；human 由绑定 interaction 同步结算，不参与 worker FIFO；
- unknown effect 不得自动重放；
- `cancel_requested=true` 的 claimed effect 只能接受 stale/unknown 审计，不得回到 succeeded。

### 3.4.5 `core_events`

字段：

- `(run_id uuid, seq bigint)` 联合主键；
- `event_id uuid UNIQUE`;
- `type text NOT NULL`;
- `payload jsonb NOT NULL`;
- `payload_hash text NOT NULL`;
- `source_effect_id uuid NULL`;
- `epoch_ordinal bigint NULL`;
- `turn_ordinal bigint NULL`;
- `created_at timestamptz NOT NULL DEFAULT now()`。

- `name`
- `description`
- `schema jsonb`
- `enabled boolean`

| 字段 | 类型与约束 |
|---|---|

| kind | text NOT NULL，闭集 start/steer/respond/cancel/receipt |
| request_digest | text NOT NULL，64 位小写 SHA-256 十六进制 |

| response | jsonb NOT NULL；完整已处理响应 DTO |
| created_at | timestamptz NOT NULL DEFAULT now() |

### 3.4.11 组合引用、计数与保留周期

runs 的 `(run_id, driving_operation_id)` FK 在 operations 创建后添加。start 插入顺序为 run（driving=NULL）→ epoch → completed 控制 operation → pending admission/effect → 设置 driving，全部同事务。snapshot.last_operation_id、event.source_effect_id 使用带 run_id 的组合 FK；events 引用 run；wakes/snapshots 的 `(run_id,epoch_ordinal)` 引用 epochs。所有引用禁止跨 run 关联，禁止级联删除审计记录。

| 字段 | 分配规则 |
|---|---|
| registration_generation、continuity_generation | 恒为 1，run UUID 不复用，不重新注册 |
| current_epoch_ordinal | start=1；仅 completed/failed 的 terminal steer 加 1 |
| turn_ordinal | 初始 llm admission=1；每个新 admit_turn 加 1，跨 epoch 不重置；tool 沿用源 llm turn |
| operation.attempt_seq | run 锁内按本 run MAX+1 分配；控制和执行共用 FIFO 序列 |
| event.seq | run 锁内按本 run MAX+1 分配 |
| effect.attempt_no/fence | 初始 0；claim 各加 1；claimed cancel/转 unknown 再增加 fence |
| context_revision | 初始 1，无公开修改入口；普通 history/steer/respond 不增加 |

start/steer/respond 控制 operation 记录对应新 admission 的 turn，cancel 记录当前 turn。分配与插入同事务，rollback 不留下分配状态。context_revision 与 snapshot revision 分离；pin 故障只由 owner 注入。

events、wakes、requests、pins 保留至整个临时数据库删除。Phase 0 没有 TTL、reaper、消费删除、生产归档或在线压缩。

## 3.5 状态机

### 3.5.1 Run 状态

| 当前 | 允许迁移 | 触发 |
|---|---|---|
| running | waiting_for_input | publish waiting snapshot |
| running | completed/failed | publish terminal snapshot |
| running | cancelled | cancel |
| running | blocked_unknown | 有效 unknown receipt 或 recovery 将 claimed effect 置 unknown |
| waiting_for_input | running | respond 或 instruction steer |
| waiting_for_input | cancelled | cancel |
| blocked_unknown | cancelled | cancel；seal 明确列出 unknown |
| completed | running | terminal steer，新 epoch |
| failed | running | terminal steer，新 epoch |
| cancelled | 无 reopen | 只能 poll；重复控制返回 already_terminal |

禁止：

- `unknown` 直接变成 succeeded；
- cancelled 通过 steer/respond 复活；
- waiting interaction 被普通 publish 覆盖；
- terminal snapshot 后再写旧 operation 的 snapshot；
- active steer 关闭当前 epoch。

### 3.5.2 Epoch 状态

- initial epoch 在 start 创建并打开；
- active steer 保持 ordinal 和 continuity；
- completed/failed 的 terminal steer 关闭旧 epoch，创建 `ordinal+1`、相同 continuity 的 steering epoch；
- cancel 关闭当前 epoch；
- cancelled run 不创建新 epoch。

### 3.5.3 Operation 状态

- start/steer/respond/cancel 创建即 completed，completed_at 同事务赋值；它们证明控制准入，不等待 receipt。
- 只有 admit_turn/admit_tool 创建为 pending。
- pending → completed：receipt、必要 successors/publication 和 journal 在完整 T2 内提交；
- pending → archived：旧 driving 使用 archived_stale；unknown 使用 unknown；失败链尚未执行项使用 upstream_failed；
- pending → closed：cancel，只关闭执行 admission，不关闭 cancel 控制 operation；
- completed/archived/closed 不得重新进入 pending；
- receipt replay 不改变状态。

### 3.5.4 Effect 状态

- llm/tool ready → claimed：driver lease 有效、bound claim 为 FIFO 队首、attempt/fence 递增、写 pin；
- llm/tool claimed → succeeded/failed：token、driver owner/fence/expiry、pin 全匹配；
- human ready → claimed → succeeded：operator 的 respond 或 instruction steer 在同一事务内完成，不读取/续租/接管 driver lease；
- claimed → unknown：有效 unknown receipt 或接管后 recovery；
- ready → cancelled：cancel；
- claimed + cancel_requested：保留 claimed 账本，旧 receipt 只返回 stale；恢复后可变为 unknown；
- succeeded/failed/unknown/cancelled 只允许 replay 或审计，不允许自动重放。

### 3.5.5 Model→tool→result→model→final

1. start 创建 completed `start` 控制 operation，再创建 pending `admit_turn` 和 llm effect。start/steer/respond 的 operation_id 指控制准入；execution_operation_id 指执行 admission。
2. worker claim llm，T1 COMMIT，Fake LLM 返回文本或 tool calls。
3. T2 只有一次宿主 `accept_receipt` 调用；它先验证全部结果，再原子结算、生成 successors、publish 和写 replay journal：
   - 无 tool calls：内部 publish `running`、`waiting_for_input` 或 terminal；running 创建下一 admit_turn；
   - 有 tool calls：按数组原序插入 admit_tool 和 effect，再发布 running，不能发布 terminal。
4. 每个 tool effect 完成后：
   - 未完成的 tool queue 继续 promotion；
   - 最后一个 tool 成功后同一 T2 插入 `admit_turn`，生成下一轮 llm effect。
5. tool result 不直接成为 terminal；它进入 events/history，下一轮 LLM 通过 worker history DTO 读取。
6. LLM 最终结果只能通过 publish 进入 completed/failed。
7. waiting_for_input 必须带合法 interaction，且没有其他 ready/claimed llm/tool 或 pending 执行 operation。human channel 创建绑定已完成 llm admission 的 human effect，snapshot.interaction_effect_id 指向它；ce channel 不创建 human effect。
8. 当前链失败时，将尚未执行的 ready successors 置 cancelled，pending successors 归档 upstream_failed，再通过唯一 closeout 发布 failed。unknown 不执行失败收尾，进入 unknown wall。

active steer 新建 admission 并成为 driving_operation_id，同 epoch FIFO 排队，不撤销已 claim IO。旧 driving 的 succeeded/failed receipt 仍可结算 effect 并追加结果事件，但 operation 归档 archived_stale，不生成 successors、不更新 snapshot。已准入的旧 tool 项按 FIFO 执行并归档，旧链最后一个 tool 不再产生 continuation。判断 tool 是否当前链时，通过 payload.source_operation_id 追溯源 llm driving admission；不能直接比较 tool operation ID 与 driving_operation_id。正常 continuation 在 admission 同事务更新 driving_operation_id。

Phase 0 不实现 approval workflow；若未来需要工具审批，新增 interaction/operation 类型，不改写本状态机。

## 3.6 API、DTO 和错误合同

所有 JSON 顶层使用 `schema_version: 1`。除 wait 外，成功和预期拒绝均包含 `ok`。未知数据库错误抛出并回滚，不转换成业务拒绝。

### 3.6.1 六个控制入口

```text

                    epoch bigint, after_wake_id bigint default 0) -> jsonb
v99_core_cancel(actor uuid, run_id uuid, request_id text) -> jsonb

               request_id text, expected_epoch bigint) -> jsonb
v99_core_respond(actor uuid, run_id uuid, interaction_id text,
                 response jsonb, request_id text) -> jsonb
```

`wait` 协议由 `wait_check` 和 Python `ce_wait` 组成；数据库函数只做一次纯读检查，不 sleep、不持事务等待。

Start 成功 DTO 恰含：

```text

```

Poll 未授权、未知 run、registration 失配统一返回：

```json

```

Wait 返回固定八键，不添加 `ok`：



其余成功 DTO 的顶层闭集如下（nullable 键也保留，不随分支删键）：

| 入口 | 顶层键 |
|---|---|
| poll 可见 | schema_version、ok、run_id、registration_generation、epoch_ordinal、continuity_generation、revision、status、snapshot |
| cancel | schema_version、ok、run_id、operation_id、revision、status、cancelled_effect_ids、unsettled_claim_ids、unknown_effect_ids |
| steer | schema_version、ok、run_id、operation_id、execution_operation_id、epoch_ordinal、revision、status、queued |
| respond | schema_version、ok、run_id、operation_id、execution_operation_id、epoch_ordinal、revision、status |

Respond 的 response 必须是对象，顶层恰含 `schema_version:1` 加一个 one-of 键：

- `response`：非空 string 或 number/boolean，`0`、`false` 合法；
- `answers`：非空 object；
- `skip:true`。

未知键、多选、空值和不合法类型返回 invalid_response。interaction_id 在 UUID 转换前校验，格式错误返回 invalid_args，合法 UUID 但不是当前 interaction 返回 interaction_mismatch。成功返回控制 operation_id、execution_operation_id、epoch_ordinal、revision 和 running status。

human channel 的 respond 持有 run 锁，内部 bound claim 对应 human effect、递增 attempt/fence、写 driver_fence=NULL 的 pin，再通过共用 ledger CAS 结算，清 interaction、写 human/responded、创建 completed respond 与 pending admit_turn、publish running、写 journal，全部一个事务。审计包含 settlement_channel=operator_response 和真实 caller role；不伪造 ce-respond driver。instruction steer 使用同一内部结算过程，CE channel 只消费 interaction。worker 永不 discover/claim/accept human。


worker DTO 不暴露控制表；discover/claim/worker_history 是受控 projections。driver 字符串是并发 owner 标识，不是凭据；真实认证来自 service 数据库角色，该角色在 Phase 0 是受信宿主。

```text

                          driver text, driver_fence bigint,
```

受控 projection 形状：

- discover：`{schema_version,ok,run_id,driver_fence,revision,next}`；next 为 NULL 或恰含 `{operation_id,effect_id,kind,turn_ordinal,attempt_seq}`，只返回当前 epoch FIFO 队首 llm/tool。

### 3.6.3 Receipt 闭集与校验

receipt 顶层恰含八键：`schema_version,status,effect_id,attempt_no,fence,context_revision,catalog_revision,effect_result`。schema_version 必须为数字 1；status 为 succeeded/failed/unknown；effect_id 先验证 UUID 字符串再转换。attempt 是 JSON 正整数且不溢出 integer；fence/revision 是 JSON 正整数且不溢出 bigint，不接受字符串、负数、小数。按规范化 JSONB UTF-8 计算 `octet_length(receipt::text) <= 1048576`。

effect_result 必须是对象，worker 不允许 human receipt；SQL 校验期不执行任何外部 IO：

| 分支 | 结果合同 |
|---|---|
| llm succeeded | §3.9 的 LLM 闭集及互斥校验 |
| tool succeeded | 恰含 schema_version:1、adapter:"ce-fake-spawn"、simulated:true、task；task 与请求一致 |
| failed/unknown | 恰含 schema_version:1、error；error 恰含非空字符串 code/message |

形状、类型、大小和 human receipt 错误为 invalid_receipt；合法形状中未知工具和非法参数为 invalid_tool/invalid_tool_args。全部校验先于 mutation。operation/effect 绑定错误为 receipt_request_mismatch，不能占用后续合法 receipt ID。

### 3.6.4 Request replay 与完整 T2

四个控制写入口及 accept_receipt 使用 core_requests；driver acquire/claim/recover 按状态和 fence 保证安全，不虚构 request ID。

可 replay 入口先校验 caller/actor 和静态输入，再获取事务 advisory lock `hashtextextended('v99-core-request:' || request_id, 0)`，计算规范化 JSONB 的 SHA-256：版本、入口、原始参数、payload、CAS 参数；receipt 包含原 driver/driver_fence 和完整 receipt。start 的输入 run_id 为 NULL，不包含之后生成的 run UUID。哈希碰撞仅影响并发，身份以完整 request_id 判定。

1. journal 同 ID、同 digest：当前 caller 授权后，零写返回存储 response，**不检查当前 lease/pin/catalog/terminal 状态**。
2. 同 ID 不同 digest：控制请求 request_id_conflict，receipt 为 receipt_conflict。
3. journal 不存在：按固定锁序读绑定 run/operation/effect；绑定错误及取消后 late receipt 先走明确的审计分支，不进行新结算。其余分支再验证当前状态、lease/token/pin 并执行。业务拒绝不占用 request ID。

控制 request_id 禁用保留前缀 ce:；receipt_id 必须等于 `ce:<execution_operation_id>:receipt`。内部派生键保留 `ce:<operation_id>:publish:<purpose>`、`:tool:<index>`、`:next_turn`，但不建立独立 journal，也不在 run 锁后获取新的 request advisory lock。重试保留原提交参数，不换成新 driver 的 token。

accept_receipt 是宿主唯一 T2 写入口，原子执行：验证全部 receipt → effect CAS → operation 完成/归档与结果事件 → successors → 必要 publication/closeout → journal response。宿主不能先提交账本再单独 publish。

snapshot revision：start=1；claim/lease/pin/settlement/纯审计不增加；每次实际 publication 恰加 1，同步 run/snapshot/wake。accept 在 T2 内读取已锁 run 的当前 revision R 传给内部 publish；不能使用 T1 缓存值。旧 driving 仅归档，不发布、不增加 revision。

successor admission 或 publication 在 settlement 后拒绝时，整个 accept mutation 区间必须回滚；只捕获明确登记的业务拒绝再转换 DTO。未知 SQL 错误（包括非预期 P0001）原样抛出，不得笼统吞掉。mid-T2 rollback 后，宿主保留 result、rollback 连接并提交同一 receipt，禁止重做 Fake IO。

## 3.7 事务、锁序和并发

所有写路径固定锁序：

```text
request advisory lock
→ core_runs
→ current core_epochs
→ target core_operations
→ target core_effects
→ core_meta（共享锁；catalog 维护独占锁）
→ pin/event/snapshot/wake/journal writes
```

禁止先锁 effect 再回头获取 run。所有既有行的 SELECT ... FOR UPDATE 必须遵循上述顺序；T2 创建新的 successor ID 不得借机反向锁既有 operation。多行 operation 按 attempt_seq 升序，effect 按 effect_id 稳定排序。

Driver lease 是唯一授权租约，使用数据库 clock_timestamp()；driver_acquire 的 lease_ms 范围 1–60000：

1. 锁 run；当前 lease 未过期且 owner 不同，返回 driver_required、零写。
2. 同 owner 未过期续租不增加 fence；首次获取或任何 owner 过期重获都增加 driver_fence。
3. 返回 owner、driver_lease_until、driver_fence。
4. 每次新 discover/claim/history/accept、内部 worker publish/recover 均校验 owner/fence/expiry；已提交 receipt replay 走 §3.6.4 例外。
5. worker 每次进程启动使用新 driver ID；数据库不证明进程身份，Fake host 必须遵守。无第二 effect lease。

Effect bound claim：

1. discover 只读返回当前 epoch 的 FIFO 下一项。
2. claim 锁 run 后重新校验 driver、unknown wall、已有 claimed effect 和队列。
3. 参数 operation_id 必须是按 attempt_seq 排序的首个可执行 pending operation，且主要 effect 为 ready；不接受 human。
4. 队首不可领取返回 not_claimable；即使用 SKIP LOCKED 也只能检查绑定项，绝不能改领后项。
5. 按固定顺序锁 operation/effect/meta，递增 attempt_no/fence，写 claim_driver_fence 和 immutable pin。
6. 返回 request、idempotency_key 和全部 attempt/fence/pin。新 driver 必须先 recovery，不能越过旧 claimed 工作。

目录维护只获取 meta/tools，不反向获取 run。所有锁持有到当前短事务结束；外部 Fake IO 绝不持有事务。

## 3.8 Unknown、恢复和 closeout

数据库不能保证外部副作用 exactly-once。它只能保证：

- 本地 effect 账本一次 CAS 结算；
- 重复 receipt 可识别；
- driver takeover 后旧 token 可检测为 stale；
- 无法判断外部结果时进入 unknown。

两条合法 unknown 路径：

- 有效 worker 提交 status=unknown，经 driver/token/pin 校验后进入同一 T2；不必等新 driver。
- recover_unknown 校验当前有效 driver 后，只选择 status=claimed 且 claim_driver_fence 与 run.driver_fence 不同的旧 claim；仅 lease 到期但未重新 acquire 不改变 effect。

共用转换：effect 置 unknown、fence 加 1；执行 operation 归档 unknown；追加 effect/unknown；正常 run/snapshot 转 blocked_unknown、发布一次 snapshot wake；无 successors。receipt 路径写 journal，recovery 无 request ID，按状态幂等。

真正 blocked_unknown 的 Phase 0 生命周期出口只有 cancel。poll/wait 和已提交 receipt replay 继续可用，steer/respond/new claim/正常 closeout 均受 unknown_wall 拦截。没有 resolve 动词、隐藏 resolution 函数或自动重放；基于外部证据的 resolution 登记为 Phase 1 偏差。

| 丢 COMMIT 响应场景 | 处理 |
|---|---|
| T2 已提交 | 原 receipt 命中 journal，即使 lease 过期或已接管也能读回 |
| T2 未提交、result 仍在、原 claim 有效 | 原 receipt 重做完整 T2，不重做 Fake IO |
| 无 journal，claim 已失效或 result 丢失 | takeover/recovery 转 unknown，之后 cancel-only |

取消后的 recovery 仅清理账本：允许 acquire 后将遗留 cancel_requested claim 转 unknown，但 run 保持 cancelled，不改写已封存 seal，不发布新 snapshot/wake。取消 seal 记录取消时事实，后续 recovery 另写事件。

单一 `v99_core_closeout` 规则：

- completed/failed：当前执行 operation 先在 T2 中完成；必须无 ready、claimed、unknown effect、无 interaction、无 pending 执行 operation。随后关闭 epoch，写 run/closed seal，更新 run/snapshot，产生一个 terminal wake。控制 operation 均已 completed，不构成阻塞。
- cancelled：允许从 running、waiting_for_input 或 blocked_unknown 进入；事务内 ready effect 置 cancelled；claimed effect 设置 `cancel_requested=true`、递增 fence、保留原结果未知；unknown effect 保留 unknown；关闭 pending operations 和 epoch；seal 必须列出 cancelled、claimed、unknown IDs。取消 seal 不表示外部 IO 已停止，也不表示任务成功。
- cancelled 后迟到 receipt：
  - effect 已 unknown：返回 `unknown_wall`；
  - effect 仍为 cancel_requested claimed：返回 `stale_claim`；
  - 追加 `receipt/late` 审计；
  - 不写 snapshot、不 promotion、不复活 run。
- closeout 不复制 strict/fallback 两条实现；所有分支都由同一函数、同一 seal 格式和同一审计字段完成。
- run/closed 的 seal 恰含 schema_version、run_id、epoch_ordinal、status、cancelled_effect_ids、unsettled_claim_ids、unknown_effect_ids，数组始终存在；completed/failed 的 unsettled/unknown 数组必须为空。events 对 `(run_id,epoch_ordinal) WHERE type='run/closed'` 建部分唯一索引，防止重复封口；terminal steer 不改写旧 seal。

## 3.9 IO 边界与 worker 微观 turn

Fake worker 的精确顺序：

1. 独立短事务 driver_acquire 并 COMMIT；随后独立短事务 recover_unknown 并 COMMIT。
2. T1：discover → bound claim_effect → worker_history，全部通过 service projections；缓存 request/token/history 后 COMMIT。
3. 断言 psycopg2 连接 TRANSACTION_STATUS_IDLE；第二连接应能看到已提交 claim。
4. 在无事务、无网络的 Fake LLM/Tool 中执行，调用后再次断言 IDLE。history 必须在 T1 内读取，不能在 IDLE 断言后隐式重开事务。
5. 保留已知 result；只允许显式 DefinitelyUnsent 类型的最多一次重试，ambiguous failure 必须报告 unknown，不能再次 IO。
6. T2 仅调用 accept_receipt；它负责 ledger、完整 successors、publication/closeout、journal；然后 COMMIT。
7. mid-T2 abort 或丢 COMMIT 响应时，rollback 连接并用原 receipt 重交/读取 journal，禁止再次 Fake IO。
8. worker restart 仅有 run_id 而没有已知 result 时不得执行旧 claimed effect；使用新 driver ID，等待 lease 到期、acquire/recovery/unknown。

LLM 结果：

```text
{
  schema_version: 1,
  text?: non-empty string,
  tool_calls?: [{id, name, args}],
  ce_status?: running|waiting_for_input|completed|failed,
  interaction?: object,
  failure_reason?: object
}
```

以上是闭集：text 与非空 tool_calls 至少一个存在；每个 tool call 恰含 id/name/args，ID 在本次结果内唯一。含 tool_calls 时 ce_status 只能省略或 running，不可携带 interaction/failure_reason；无 tool_calls 时必须显式 ce_status。waiting 必须带合法 interaction，其余状态禁止 interaction；failed 必须带恰含 code/message 的 failure_reason，其余状态禁止。SQL 在 T2 的任何 mutation 之前验证未知工具、参数闭集、task 长度和所有互斥规则，分别返回 invalid_receipt/invalid_tool/invalid_tool_args；Python 预检不能替代 SQL。

Phase 0 Fake tool 只接受：

```text
spawn_subsession(params={task: string length 1..1024})
```

返回恰含 schema_version=1、adapter=ce-fake-spawn、simulated=true、task=请求 task 的对象，不创建子 run、不调用 native spawn。

Fake host 不得：

- 直接 `SELECT/INSERT/UPDATE/DELETE` `v99_core` 控制表；
- 读取数据库连接之外的网络；
- 在事务打开时执行 LLM/Tool；
- 使用 `pgmq`；
- 调用 v13/v15 函数。

## 3.10 六动词行为矩阵

| 动词 | Caller | 主要写集合 | 成功行为 | 关键拒绝 |
|---|---|---|---|---|
| start | operator | run、initial epoch、completed start、pending admit_turn、user event、llm effect、snapshot、wake、journal | 创建唯一 canonical run | invalid_args、unauthorized、request_id_conflict |
| poll | reader/operator | 无 | 返回当前 snapshot/run projection | 未知/越权统一 expired |
| wait | reader/operator | 无 | 按 wake cursor 返回 interrupted/actionable/epoch/waiting/timeout | invalid_wait_args、expired |
| cancel | operator | completed cancel、ready effect、claimed cancel fence、关闭 pending admission/epoch、snapshot、seal、wake、journal | 目标 run cancelled；不级联 | already_terminal、request conflict |
| steer | operator | completed steer、pending admit_turn、可能 human 同步结算、user event、run/snapshot/wake、journal | active FIFO；terminal 新 epoch；不复活 cancelled | stale_epoch、use_respond、unknown_wall |
| respond | operator | completed respond、human 同步结算、pending admit_turn、run/snapshot/wake、journal | 消费当前 interaction，保持 epoch | invalid_response、interaction_mismatch、unknown_wall |

## 3.11 ACL、SECURITY DEFINER 和真实身份

setup 创建或校验角色，40_permissions.sql 只负责最终 ACL，不重复拥有角色生命周期：

- `v99_core_operator`：六动词写入口；
- `v99_core_service`：driver acquire/discover/claim/history/accept/recover；
- `v99_core_reader`：poll/wait；
- setup 创建唯一 LOGIN host roles，分别加入上述 NOLOGIN group。

所有 SECURITY DEFINER 函数：

- owner 为 setup 使用的 pgembed 受信超级用户，同时拥有数据库/schema；
- `SET search_path = pg_catalog, v99_core`;
- 使用 schema-qualified 表名；
- `REVOKE ALL ... FROM PUBLIC`；
- 仅向对应 group GRANT EXECUTE；ledger、human settlement、publish、wake、closeout 等内部函数不向宿主授权；
- 不授宿主控制表裸读写；schema USAGE 和目标数据库 CONNECT 按角色显式授予；撤销 PUBLIC 函数 EXECUTE、数据库 CONNECT/TEMP、schema CREATE，并设置 owner 默认权限以防新函数重新获得 PUBLIC EXECUTE。

`v99_core_caller_role()`：

1. 读取 `current_setting('role', true)`；
2. `NULL`、空字符串或 `none` 时回退 `session_user`；
3. 验证角色存在；
4. 用 `pg_has_role(caller, group, 'USAGE')` 判断 operator/service/reader。

`p_actor` 不是认证来源。Phase 0 不建 principal 表，因此：

- start 只接受 p_actor=NULL；
- 其他入口接受 NULL 或目标 run_id；
- 任意其他 UUID 都是 unauthorized；
- service 不可调用六个控制动词。

setup 必须使用真实非超级用户 LOGIN（无 CREATEDB/CREATEROLE，仅加入职责 group）连接验证正例；超级用户单独调用不能作为 ACL 证明。actor 只校验目标关系，不表达租户认证或所有权。

固定 group 生命周期由维护数据库连接上的 v99-core-setup 会话 advisory lock 串行化，覆盖 fixture 生命周期；既有 group 只校验，不修改或删除。只清理由本 fixture 创建且记录 name/OID 匹配的数据库和角色。

## 3.12 Wait、NOTIFY 和游标

v99_core_wait_check 在同一个数据库读快照内完成只读、无锁副作用检查，优先级：

1. 参数非法返回 invalid_wait_args；
2. run 不可见或 registration 不匹配返回 expired；
3. 请求 epoch 大于当前 epoch 返回 invalid_wait_args；
4. 按 run+registration+`wake_id > after_wake_id` 查最早未读 steering wake，返回 interrupted_by_steering；不按请求 epoch 过滤，旧 epoch waiter 也能拿到 terminal steer 正文；
5. interaction 或 terminal snapshot 返回 actionable；blocked_unknown 也为 actionable，避免无限等待已阻塞 run；
6. 请求 epoch 小于当前 epoch 返回 epoch_advanced；
7. 否则 waiting。

steering 正文放在返回 DTO 的 snapshot.steering_message 中，不增加顶层键；所有授权 reader 可见，不做 self-origin 隐藏。返回最早 steering wake 的 ID；没有未读 steering 时可推进至本次读快照可见的最大 wake ID。重复游标允许重复交付，不同 waiter 各自推进。timed_out 只由 Python helper 在 deadline 最后一次检查仍为 waiting 时生成。

内部 v99_core_wake 同事务插入持久 wake，并调用 pg_notify('v99_core_run_changed', run_id文本 || '|' || revision文本)。通知提交后才可见，payload 只提示重查：

| publication 写入者 | wake reason |
|---|---|
| start、respond、普通 running/waiting publication | snapshot |
| active/terminal steer | steering_requested |
| completed/failed closeout | terminal |
| cancel closeout | cancelled |
| reported/recovered unknown，run 尚未 cancelled | snapshot |

每次 publication 恰一个 wake，terminal/cancel 不叠加 snapshot wake。replay、旧 driving 归档、claim、续租和取消后账本 recovery 不发 wake。

`ce_wait`：

- 起始连接必须 IDLE；
- 参数检查失败时零 SQL；
- 默认轮询间隔 50ms，允许范围 10ms–1s；
- timeout 允许 0–3600 秒；
- 每次检查都是短读事务，事务结束后才等待；
- 可 `LISTEN v99_core_run_changed`，但通知 payload 不可信；
- 通知丢失时 deadline 前后都重新读表；
- finally `UNLISTEN` 并保持连接 IDLE；
- 同一 waiter 携带 `after_wake_id`，不同 waiter 可以分别看到同一 wake。

## 3.13 No-network gate

明确使用 psycopg2：local_dsn 用 psycopg2.extensions.parse_dsn 解析 pgembed URI；事务状态使用 conn.info.transaction_status 与 TRANSACTION_STATUS_IDLE；deadline 使用 Python 单调时钟。

DSN 必须显式包含单个绝对 Unix socket host（host.startswith('/')），且与 pgembed 实际 socket 路径一致。拒绝缺失 host、127.0.0.1/TCP、hostaddr、多 host 和 service 间接配置，不允许 libpq 默认 host 回退。

Python socket monkeypatch 只证明 Python 层行为，不能声称覆盖 libpq 的 C 层 socket；数据库连接本地性由 DSN 验证保证。

`test_core.py` 静态检查：

- 扫描 Fake host/runtime 的 AST/import，禁止 socket 网络构造、requests/httpx/openai/provider SDK；测试 guard 自身可 import socket 以拦截，并用负例证明扫描未被通配排除；
- Fake host 源码不得出现 `pg_sleep`、native spawn、控制表裸 SQL；
- monkeypatch socket，仅允许 `AF_UNIX`；
- 若捕获 `AF_INET`/`AF_INET6`，立即失败；
- subprocess 只允许 setup 所需 `psql` 或 `uv` 命令；
- Fake IO 回调前后断言 `TRANSACTION_STATUS_IDLE`；
- 不在 gate 中打开真实 provider、网络或 API key。

# 5. Risks and migration

## 5.1 双租约漂移

缓解：删除 effect lease 字段/参数；只有 run driver lease 加 effect attempt/fence。G6 验证双 driver 竞争、有效续租不改 fence、过期重获递增 fence、旧 receipt 新结算失败和单 run 单 claim。短 lease 测试用 Python 单调时钟、有总时限的轮询，不用 pg_sleep 或长 sleep。

## 5.2 Cancel 与 unknown 混淆

缓解：cancel seal 明确区分 `cancelled_effect_ids`、`unsettled_claim_ids`、`unknown_effect_ids`；completed/failed 不能绕过 unknown；迟到 receipt 只能 stale/unknown。

## 5.3 Pin 失配

缓解：pin 记录 request/context/catalog/driver；human pin 的 driver 为 NULL；claim/accept 锁 meta 防目录变更竞态。失配返回 stale_claim，不伪造成功；无 journal 的旧 claim 按 takeover/recovery 进入 unknown。G1/G3/G7 用 owner 注入 context/catalog 变更，证明宿主不能改 pin，且已提交 replay 不被后续版本变化破坏。

## 5.4 NOTIFY 丢失

缓解：NOTIFY 只唤醒；wait deadline 前后重新读取 wakes/snapshot；测试无 listener、丢 payload、通知先后反转。

## 5.5 Fake host 越权

缓解：worker 仅调用 projection functions；静态扫描禁止控制表 SQL；非超级用户 service/reader 角色运行正例和裸表负例。

## 5.6 Schema 漂移

缓解：setup before/after catalog 差分；关系、函数签名、ACL、owner、search_path、索引和触发器使用闭集断言。

## 5.7 提交边界污染

缓解：唯一里程碑完成前不提交；提交时只逐路径 `git add` `v99/core/**`、两个 review docs 和计划文件；严禁 `git add -A`、`git add .` 或加入 `demo_v15`、其他 docs。

## 5.8 Unknown、T2 与保留周期的边界

真正 unknown 的生命周期出口只有 cancel；失去 result 的进程不能证明外部副作用结果。G5 区分已提交 journal、未提交但 result 保留、result/claim 丢失三类，防止把丢响应直接判为 unknown。无 unknown resolution、无生产 retention 明确进入偏差台账。

完整 T2 由 accept_receipt 拥有，G3 在 settlement 后故障注入，验证 successors/publication/journal 一起回滚；重交同 receipt，Fake IO 次数仍为 1。events/wakes/requests/pins 仅随临时库清理，不能宣称支持无限期生产运行。

## 5.9 数据迁移与回滚

Phase 0 不迁移 v13 数据，也不提供 v13→v99 转换。失败时只删除本次创建且 OID 匹配的临时数据库和角色；旧 v13/v15 栈完全保留。生产回滚等价于停止使用 `v99/core`，无需回滚历史 loader。
