# pg-agent v6.1 · 代码工作台 + 文件工作台开发方案

**日期：** 2026-09-17
**状态：** 方案（未开工）。2026-09-18 turn 4 仅修订 B005/B006/B010 的统一 mutation 合同（§3.6–3.9 及对应接口/阶段）。父独立审核的最近有效结论仍为 P0=0/P1=8：B001–B004 plan-level CLOSED，B005–B012 OPEN；本轮三项仅为候选关闭，等待父控制器完整方案 L4 复核，不自行降低计数。全部新增 gate 均 NOT RUN，D1–D6 均待用户确认。B007/B008/B009/B011/B012 未解决；阶段顺序与 gate 纪律沿用 v6。
**定位：** 在 **不改动 v1–v6 任何文件** 的前提下，仿照 v6 的数据工作台架构，增加两条工作台轨道：
1. **代码工作台** —— `sitting_duck`（AST 即数据）；
2. **文件工作台** —— `duck_block_utils` 及其同作者插件族（文档块即数据）；
3. **存储** —— 代码文件与一般文件存放在 **tigerfs**（每个文件是一条 PostgreSQL 行），tigerfs 由 pgembed 打包。

## 0. 结论摘要

- **架构可复用性高**：v6 已经把「PG 是事实源、SQL 只入队、库外 worker 执行、bounded 结果回写、op_seq 定序、artifact 依赖与重放」搭成完整骨架。代码/文件工作台是同构的第二条平面，但不能直接复制为安全/一致性证明，必须补齐身份、权限及后续 CAS/receipt/replay 合同。
- **有一个必须先解决的硬约束（ABI 墙）**：v6 的 DuckDB 是 **dev 构建的 fork**（`1.6.0.dev366+ga1f0ab1911`），而 `sitting_duck` / `duck_block_utils` 是 **面向已发布版本构建的 CPP-ABI 社区扩展**。源码判据表明二者**不能直接互载**（§2.5.1）。
- **推荐架构：双平面**（D1-A）。数据平面保持 v6 原样（fork DuckDB，无文件访问）；代码/文件平面 = **独立 worker 进程 + 独立 uv 环境 + 已发布版 DuckDB + 官方签名的社区扩展**。两平面只通过 PG 表与 PGMQ 通信，不共享进程内状态。
- **文件读取默认走「行读」而不是「挂载点读」**（D2-A）：`parse_ast(code VARCHAR, language VARCHAR)` 接受**内容作值**，所以解析路径**完全不需要文件系统访问**，v6 的 `enable_external_access=false` 姿态可以逐字保留。tigerfs 挂载点用于人和其他工具按真实路径访问。
- **第一个破坏性能力**：文件工作台是**可写的**。v6 全程只读；写能力需要用户显式批准，并单独设 gate（§7 D4）；产品批准不是运行授权，每个持久化请求仍须通过 §3.3 的默认拒绝检查。
- 建议分 12 个阶段（K1、P1、S1–S10），其中 **P1 是 go/no-go**。

## 1. 目标与非目标

### 1.1 目标（v6.1 第一版必须完成）

1. 代码文件与一般文件存放在 tigerfs（PG 行），有稳定的路径身份、内容哈希与 generation；
2. 把文件注册进当前 run 的代码工作台，解析为 AST，得到命名 artifact；
3. 后续只读 SQL 引用该 artifact 形成**链式分析**（与 v6 的 source→view 链同构）；
4. 提供**有界**预览、列信息、定义、列表、受依赖保护的删除；
5. 文件工作台：读、写、补丁、列表、stat、删除，以及「文档块」抽取与渲染；
6. 代码 AST 与文档块可组合：`ast_to_blocks()` → `db_*` 块操作 → 渲染回文档；
7. SQL 侧 named tool 全部 enqueue-only；DuckDB、挂载/网络 IO 在库外完成；权威 PG 字节变更与 receipt 由 §3.8 同库短事务完成（不是在事务内调用文件系统）；
8. 统一四段式错误信封 `{Type, Phase, Problem, Solution}`；
9. PGMQ 异步、visibility timeout、DLQ、op_seq 定序、worker 崩溃恢复；
10. 不修改 v1–v6 任何字节；不改 repo 根 `pyproject.toml` 的 duckdb pin。

### 1.2 明确不做（v6.1 核心版外）

- 不做 git 感知分析（`duck_tails`）——保留为后续版本的候选；
- 不做运行时 grammar 注册（`sitting_duck` 的 `register_language()`，需要打开 `sitting_duck_enable_runtime_grammars`）；
- 不做跨平面原子提交（与 v6 的边界一致）；
- 不做分布式 / 多机；不做 Linux/Windows 矩阵；
- 不做自动改码回写仓库（AST 改写只在显式 `wb_file_write` 下发生，不做自动 patch-apply 流水线）；
- 不把 tigerfs 的 `.history/`/`.undo/` 纳入 v6.1（需要 TimescaleDB preload，见 §2.4）。

### 2.2 sitting_duck 能力面（代码工作台）

- 定位：**DuckDB 官方社区扩展**（C++，MIT，maintainer `teaguesterling`），把 tree-sitter AST 变成可 SQL 查询的扁平表。社区条目 `duckdb-web/community_extensions/extensions/sitting_duck.md`（扩展版本 1.7.4）。
- 构建名与产物名不一致：`CMakeLists.txt:4` 为 `TARGET_NAME sitting_duck`，`Makefile:4` 为 `EXT_NAME=duckdb_ast`。
- **内容入口（关键）**：
  - `parse_ast(code VARCHAR, language VARCHAR)` → TABLE，`src/parse_ast_function.cpp:178`；
  - `parse_ast_list(code, language)` → `LIST<STRUCT>`，`src/parse_ast_list_function.cpp:241`。
  两者吃**内容字符串**，不吃路径 ⇒ 解析无需文件系统访问。
- **路径入口**：`read_ast(file_patterns ANY [, language VARCHAR])`，`src/read_ast_streaming_function.cpp:636,659`；命名参数含 `ignore_errors / context / source / structure / peek / batch_size / max_depth / prune / max_source_bytes / parse_timeout_ms / max_parse_nodes`。这些预算参数与 v6 的 budget 概念一一对应。
- **扁平 schema 是 19 列**（权威在代码，不在文档）：`src/unified_ast_backend.cpp:356-361` —— `node_id, type, name, file_path, language, start_line, start_column, end_line, end_column, parent_id, depth, sibling_index, children_count, descendant_count, scope, peek, semantic_type, flags, qualified_name`。README/`API_REFERENCE.md` 仍写「21 列」⇒ **文档漂移，gate 必须按代码与 `ast_supported_languages()` 实测断言**。
- 约 100 个 SQL 宏（`src/sql_macros/*.sql`，编译期嵌入）：`ast_children / ast_descendants / ast_definitions / ast_get_calls / ast_call_graph / ast_find_references / ast_function_metrics / ast_select / ast_match / ast_patch / ast_to_blocks` 等。
- 与文件工作台的接缝：`ast_to_blocks()` 产出 duck_block，正好交给 `duck_block_utils.db_render_blocks()` 渲染 ⇒ 两轨道可组合（§1.1 第 6 条）。
- 上游 pin：duckdb submodule `b155d6f`（branch `v1.5-variegata`）；CI 对 v1.5.4 构建。**这是 ABI 墙的根源**。

- **`duck_block` 本身是一个 STRUCT 类型，不是插件**；提供能力的是 **`duck_block_utils`**（`duckdb-web/community_extensions/extensions/duck_block_utils.md`，扩展版本 1.2.1，MIT，作者同上）。本机未克隆该仓库。

- 同作者可用的兄弟插件（均在 duckdb 社区扩展表内）：`webbed`（XML/HTML+XPath，**本机已克隆** `~/Projects/duckdb_webbed`）、`markdown`、`read_lines`（带行号读文本）、`duck_tails`（git 感知）、`duck_hunt`（测试/CI 日志 110+ 格式）、`duckdb_mcp`。

### 2.4 tigerfs 现状（存储）

- **不是 pgembed 的一部分，也不属于本用户**：上游是 `timescale/tigerfs`（Go，Apache-2.0），版本 v0.7.0，本地 checkout `~/Projects/tigerfs`。
- **pgembed 已打包**（这是「要用起来了」的现状）：`pgembed/pgbuild/Makefile:49` 的 `EXTENSIONS` 含 `tigerfs`；下载目标 `:687-696`，从 timescale release 取预编译二进制，四个平台 SHA-256 钉死；`EXTENSIONS` 里它走**独立分支**而非 `extensions{}` 清单。
- **本机已可运行**：`pgembed/src/pgembed/pginstall/bin/tigerfs`（12.9 MB，2026-09-16 构建），`tigerfs version` → `TigerFS 0.7.0 / darwin/arm64`。
- **接口形态：单一 Go 二进制 + CLI**。不是 SQL 扩展、不是 Python API。子命令 `mount / unmount / list / status / info / stop / version / migrate / config / create / fork / test-connection`。挂载机制：Linux = 内核 FUSE；**macOS = 用户态 NFS（免 root）**。
- **映射**：表=目录，PK 值=行目录，列=文件；扩展名按类型（`.txt`/`.json`/`.bin`）。行文件支持 TSV/CSV/JSON/YAML 的 PATCH 语义。
- **事务与并发**：每个 fs 操作 = 一条 SQL 自动提交；row-as-file 写 = **单条 UPDATE（原子）**；row-as-directory 多列写 = **多条 UPDATE（非原子）**；MVP 无显式事务；并发靠 PG MVCC，**last-write-wins**，无 fs 级锁。
- **大文件**：分块写，macOS NFS `wsize=128KB`；多 chunk 存在 **O(n²) 写放大**（1 MB 文件约产生 4.5 MB 库写）。⇒ v6.1 必须设文件大小上限，并优先走行读/行写。
- `.history/`/`.undo/`/`.savepoint/` 需要 **TimescaleDB preload**；v6.1 不纳入（§1.2）。
- pgembed 本体：`pgbuild/Makefile:72` → **PostgreSQL 18.4**；已打包扩展 14 个（pgvector/vectorchord/age/psql_bm25s/timescaledb/pg_cron/pg_net/pgsql_http/plsh/firebird_fdw/pgmq/pg_partman/pgtap/pg_jsonschema）；**pg_duckdb 不存在且被测试显式否定**。
- pg-agent 现状：**完全没用 tigerfs**，唯一提及是 `docs/plans/v4-expansion-2026-08-28.md:134` 的 bundle 清单。

### 2.5 三条硬约束

#### 2.5.1 ABI 墙（最高风险）

源码判据：

- CPP / C_STRUCT_UNSTABLE 两种 ABI **要求 duckdb 版本精确相等**：`duckdb-pgagent/src/main/extension.cpp:48-57`——"The file was built specifically for DuckDB version 'X' and can only be loaded with that version"。
- 版本目录名的取法：`duckdb-pgagent/src/main/extension/extension_install.cpp:36-45`——release 构建取版本号，**dev 构建取 `SourceID()`**。
- fork 是 dev 构建（`v6/README.md`：`library_version=v1.6.0-dev13823`、`source_id=a1f0ab1911`），其 `CMakeLists.txt:563-571` 把扩展目录名规范化为 **git hash**。
- 本机实测旁证：`~/.duckdb/extensions/a1f0ab1911/osx_arm64/` **为空**；而已有产物都在 `v1.5.5/`、`v1.5.5` 之外的历史目录下。

⇒ 任何要载入 v6 fork 的扩展，footer 里的 `duckdb_version` 必须是 `a1f0ab1911`，即**必须用这份 fork 源码树构建**。`allow_unsigned_extensions=true` 只绕过**签名**校验，**不绕过版本/平台校验**。`sitting_duck` 面向 v1.5.4 构建 ⇒ 预期不可载入。

> P1 阶段必须**实测**这条（把结论从「源码判据」升级为「证据」），它是 D1 决策的唯一依据。

#### 2.5.2 文件访问沙箱（可控，不是墙）

- v6 连接硬化最后一步是 `SET enable_external_access=false`（`v6/session_durability/duckdb_grammar.py:259,277`）。
- DuckDB 另有白名单：`allowed_directories` 的语义是「**即使 enable_external_access=false 也始终允许查询的目录前缀**」（`duckdb-pgagent/src/include/duckdb/main/settings.hpp:267-276`），执行点在 `duckdb-pgagent/src/main/config.cpp:924-960`（`CanAccessFile`，经 `OpenerFileSystem` 对每次 open 生效）。
- **但 setter 有顺序约束**：`duckdb-pgagent/src/main/settings/custom_settings.cpp:270-278` —— external access 为 false 时**拒绝**修改 `allowed_directories`，且 DB 未启动时也拒绝。⇒ 正确次序是：`LOAD 扩展` → `SET allowed_directories=[...]` → `SET enable_external_access=false`。

⇒ 这些是 fork 源码中的目录例外机制，**不是所选 release/扩展已验证的隔离证明**。放开前缀比完全禁文件更宽松；它既不识别 run/workspace，也不证明 native 函数遵循同一文件系统检查。D2-B 必须通过 §3.4/3.5 的资格 gate；未经证明时 fail-closed，不能以目录白名单替代授权。

#### 2.5.3 版本 pin 不可就地改

- 根 `pyproject.toml` 的 `duckdb==1.6.0.dev366+ga1f0ab1911`（`[tool.uv.sources]` 指向 `../duckdb-python-pgagent/dist-special-g1/...whl`）是 v6 的身份门（`v6/session_durability/duckdb_grammar.py:19-21` 的 `EXPECTED_*`）。
- `v7/README.md` 已明文：「v6 的 duckdb pin **不得就地**改成 v7 wheel」。
- ⇒ 代码平面必须有**自己的环境**，不能靠改根 pin 实现；也不能在同一进程里 import 两个 duckdb（模块名冲突）。

## 3. 架构决策

### D1 — 代码/文件平面用哪个 DuckDB？（推荐 A）

**A. 双平面（推荐）**
数据平面保持 v6 原样；新增**独立 worker 进程 + 独立 uv 工程**，pin 一个**已发布版 duckdb**（社区渠道实际提供 sitting_duck 构建的那个版本，本机旁证为 v1.5.5），用官方**签名**社区扩展：`INSTALL sitting_duck FROM community; LOAD sitting_duck;`（同 `duck_block_utils`/`markdown`/`read_lines`/`webbed`）。两平面只经 PG 表 + PGMQ 通信。

- 优点：零移植风险；无自建 unsigned 扩展；不动 v6 身份门；不与 fork 的 grammar 机制纠缠；两平面可独立 gate。
- 代价：第二个 venv、第二个 worker 进程、第二条队列、第二份依赖预算。

**B. 移植到 fork（备选）**
把 `sitting_duck`/`duck_block_utils` 的 duckdb submodule 指向 `/Users/wxl/Projects/duckdb-pgagent`（a1f0ab1911）后重建，按 v6 的 grammar 扩展模式做 SHA-256 钉死 + unsigned LOAD。

- 优点：单 DuckDB、单 worker、两工作台共享一个会话。
- 代价：v1.5-variegata → 1.6.0-dev 的 CPP API 漂移移植（含 vendored tree-sitter 与 30 个 grammar），维护面转移给自己，且产物是 unsigned。

**推荐 A**，理由：v6 已经证明「worker 的 DuckDB 是 PG 合同背后的实现细节」；A 把不确定性放在**环境**里而不是**代码**里。P1 产出决策记录；B 在 P1 中做**限时**可行性尝试（时间盒），失败即关闭。

### D2 — 文件内容怎么进 worker？（推荐 A）

**A. 行读 / 行写（推荐）**：可信 ingress 经 psycopg2 调用受限 PG 行读取接口，把已授权内容作为**值**喂给 `parse_ast(code, language)`；持久化只能经 §3.2/3.8 的 mutation 接口。字节、CAS、receipt 与 durable fence 统一按 §3.6–3.8，不以单条 UPDATE 或 per-run op_seq 代替。
- 为什么：解析路径**完全不碰文件系统** ⇒ v6 的 `enable_external_access=false` **逐字保留**；避开 NFS 的 O(n²) 写放大；避开 row-as-directory 的多条非原子 UPDATE；在容器/CI 里不需要挂载也能跑 gate。
- 代价：需要 §3.2 的多角色受限接口，而不是给 worker tigerfs/agent 表的直接 DML；挂载点与行内容必须满足 §3.6 的统一字节/CAS 合同，不能维护异步 hash 镜像。

**B. 挂载点读写**：仅可信 ingress / mutation 服务可使用经过资格验证的挂载适配器；用户 SQL 会话永不获得挂载目录例外。§2.5.2 的设置只是纵深防线，还须满足 §3.1–3.4 的身份、授权和防逃逸检查。
- 为什么可能仍需要：`read_ast(路径)` 形态、二进制/大文件、以及让 worker 看到与其他工具**逐字节相同**的视图。

**推荐 A 为默认路径，B 作为可选路径**（两者共用同一 artifact 身份与 hash 校验，不产生两条真相）。**待确认**：见 §7 D2。

### D3 — 文件工作台是「一个平面」还是「两个平面」？

**推荐：一个平面，两个工具族**。`sitting_duck` 与 `duck_block_utils` 同作者、同 ABI 前提、同文件访问需求、且可组合（`ast_to_blocks` → `db_render_blocks`）。拆成两个 worker 会带来两条队列却没有收益。⇒ 一个 `codefs` 平面，对外暴露 `wb_code_*` 与 `wb_file_*` 两族 named tool。

### A1 — 定序：共享还是各自一条序列？（内部架构项，非用户 D4）

**推荐：每平面各自一条 op_seq**（`codefs_sessions.next_op_seq` 独立），不复用 `duck_workbench_sessions`。理由：不触碰 v6 表；避免跨平面耦合把两条独立链路的失败互相传染；与 v6「一个 stage 一个库」的隔离纪律一致。

### 3.1 身份与 run 边界（V61-B001）

以下是 S1 DDL 之前必须固定的逻辑合同；P1 只选择 tigerfs 的物理映射，不得把路径列重新当作全局身份。

- `workspace_id UUID` 由可信 workspace 管理端分配，绑定唯一存储根/adapter；显示名、挂载前缀及调用参数 `workspace` 都不是权限证据。D5 决定独享/共享布局，不改变此隔离键。
- 文件身份是 `(workspace_id, object_id UUID)`，`object_id` 由服务分配且永不复用。活动路径只设 `UNIQUE(workspace_id, canonical_path)`；同一相对路径可同时存在于两个 workspace，绝不能以 `path PK` 跨 workspace 去重。tigerfs PK/parent/filename 到该身份的映射必须唯一可核验。
- `canonical_path` 是区分大小写、Unicode NFC 的 UTF-8 相对路径，`/` 分段；拒绝绝对路径、空段、`.`、`..`、反斜杠、NUL/控制字符及非规范输入，不静默折叠别名。传输层恰好解码一次；授权后禁止再次 URL 解码/路径重写；任何适配器的大小写/Unicode 别名冲突必须拒绝注册，不能合并对象。prefix 授权按路径段匹配，`a/` 不包含 `ab/`。
- rename 保留 `object_id`，原子更新路径绑定；跨 workspace 的 move 不是 rename，须显式授权的 copy/create + remove，并创建新对象。删除保留身份墓碑；同路径重建分配新 `object_id`，即使内容相同也不是旧对象。旧 artifact、排队请求与授权不得自动转指重建对象。rename 不是新增必需 named tool，但外部/管理端 rename 也须遵循本合同。
- ingress 在授权下将路径解析一次，排队绑定明确 `object_id`；create 绑定 workspace + 未占用规范路径，并预留新对象身份。worker 不得执行时按旧字符串重新选择另一对象；路径授权须同时复核当时与当前路径，rename 出授权范围即拒绝。版本/ABA 比较按 §3.6；请求不因重试刷新 expected_version。
- `principal_id` 来自认证网关，`run_id` 来自服务端 run 注册表；服务端绑定 `(principal_id, run_id, allowed_workspace_ids)`。named tool 不接受自报 principal；自报 workspace 只是选择器。共享 DB login 下，网关签发不可伪造、短期且绑定 principal/run/audience 的 `auth_context`，受限 PG 接口验证后再查活动 run/membership；可写 GUC、SQL 参数、prompt、队列消息均不能建立可信身份。未实现可信上下文验证则禁用接口，不能退回 `current_setting` 即授权。
- artifact 键为 `(run_id, artifact_id)`，命名唯一性为 `(run_id, artifact_name)`；source/file 引用完整 workspace/object 身份。注册、查询、预览、列表、stat/search、blocks/render、依赖遍历及恢复均校验当前 run 的活动 read grant；list/search 先授权过滤再枚举，拒绝不得泄漏另一 workspace 的路径、内容或存在性。
- D2-B 额外要求：根内逐段解析且不跟随 symlink，拒绝 symlink/hardlink 别名、`..`、根替换及检查后路径替换；授权的对象与实际打开对象须一致。证明不了 race-safe 根约束/对象绑定的 adapter 不得启用，不许退化为字符串前缀检查。人工/外部挂载写也必须经过同一受控身份/授权边界；原始表凭据不可授予普通挂载客户端。

### 3.2 最小权限与状态转换接口（V61-B002）

这是 v6.1 新接口设计，不是 v6 现有函数已满足的声明。两条连接本身不能构成权限隔离。下表的 runtime login 均非 owner、非 superuser、无 BYPASSRLS、无 CREATE/SET ROLE 到 owner 的能力；模型/用户 SQL 无 PG 凭据。

| 权威主体 / login | 允许的窄接口（拟定名称） | 禁止的直接权限 |
|---|---|---|
| 认证网关 / `codefs_frontend` | 校验 `auth_context` 后调用 `enqueue_codefs_operation`、读取当前 run 的有界状态 | agent/tigerfs/授权表 DML；PGMQ send/read/delete；claim/apply；自行创建 grant |
| 调度执行端 / `codefs_executor` | `claim_codefs_next(worker_identity)`、`renew_codefs_claim(request_id, attempt_token)`、`open_codefs_session`、`mark_codefs_session_lost`；调用 ingress/mutation/apply 接口 | 任意状态/文件表 SELECT 或 DML；自选 principal/run 的 claim；直接 PGMQ 操作；owner 角色切换 |
| 文件 broker / `codefs_storage` | 已验证 request/attempt 下的 `read_codefs_object`、`list_codefs_objects`、`mutate_codefs_object` | 通用 SQL 执行接口、任意表/路径访问、直接表 DML、grant 管理；查询子进程不得持有此凭据 |
| 收尾调度端 / `codefs_controller` | `apply_codefs_result`、`resume_codefs_run`、`archive_codefs_request`、`deadletter_codefs_request`，均须 request + attempt + 已记录状态 | 文件写、grant 创建、任意状态 DML、直接 PGMQ archive/delete |
| 授权管理端 / `codefs_authorizer` | `grant_codefs_access`、`revoke_codefs_access`、关闭 run/workspace 授权；只能管理自身委派范围 | 业务文件/会话 DML；以执行端身份自行扩大授权 |
| 迁移端与 NOLOGIN owners | 迁移端离线部署；state / storage / auth 分开所有权；另设 §3.8 `codefs_commit_owner`，仅获固定协调事务所需的表/列权限及私有 helper EXECUTE | runtime 继承 owner；模型触达迁移凭据；通用动态 SQL / 任意状态 setter |

- named tools 保留 `VOLATILE SECURITY INVOKER`，但只转交受控 enqueue 接口；INVOKER 本身不授予底表权限。内部窄接口使用经过审查的 `SECURITY DEFINER`（或等效可信服务边界），REVOKE PUBLIC EXECUTE，按签名逐项 GRANT；固定安全 `search_path`、完全限定对象名、参数作为值、不信任临时 schema/用户函数/调用者 owner 名。state owner 不拥有文件表；storage owner 不拥有 run 状态表；auth owner 不拥有业务内容。禁止直接暴露 v6 helper 作为旁路，也不修改 v6 文件。
- 每个内部接口验证真实调用角色、服务端 request 记录、principal/run/workspace/object 绑定、当前授权及合法前置状态；凭一个 request UUID 不足以执行。`claim_codefs_next` 从服务端分配给该 worker/pool 的就绪队列选择，不接受调用者指定任意 run；只返回该请求的短期不透明 attempt token。客户端提交的 op_kind、scope 或队列 payload 不能覆盖台账。
- `open/mark_lost` 只改变当前 claim 所属 session 的枚举状态；`renew` 只延长仍活动的当前 claim。`apply` 只接收与台账匹配的结果 envelope，不允许任意 artifact upsert/状态字段；重新检查依赖及授权，不接受跨 run、过期或不匹配 attempt。`resume` 只恢复已 apply 的可恢复 continuation，不能指定另一 run 或自行推进 op_seq。
- `archive_codefs_request` 指队列归档，不是 artifact 删除：只允许已记录 terminal + apply/resume disposition 的请求；等待前序/可重试请求不能冒充 terminal。`deadletter` 只允许已记录的 terminal failure/耗尽重试，保留有界脱敏原因，不授予重放或文件写权。mutation 的重试、已提交写后撤销/DLQ 按 §3.8；完整 worker/队列生命周期仍属 B011。
- 撤销/到期后的拒绝收尾使用独立的 controller 终态权限：仍验证 request/run/attempt 与已记录状态，但不要求复活原 read/write grant；只可记录脱敏 `authorization_denied`、终止 continuation 并按合法 disposition 归档/DLQ，不得借 cleanup apply 发布成功 artifact 或披露内容。§3.8 保证合规 mutation 不会产生“文件已提交但无 receipt”；发现此情况视为完整性破坏，隔离且不猜测重写。
- 文件 broker 只能按台账载明的 op 执行受限读取或一次 mutation 意图，不执行模型 SQL。`mutate_codefs_object` 只接受固定 action 与绑定的对象/内容证据；它不能代替 claim/apply/resume。revoke 只能由 authorizer 执行，worker 不得自授或复活 grant。外部 provider/文件 IO 不得置于 agent 状态事务内。

### 3.3 单次操作授权与持久化分类（V61-B003）

**D4 是产品写能力批准，尚未批准；不是 grant。** 未批准时写入口在广告、enqueue 和 mutation 边界均禁用。批准后仍 default deny；capability 元数据和 live prompt 仅用于发现，不授予执行权。D5 的默认只读不删除必需写能力：只有另行授予精确写权限的 run 才能使用它。

- 服务端 grant 至少包含 `grant_id, principal_id, run_id, workspace_id, actions, object_scope/path_scope, content_constraints, not_before, expires_at, revocation_epoch, status`；由 authorizer 根据已认证授权主体创建，不能由工具参数自证。scope 为确切对象集或分段路径子树；动作严格区分 read/list/register/query/render、create/overwrite/patch/remove/rename；remove/rename 还检查依赖与源/目的域。期限必填，不给 wildcard/infinite 隐式默认值。
- 每个 request 生成不可变 `operation_authorization`：绑定 grant/epoch、principal/run、workspace、确切 action、对象或 create 目标、规范路径，以及写入/patch 内容的 digest/长度/约束、有效期限；这些证据由可信端生成/验证，不信任调用者提供的 hash。grant 可限定内容 digest 集或服务端校验的内容策略；不得仅以“可写某目录”授权任意 action/内容。read 也需有效 grant，SQL source/artifact 的权限不能扩大源权限。
- create/overwrite/patch/remove 以及任何 render 后自动保存、导出、复制、元数据驱动写路径、管理/挂载修改都是文件 mutation，必须命中明确 action；用户 SQL 不允许通过函数副作用间接执行。`wb_file_render(..., path, block_query)` **只返回有界渲染结果，不保存 tigerfs 字节**；path 仅为已授权源/格式上下文，不是输出目的地。持久化须另调 `wb_file_write` 并重新授权，其路径/内容证据不能继承纯 render 的 read grant。注册/命名 view 的受控 artifact 元数据持久化由 state 接口授权，不等于文件写权限。
- 检查点：enqueue 前、claim 后/读取内容前、**实际文件 mutation 提交边界**及结果披露前。不能等到 `apply_codefs_result` 才检查，因为文件副作用可能先于 apply。直接调用 named tool、内部 mutation、恢复/重试、外部挂载入口都不能跳过检查。
- revoke 更新 grant 状态/epoch；排队快照不是永久通行证。实际 PG mutation 与最终 grant 检查必须在同一授权序列化边界内（锁定相关 run/membership/grant 状态至短事务提交；revoke 获取冲突锁），权限关闭/到期同样检查。revoke 已返回后尚未提交授权的请求不得产生文件副作用；若 mutation 先取得锁并提交，revoke 等待它完成后才确认，不承诺回滚既有提交。外部挂载适配器若无法实现等价顺序就阻塞该写模式，不能只做“写前查一次”。该授权线性化与 §3.8 的同库锁序、CAS/receipt 共用一个提交边界；grant 到期在最终 mutation 线性化检查时判断，不把旧排队快照当通行证。
- 被拒请求只允许记录有界拒绝审计/终态；文件字节、路径绑定、generation、用户 artifact 不变，不读取/披露未授权内容。撤销后的已提交结果只能作内部脱敏恢复，不能重新执行 mutation 或披露内容；最终 receipt/recovery 按 §3.8 的 `committed_redacted` 收尾，不把已提交写误报为未写或再次执行。授权检查基础设施不可用、身份/内容证据不完整均拒绝，不能 fallback 到宽角色。

### 3.4 可信 ingress 与任意 SQL 的不同通道（V61-B004）

**SELECT-only 仅为必要条件，不是 native 扩展的沙箱证明。** 本节限定授权边界；B008/B009 的实际 schema、完整源文本及 blocks API 链仍待后续修订，不能把它们标为已解决。

1. **可信 ingress**：闭集 dispatcher 接收已授权 request，不接收自由 SQL；D2-A 经 `read_codefs_object` 获取值，再调用版本清单中已审查的 `parse_ast`/内容型插件入口。只有它能持 storage 凭据。D2-B 若获批准，只在独立受控 ingress 进程通过合格 adapter 读取精确授权对象，不能把开放目录的连接借给 query。`markdown/read_lines/webbed` 等必需能力必须证明内容型适配链；没有合格入口则阻塞交付该必需能力，不得删除需求或偷偷用路径/网络入口替代。
2. **用户 query / block_query**：独立隔离会话/进程只接收当前 run 已授权 artifact 的有界数据；即使共享 workspace，不同 run 也不得共用可读取对方内存/缓存的 query 进程。不持 PG/storage 凭据，不挂载工作区、不继承 ingress 的文件/网络句柄。默认 `enable_external_access=false`、目录/路径例外为空、禁止 autoload/autoinstall/运行时 grammar；OS 层不得可读宿主 workspace/凭据或访问网络。受信运行库/扩展是预置只读输入，不是用户可查询的数据源；若平台隔离做不到则不得接受任意用户 SQL。
3. **allowlist 而非 denylist 补丁**：所选 DuckDB + 扩展 hash 绑定已审核的关系、scalar/table function、重载、宏定义及依赖闭包 manifest。只允许单条无副作用查询；CTE/subquery/view 的叶关系必须解析到当前 run 的授权 artifact catalog。PG 状态表、其他 run schema、任意系统目录、文件/URL 路径、凭据和未批准 native 函数均不在可见闭集。显式拒绝 DDL/DML、ATTACH/COPY/INSTALL/LOAD/SET/PRAGMA/CALL、用户 CREATE MACRO/UDF 及有副作用的 SELECT 函数。
4. **绑定后校验**：使用所选版本可验证的解析/绑定结果，不用正则字符串匹配冒充安全分析。规范化 quoted/qualified 名称并解析到 catalog identity，递归检查宏/view 展开后的调用图；参数也受约束。`query/query_table` 等动态 SQL/关系名、glob/path 表函数及不能静态穷举到授权 artifact 的解析一律拒绝。默认不暴露 raw `read_ast` 或路径型 `ast_to_blocks`；内容/表输入宏只有完整调用闭包通过审查才可开放。不能检查某个 native/宏的间接 IO 就不允许执行。
5. **每次执行重新授权**：包括已准备 SQL、缓存 view、block_query、重试和恢复，逐个复核依赖 artifact 当前 read grant；撤销后禁止新执行/结果披露。validator/policy manifest 不可由用户会话修改；扩展/宏或环境身份变化使资格失效。仅固定函数名、官方签名、目录前缀或者 fork 源码示例都不等于所选 release 实测通过。
6. **fail-closed 资格**：P1/S2 必须在选定二进制、实际配置与进程隔离下用低层 fixture 证明内容入口、artifact 查询及 AUTH-Q 的 native/宏/动态解析负向；§3.5 的真实队列/撤销/角色集成在对应 S4/S6/S7/S9 重跑，不假定早期已有这些接口；无法证明 binder 闭包、native 文件/网络隔离或必要能力时 no-go，不降低为“只读 SQL 已校验”。宿主 mount 可供受控工具使用，但永远不扩大 query 会话权限。

| AUTH-Q / B004（P1/S2/S7/S9） | 合格内容 ingress→AST artifact→链式 view→授权 block_query/纯 render；行读模式无需目录例外；必需插件组合保留 | 直接/quoted/qualified native 文件函数、嵌套宏/view、动态关系/SQL、CTE 隐藏外部读取、网络入口、另一 workspace 即使在同一允许前缀内、撤销后的缓存查询均拒绝且不泄漏；未知 native/宏、变更 manifest 或检查失败拒绝 bootstrap/query |
| AUTH-M / B001/B004（D2-B 及产品 mount gate） | 合格 adapter 下授权精确对象读写，与 PG 身份一致 | symlink/hardlink、大小写/Unicode 碰撞、`../`、同前缀另一 workspace、根替换/检查后路径交换均被拒；adapter 证明不足保持模式关闭 |

enqueue/claim/read/mutate/apply 从权威台账取得 `request_id, operation_digest, principal_id, run_id, workspace_id, object_id/creation_target, canonical_path, action, grant_id, revocation_epoch`；§3.6–3.8 定义 `expected_version`、payload refs、receipt 与 `(attempt_epoch, attempt_token)`，不可用 NULL/临时值绕过。队列只是定位引用，grant 不是 CAS，UUID token 本身不是 fence，receipt 不是可重放 source 快照。B007 的 source/config/dependency manifest 与 B011 的完整 lifecycle/装载表仍待闭合；hydrate **绝不能重放文件 mutation**。以下合同只为 B005/B006/B010 提交候选修订，不改变最近独立判定。

## 5. 每阶段要点

### P1 · 探针（唯一 go/no-go）

以下是未来必须实测并留下原始输出的要求，当前均未运行；安装、挂载、写入与构建须另获操作批准。P1 分为 row-only 资格与产品 mount 资格：行读核心测试可不挂载，但不免除 P1 的 mount 生命周期检查；缺少环境/批准则产品 go/no-go 仍未通过，不得等到 S9 才首次处理。

1. **ABI 墙复现**：在 v6 fork 连接上尝试 `LOAD` 现成的社区 `sitting_duck.duckdb_extension`，记录真实错误串（预期命中 §2.5.1 的版本不匹配）。
2. **代码平面可用性**：建独立 uv 工程，pin 一个已发布版 duckdb，`INSTALL … FROM community` + `LOAD` 成功；打印 `duckdb_extensions()`、扩展版本、以及 `ast_supported_languages()` 的**实际**语言清单（**不采信 README 的 27/21**）。
3. **schema 实测**：`DESCRIBE`/`pragma_table_info` 记录 `parse_ast` 与 `read_ast` 的真实列集，与 `sitting_duck/src/unified_ast_backend.cpp:356-361` 的 19 列比对。
4. **确定性**：同一份 fixture 内容 → 两次 `parse_ast` → 逐行相等（`node_id` 稳定）——这是 artifact `definition_hash` 与重放的前提。
5. **tigerfs 生命周期**：mount → 写一个文件 → 从 PG 行复读 → unmount → **在 pgembed server 停止之前完成 unmount**；记录 macOS NFS 下 `tigerfs unmount` 的退出码与实际状态（可能非零退出但仍成功，需要状态复核 + `diskutil unmount force` 兜底）。
6. **映射形态**：确认工作区用 file-first 还是 data-first，记录物理 PK/parent/filename 到 §3.1 workspace/object/canonical_path 的唯一映射；逻辑身份不由物理路径主键决定。选定 release/扩展还必须通过 AUTH-Q；mount adapter 必须通过 AUTH-M，不能照搬 fork 机制假定通过。
7. **决策记录**：D1 取 A 还是 B；若是 A，钉死代码平面 duckdb 版本与扩展版本；若是 B，记录限时移植的实测结论。
8. **B 的限时尝试**：把 `sitting_duck` 的 duckdb submodule 指向 fork 源码后尝试构建，**时间盒**；结果仅作 D1 的输入。

### S1 · schema

- 镜像 `v6/source_ingress/duck_sources.sql` 的四张表，但**新表名、新库**，不触碰 v6。
- `codefs_artifacts.artifact_kind` 需含 `{'file','source','view'}`：`file` 引用 `(workspace_id, object_id)`，`source` 是解析产物，`view` 是命名只读结果；artifact/name 均受 run 作用域约束。
- `codefs_files`：`(workspace_id, object_id)` 复合主键，活动 `UNIQUE(workspace_id, canonical_path)`，另含 `content_hash, generation, byte_size, language, updated_at, tombstone`；不以 hash 跨对象/工作区合并身份。版本字节原子关系在 B005 补齐。
- 新增 workspace/run-membership/grant/operation-authorization 的逻辑记录与 §3.2 ACL、受限接口；DDL 具体 SQL 路径/装载切点随 B011 冻结，不把旧“四表/五文件”概述当作已完整设计。
- `codefs_operations.op_kind` 闭集 CHECK 必须先把 P1 定下的真实 op 集列全。

### S2 · 会话与扩展装载

- 复制 `v6/session_durability/duckdb_grammar.py:241-285` 的硬化次序，但**身份常量改为代码平面自己的**（一个 `CodefsExtensionConfig`，不复用 v6 的 `EXPECTED_*`）。
- 用户 query 会话必须为空目录例外且关闭 external access；D2-A ingress 亦无需文件例外。D2-B 只在隔离的可信 ingress 按所选 release 经验证的顺序配置，不能把 fork 设置顺序或前缀检查当作证明。
- 按 §3.2 分离 runtime logins 与 NOLOGIN owners：worker 禁止底表直写，但允许经受限命令完成必要状态转换，不再以“两连接”代替权限制约。AUTH-R 必须实测最小权限完整循环和所有直接 DML/伪造命令负向。
- AUTH-Q/M 资格未通过保持接口/模式关闭；可信解析进程不得与任意 SQL 会话共享凭据或开放文件通道。

### S3 · 摄入

- 注册工具输入是**路径 + workspace 选择器**，不是授权；服务端验证 auth_context/read/register grant 并解析为 §3.1 权威身份，台账绑定对象后入队。内容经受限 ingress 读取，注册内容**永不进 PGMQ**；write/patch 内容引用与保留策略仍由 B010 补齐。
- 解析产物落库：`parse_ast` 的结果要么物化为 run 作用域表，要么持久化为 `source` artifact——需在 S3 决定并固定（建议：物化为 `source` artifact，与 v6 的 `snapshot_table` 同语义）。
- 预算直接映射 `sitting_duck` 的命名参数，不另造一套。

### S4 · 队列

- overlay `refresh_plugins()`：`v_legal_kind` 追加 `codefs_heavy`；D4 决定是否启用写能力（如 `fs_mutation`），静态 capability 不替代 §3.3 动态授权。
- `apply_codefs_result` 参考 v6 的幂等短路、`last_completed_op_seq = v_op_seq - 1` 乱序门、drop 依赖二次复核与 resume；不得直接照抄其权限假设。claim/session/apply/resume/archive/DLQ 必须走 §3.2 的受限接口；文件写授权在 mutation 边界完成，不在 apply 时补救。
- 队列消息只用于定位台账，不信任其 principal/run/action/scope；AUTH-R/W 测试伪造与排队后撤销。文件幂等、attempt fencing、retry/terminal disposition 仍须 B006/B011 后续闭合。

### S5 / S6 · 工具族

`wb_code_*`（先镜像 v6 的 7 个，再加 AST 专属）：

```
wb_code_register(brief, workspace, path, artifact_name)      -- 文件 → AST source

wb_code_references(brief, view_name, name)                    -- ast_find_references
wb_code_source(brief, view_name, start_line, end_line)        -- ast_get_source
```

`wb_file_*`（文件工作台）：

```

wb_file_stat(brief, workspace, path)
wb_file_list(brief, workspace, prefix)
wb_file_write(brief, workspace, path, content)                -- 破坏性，见 §7 D4
```

- 所有工具保持 v6 的形状：`(p_brief, …) → jsonb`、`VOLATILE SECURITY INVOKER`、COMMENT 里带完整 `plugin`/`llm_tool` 元数据（`args` 键数必须与函数参数数相等，否则 `refresh_plugins()` 抛错——`v6/queue_bridge/duck_queue.sql:122-139`）。
- 所有入口遵守 §3.1–3.4；外部工具签名不暴露可伪造 principal/grant。破坏性工具除**前置依赖/存在性拦截**与明确 `Type` 外，必须经 default-deny operation authorization；read/render 也不能绕过 read grant。内部 request 字段不得因保持 named-tool 形状而省略。

### S7 · 提示词

- 新增 recipe 版本（v6 用的是 `agent_system` v3，见 `v6/dialect_guardrails/duck_prompt.sql:2`）⇒ v6.1 编译 **v4**，**不修改 v6 的 SQL 文件**。
- 两个新工具族必须**按能力与当前授权条件广告**：扩展未装载、workspace 未注册、当前动作无 grant 或 D4 未批准写时，相应工具不出现；广告不是安全检查，直接调用仍受 §3.2/3.3 限制。沿用 v6 对 grammar capability 的展示做法（`v6/session_durability/duckdb_grammar.py:182-189` 的 `prompt_text()` + worker 侧追加 system 消息）。
- 也可用 `prompt_slot`（`source='live'`）机制（`v5/prompt_pipeline/prompt_pipeline.sql:53-118`）作为补充挂点。

### S9 · 集成验收（必须包含）

1. tigerfs 里放一个 fixture 代码文件 → `wb_code_register` → `parse_ast` 命中定义 → 命名 view → 链式 view（复用 v6 `v6/integration/test_v6.py:42-55` 的形状）；
2. AST→blocks→`db_render_blocks` 渲染→显式授权的 `wb_file_write` 写回 tigerfs→**从 PG 行复读并逐字节校验**；这是必需组合能力，不授权直接调用路径型 `ast_to_blocks`；实际完整内容 API 链仍由 B009 冻结；
3. 依赖保护：删被依赖的 artifact 被 `DUCK_DEPENDENCY_EXISTS` 等价错误拦截；
4. 完整重跑 AUTH-I/R/W/Q；如选 D2-B 还跑 AUTH-M。跨 workspace 即使位于同一目录前缀也必须拒绝，query 不得拥有路径读取能力；
5. worker 崩溃/租约过期/乱序投递的恢复路径；
6. `v1`–`v6` 目录字节未变（`git status` 与基线 hash 比对）。
