## 5. 组件与接口

```text
Host.drive
  → Control.execute("start" | "steer" | "respond" | "claim_resume")
  → resolve_handle                         # 事务外；pending 则 drive 返回 wait
  → 这条 operation 还没有 admit_turn 时：admit_turn
  → 循环：
       未完成的工具：事务外 FakeTool，accept_tool_result
       未完成的 turn：事务外 FakeWorker，accept_turn_receipt
       回执有工具：进度 publish_snapshot，admit_tool，再进循环
       工具都完成：admit_turn（input_kind = host_continue），再进循环
       终态回执：publish_snapshot / record_provider_handle，然后返回
decide(snapshot) 只读已提交快照，返回 run_now | wait | needs_input | stop | failed
```

Worker 与 FakeTool 不接数据库，不拿到 DSN。Host 不直接插表。工具不改 run 状态。

### 5.1 Control

`v20/alpha/control.py`

```text
Control.execute(verb: str, actor: str, payload: dict) -> dict
```

返回已提交事实的 JSON 对象，至少含 `request_id`、`verb`、`status`、`run_id`、`session_id`、`revision`。冲突与拒绝抛 `ControlError`，带 `code`。未知动词在开事务之前拒绝。

设计五 `:347` 的锁顺序是 run、epoch、operation、artifact。alpha 在 run 之后、epoch 之前加一把 session 锁，因为 `steer` 要 CAS `sessions.revision`，`cleanup` 要写 session 的 `terminal`。`cancel` 不改 session 行，仍走同一顺序，以免和 `steer`、`cleanup` 交叉。不锁 artifact，因为没有这张表。不锁 workflow。

`attempt_seq` 在这把 run 锁里按该 session 已有最大值加一分配。

`depends_on_request_id`：同一 session 里、`attempt_seq` 更小、且 `expects_handle = true` 的最近一条，包含 `archived` 与 `closed`。没有则空。只在 `start` / `claim_resume` / `steer` / `respond` 的 T1 写入。`recover_owner` 把仍需恢复的 pending operation 改成 `archived` 并把还没有 attempt 行的 `handle_state` 设为 `absent` 之后，下一笔的 `depends_on_request_id` 仍可以指向这一行。`resolve_handle` 看到 `absent` 就不等待，改用更早一条 `present` 的句柄；没有更早的就返回空句柄。

事务外等句柄的函数 `resolve_handle(request_id)` 不打开事务。等待只发生在这个函数里：

- `depends_on_request_id` 为空：返回空句柄，立即启动。
- 那一行 `present`：返回 `v20_provider_handle_attempts.handle`。
- 那一行 `absent`：改用更早一条 `expects_handle = true` 且 `present` 的句柄；没有更早的就返回空句柄。不等待。
- 那一行 `pending`：在事务外等到 `wait` 同款超时（默认 2 秒，探针可传更短），然后重读。仍是 `pending` 则返回 `{state: "pending"}`。Host 拿到 `pending` 就返回 `wait`，不再等第二次。不在打开的事务里等，也不旋转等到永远。

NOTIFY 信道名 `v20_alpha_run_changed`。载荷只有 `run_id|revision`。收到之后按 `run_id` 重查，不把载荷当新事实。凡成功提交并且改变了 `v20_runs.revision` 的动词，提交之后尽力而为地发这条 NOTIFY。会改 revision 的动词：`start`（插入时 revision 为 1）、`steer`（CAS 成功则 `runs.revision` 与 `sessions.revision` 各加一）、`claim_resume`、`respond`、`cancel`（仅当 status 从 `running` 或 `waiting_for_input` 改成 `cancelled`）、`cleanup`（设计五 `:344`、`:365`）、`recover_owner`、`publish_snapshot`（进度与终态都加一）。`accept_turn_receipt`、`accept_tool_result`、`record_provider_handle`、`poll`、`wait` 不改 `v20_runs.revision`，不发 NOTIFY。`admit_turn` 与 `admit_tool` 也不改 run revision。

### 5.2 Worker

`v20/alpha/worker.py` 复刻 v23 的界限，不复刻 v23 的表。常量与 `v23/worker.py:12`–`:18` 相同：

- `MAX_TOOL_CALLS = 8`
- `MAX_TOOL_ITEM_BYTES = 4096`
- `MAX_TOOL_TOTAL_BYTES = 32768`
- `MAX_RESULT_BYTES = 65536`
- `MAX_TOOL_ERROR_BYTES = 512`
- `INPUT_KINDS = {initial, parent_instruction, host_continue, parent_response}`
- `OUTCOMES = {progress, needs_input, completed, failed}`
- `schema_version` 必须是 1
- `storage_safe_json` 拒绝 NUL、surrogate、超出 jsonb 数值范围的数、深度大于 128。行为对齐 `v23/worker.py:72` 一带，不把函数体贴进本计划。

alpha 的 `WorkerRequest` 在 v23 字段之外加两个可空字段，因为设计五的下一轮输入要看到它们，而 v23 单表没有这两列：

- `provider_handle`：`resolve_handle` 的结果；空句柄时为 `None`
- `tool_results`：本 epoch 已提交的工具结果列表，元素为 `{invocation_id, tool_name, output}`

这两个字段进入 `input_digest` 的规范 JSON。它们不是第二套 ABI 名称。`input_kind` 也进入这份 digest。

`FakeWorker` 是纯函数，由测试注入。默认脚本，用于纵向探针：

- 输入里没有 `tool_results`：`outcome = progress`，`tool_calls` 一项，`name = "echo"`，`arguments = {"text": <instruction>}`。
- 输入里有 `tool_results`：`outcome = completed`，`result = {"saw": <第一条 output.text>}`。
- 测试传入 `script = "needs_input"` 时：第一次 `outcome = needs_input`，没有工具；`input_kind = parent_response` 时 `outcome = completed`。
- 测试传入 `script = "bare_progress"` 时：每次都是 `progress`，没有工具。Host 的终止规则见第 5.4 节。

超过大小上限抛 `WorkerContractError`，不写库。

### 5.3 FakeTool

名称闭集只有 `echo`。请求是 JSON 对象 `{"text": string}`。结果是 `{"text": <同一字符串>}`。未知工具名、非对象参数、超过 `MAX_TOOL_ITEM_BYTES` 的参数，都在事务外失败，失败记录不超过 `MAX_TOOL_ERROR_BYTES`。失败仍走 `accept_tool_result`，`status = failed`，不改 run 状态。

不读文件系统，不启子进程，不打开套接字。

### 5.4 Host 与 decide

`decide(snapshot) -> str` 是纯函数。输入只有已提交快照：`run.status`、是否有未接受的工具准入、是否有未接受的 turn 准入、所等待的那条 operation 的 `handle_state`。未接受指该行 operation 仍是 `pending`。已经 `completed` 的 turn 不算。自己这条 `expects_handle` operation 的 `handle_state = pending` 也不算「句柄仍在等待」，也不算 turn 准入。优先级固定：

1. `completed` → `stop`
2. `failed` 或 `cancelled` → `failed`
3. `expired` → `failed`（Host 不自己 `claim_resume`）
4. `depends_on_request_id` 指向的那一行仍是 `handle_state = pending` → `wait`
5. 有未完成的工具准入，或有未完成的 turn 准入 → `run_now`。两者都有时先做工具。
6. `waiting_for_input` → `needs_input`
7. `running` 且没有未完成的 turn / tool 准入 → `wait`
8. 其余 → `failed`

`drive` 的循环直接看未完成的 turn 行和 tool 行。它不调用 `decide` 来决定下一笔 `admit_turn`。`decide` 给调用方读已提交快照。`drive` 的返回值与 `decide` 用同一组词。

`Host.drive(payload)` 只允许本进程一个线程进入。第二个调用者得到 `Rejected`。另一条数据库连接上的 `cancel` 或 `recover_owner` 允许进行。

1. 调用方动词是 `start`、`steer`、`respond` 或 `claim_resume` 时，先执行该动词的 T1。这一笔不插入 `v20_turns`。
2. `resolve_handle`。空句柄或 `present` / 回退后的句柄则继续。返回 `pending` 则 `drive` 返回 `wait`。此处不再等待。
3. 若这条 `expects_handle = true` 的 operation 仍 `pending`，且还没有对它做过 `admit_turn`：执行 `admit_turn`。`input_kind` 在这一笔 T1 就写定，规则见第 6.1 节。

然后重复下面的循环：

4. 有未完成的工具准入：对每个工具在事务外跑 FakeTool，再 `accept_tool_result`。工具失败不阻止同一回执里后面的工具结算。run 保持原 status。做完再从第 4 步看。没有未完成的工具就看第 5 步。
5. 没有未完成的工具，也没有未完成的 turn，且上一份回执含 `tool_calls`，续接的 `admit_turn` 还没做：执行这一笔，`input_kind = host_continue`，输入带上这些工具结果。再从第 4 步看。这一条不成立就看第 6 步。
6. 有未完成的 turn 准入：在事务外调 FakeWorker，再 `accept_turn_receipt`。结算的是这一行 turn 自己的 operation。响应 activity 写在这一笔 T2。`expects_handle` 的那条 operation 保持 `pending`。run 的 status、`interaction`、`failure_reason` 都不变。然后按这份回执进入第 7 到第 11 步之一。
7. 回执含 `tool_calls`：这条 operation 已经完成过一轮工具时，`publish_snapshot` 把 run 写成 `failed`，Host 返回 `failed`。否则，若 `snapshot_seq` 仍空，先对这条 operation 做进度 `publish_snapshot`（operation 仍 `pending`，run 仍 `running`，`handle_state` 不变，`runs.revision` 加一）。然后对每个工具 `admit_tool`。关联 turn 可以已经是 `completed`，只核对它的 `run_id` 与 `epoch_id`（设计五 `:335`）。回到第 4 步。默认脚本只有一轮工具。
8. 回执 `progress` 且没有工具：这条 operation 还没有过无工具进度时，做一次进度 `publish_snapshot`，再 `admit_turn` 一次。这一笔的 `input_kind` 与上一笔相同，instruction 相同，`tool_results` 仍空。回到第 4 步。已经有过无工具进度时，`publish_snapshot` 把 run 写成 `failed`，Host 返回 `failed`。默认脚本与 `needs_input` 脚本不会走到这里。
9. 回执 `needs_input`：`publish_snapshot` 把 run 设为 `waiting_for_input`，写上 `interaction`，把这条 `expects_handle` operation 标成 `completed`。Host 返回 `needs_input`。
10. 回执 `completed`：`publish_snapshot` 把 run 设为 `completed`，session 设为 `dormant`，`resumable` 保持 true。完成的是 `expects_handle` 那条 operation。Host 返回 `stop`。
11. 回执 `failed`：`publish_snapshot` 把 run 设为 `failed`，写 `failure_reason`。Host 返回 `failed`。

若这次 provider 调用要记句柄，在 `expects_handle` 的那条 operation 上 `record_provider_handle`。可以与第 9 到第 11 步的 `publish_snapshot` 分开两笔，也可以同一笔 T2。两种顺序都留下当前句柄（探针覆盖）。operation 已是 `completed` 时不改 `status` 与 `result`（设计五 `:333`、`:337`）。

`respond` 只在 `decide` 已经返回 `needs_input` 之后由调用方发起。Host 不自动编造用户回答。`respond` 的 T1 把 run 设回 `running` 并插入新的 `expects_handle` operation；控制 turn 仍由随后的 `admit_turn` 插入，`input_kind` 为 `parent_response`。

`drive` 进行中，另一条连接可以 `cancel` 或 `recover_owner` 并拿走 run 锁。回执返回后，`accept_turn_receipt` 或 `publish_snapshot` 得到 `FenceRejected`（归档事件已经写入）。Host 把这当作本次 `drive` 的正常结束：返回 `failed`，不重试，不把异常抛出 `drive`。run 保持 `cancelled` 或 `expired`，Host 不再发一笔终态快照。

## 6. 状态与数据流

### 6.1 纵向链

`input_kind` 在 `admit_turn` 的 T1 确定，写入该 turn 的 `receipt`，初值为 `{input_kind, instruction}`。`accept_turn_receipt` 用 TurnReceipt 替换这份 `receipt`。operation 的 `input_message` 仍是指令文本。载荷与下表不符则 `Rejected`，不插 operation，也不插 turn。

| 前一笔 | `input_kind` |
|---|---|
| `start`，session 没有 `parent_session_id` | `initial` |
| `start`，session 有 `parent_session_id` | `parent_instruction` |
| `claim_resume` 或 `steer` 之后的第一笔 `admit_turn` | `initial` |
| `respond` 之后的 `admit_turn` | `parent_response` |
| 工具结果之后的续接 `admit_turn` | `host_continue` |
| 无工具 `progress` 之后的再试 | 与上一笔相同 |

默认脚本的已提交顺序：

1. `start` T1：session `active`，`resumable = true`；profile；run `running`，`run_id = session_id`，`owner_backend_pid` 为这条控制连接的后端 pid，`owner_generation = 1`，`revision = 1`；epoch `initial`，ordinal 1，continuity 1；operation `pending`，`expects_handle = true`，`handle_state = pending`，`depends_on_request_id` 空，`input_message` 为用户文本，`input_retained = false`；一行 `v20_transcript_turns`；请求 activity；事件一行。不插入 `v20_turns`。提交。尽力 NOTIFY。
2. 事务外：`resolve_handle` 得到空句柄。
3. `admit_turn` T1：新 operation，`expects_handle = false`，`handle_state = absent`，无 `depends_on_request_id`。新的 `v20_turns`，`status = admitted`，`input_kind = initial`，`receipt` 为 `{input_kind, instruction}`，可以填第 1 步的 `transcript_turn_id`。请求 activity。不改 run revision。
4. 事务外 FakeWorker。回执是 `progress`，并要求 `echo`。控制连接为 `TRANSACTION_STATUS_IDLE`。
5. `accept_turn_receipt` T2，在任何 `admit_tool` 之前：这一行 turn 与它的 operation 变为 `completed`，响应 activity 写下，`receipt` 换成含 `tool_calls` 的 TurnReceipt。start 的 operation 仍 `pending`。run 仍 `running`。
6. `publish_snapshot` 进度，作用在 start 的 operation 上：`snapshot_seq = 1`，预览更新，该 operation 仍 `pending`，run 仍 `running`，不改 `handle_state`。`runs.revision` 加一。提交后 NOTIFY。
7. `admit_tool` T1：新 operation，`expects_handle = false`，`handle_state = absent`，无 `depends_on_request_id`。核对第 3 步那个 turn 的 `run_id` 与 `epoch_id`。该 turn 此时已经 `completed`。
8. 事务外跑 `echo`。
9. `accept_tool_result` T2：invocation 与它的 operation 变为 `completed`。run 仍是 `running`。`interaction` 不变。不改 run revision。
10. `admit_turn` T1：新 operation，新控制 turn，`input_kind = host_continue`，输入含工具结果。可以填同一个 `transcript_turn_id`。
11. 事务外 FakeWorker 看到 `tool_results`，返回 `completed`。
12. `accept_turn_receipt` T2：这一行续接 turn 与它的 operation 完成。不改 run。start 的 operation 仍 `pending`。
13. `publish_snapshot` 最终，作用在 start 的 operation 上：该 operation 变为 `completed`，run `completed`，session `dormant`，`resumable` 仍为 true。若结果明确没有句柄且没有 attempt 行，同一事务把该 operation 的 `handle_state` 设为 `absent`。`runs.revision` 加一。提交后 NOTIFY。
14. `wait` 读到 `completed` 与新 revision。

实验对照，只说明顺序，不把实验源码当合同：`scenario.py:623`–`:675` 是 `admit_turn`，然后 `accept_turn_receipt`，然后 `admit_tool`。`control.py:1889`–`:1944` 在 accept 时把 turn 标成 `completed`。`control.py:2073`–`:2134` 只核对 turn 的 `run_id` 与 `epoch_id`。`control.py:1354`–`:1420` 的 `start` 插入 transcript turn 与 pending operation，不插入 `v20_turns`。`INSERT INTO v20_turns` 在 `control.py:2036`。

### 6.2 恢复

活着的判定是一条 SQL，由 `v20_alpha_control` 在自己的连接上执行：

```sql
SELECT pid FROM pg_stat_activity WHERE pid = %s
```

`%s` 是 `v20_runs.owner_backend_pid`。查到一行则 pid 仍活，查不到则已死。`setup_db` 把 `pg_read_all_stats` 授给 `v20_alpha_control`。W0 的 `control_role_sees_other_backend_pid` 用这个角色看另一条连接的 backend pid，必须能看到。Host 在整个 `drive` 期间保持写出该 pid 的那条控制连接打开。

`recover_owner`：上面的查询查不到旧 pid，且 run 仍是 `running` 或 `waiting_for_input`。同一事务：`owner_generation` 加一，`registration_generation` 加一，不写新 pid；run `expired`，`runs.revision` 加一，session `interrupted`，`resumable` 保持 true，当前 epoch 写 `closed_at`，仍需恢复的 `pending` operation 改为 `archived`（不是 `closed`），`input_retained` 保持 false（alpha 没有 digest 可保），还没有 attempt 行且 `handle_state = pending` 的改为 `absent`。提交后 NOTIFY。

pid 仍活则 `AlreadyActive`，不写库。run 已经是 `expired` 且 pid 已死：返回当前快照，不再抬 generation，不发 NOTIFY。

`claim_resume` 的正向闭集：`resumable = true`，session 不是 cleanup 留下的 `terminal`，并且 run status 属于 `expired`、`completed`、`failed`、`cancelled`。通过时 session id 与 run id 不变，ordinal 加一，run 回到 `running`，`runs.revision` 加一，新 operation 仍 `expects_handle = true`。`depends_on_request_id` 按第 5.1 节计算，可以指向刚刚被标成 `archived` 的那一行。不插 workflow step。`related_follow_up` 不加 `continuity_generation`。`unrelated` 才加一。控制 turn 由随后的 `admit_turn` 插入。

- `expired` 来自 `recover_owner`（设计五 `:330`、`:343`）。
- `completed` 可以在同一个 Control 进程还活着时恢复（设计五 `:479`、`:535`）。探针 `claim_resume_keeps_ids_and_advances_epoch` 从 `completed` 出发。
- `failed` 与 `cancelled` 用同一谓词。`cancel` 不改 `resumable`（设计五 `:349`）。设计五点名的 cancel 之后路径是 `steer`（`:480`、`:535`）。`claim_resume` 在 `cancelled` 上同样满足这一闭集。
- `resumable` 不为 true，或 session 是 `terminal` 且 `resumable = false`：`Rejected`，不新建 epoch，不插 operation。
- run 仍是 `running` 或 `waiting_for_input` 且 pid 仍活：`AlreadyActive`。
- run 仍是 `running` 或 `waiting_for_input` 且 pid 已死：`Rejected`，不新建 epoch。先 `recover_owner` 写成 `expired`，再 `claim_resume`。这是 D9。设计五 `:349` 写明 `claim_resume` 使用 `recover_owner` 已经抬高的 `owner_generation`，自己不另抬。

两个连接同时 `claim_resume`：一个提交并写上自己的 pid，另一个 `AlreadyActive`，不新建 epoch。

### 6.3 取消、清理、转向

- `cancel` 先锁 run，并按第 5.1 节锁 session。只有 `running` 或 `waiting_for_input` 改为 `cancelled`，`runs.revision` 加一，关闭当前 epoch，该 epoch 上 `pending` operation 改为 `closed`，没有 attempt 行的 `handle_state` 改为 `absent`。提交后 NOTIFY。不改 `owner_generation`，不改 `resumable`，不把 session 设为 `terminal`。已经是 `completed` / `failed` / `expired` / `cancelled` 则不改 status，不推进 revision，不发 NOTIFY，返回当前行。
- 完成 T2 先提交，随后的 `cancel` 不改 `completed`。`cancel` 先提交，随后的 T2 只追加归档事件，operation 保持 `closed`，run 保持 `cancelled`，然后抛 `FenceRejected`。
- `cancel` 先提交，随后的 `admit_turn` / `admit_tool` 被拒绝，不插 pending，不到事务外执行。
- `drive` 正在事务外跑 FakeWorker 时，另一条连接的 `cancel` 可以提交。回执回来后的 `accept_turn_receipt` 走上一行的归档路径。Host 的处理见第 5.4 节。本进程里第二个 `drive` 仍是 `Rejected`。
- 运行中 `steer`：CAS `runs.revision` 与 `sessions.revision`。失败为 `RevisionConflict`，不插 epoch。成功则两列 revision 各加一，关闭旧 epoch，旧 pending 改 `closed`，新 epoch，新 pending operation（`expects_handle = true`），run 仍为 `running`，清掉 `interaction` 与 `failure_reason`，两个 id 不变。提交后 NOTIFY。旧尝试的迟到 T2 只归档。控制 turn 由随后的 `admit_turn` 插入。终态（`completed`、`failed`、`cancelled`、`expired`）上的 `steer` 用新 `request_id` 开新 epoch，把 run 设回 `running`。`cancel` 之后要发布新结果，走这条 `steer`（设计五 `:480`）。
- `cleanup`：session `terminal`，`resumable = false`，可选 `list_hidden`。关闭当前 epoch，pending 改 `closed`。run 若仍在跑，改为 `cancelled` 并推进 revision，提交后 NOTIFY。事件行与 transcript 行不删除。此后 `claim_resume` 与 `steer` 都 `Rejected`。session 已经是这个终态时再调用：返回当前快照，不写第二遍，不发 NOTIFY。
- 子 session：`start` 可带 `parent_session_id`。父必须已存在，否则 `Rejected`。子的 `session_id` 是新的，子的 `run_id` 等于子的 `session_id`。不实现 spawn 动词，不级联取消。第一笔 `admit_turn` 的 `input_kind` 为 `parent_instruction`。

### 6.4 重放

幂等重放只覆盖插入了 operation 的六个准入动词。同一 `request_id` 再次提交：若 `verb` 与 `payload_digest` 都相同，返回已提交行，不写库。`payload_digest` 是准入载荷的 SHA-256（键排序、无多余空白的 JSON），`admit_turn` 的载荷含 `input_kind`。digest 不同则 `IdempotencyConflict`。已完成的 T2 再交一次，且 owner 与 epoch 仍匹配、回执对得上，原样返回 `result`，不改成 `archived`。

`cancel`、`cleanup`、`recover_owner` 不存自己的 `request_id`。可观察结果已经是该动词的终态时，返回当前快照，不写第二遍，也不插 `IdempotencyConflict` 行。`cancel` 的这一条就是设计五 `:345`。

旧 owner 或旧 epoch 的迟到 `publish_snapshot` / `accept_turn_receipt` / `accept_tool_result`：只追加归档事件。当时仍是 `pending` 才把那一行改为 `archived`。已经 `closed` 的不改成 `archived`。当前 run 快照不变。然后抛 `FenceRejected`。

### 6.5 wait

独立连接：先 `LISTEN v20_alpha_run_changed` 并提交，再读权威 revision，然后进入等待。等待期间这条连接没有打开的事务。主连接在调用 `wait` 时也是空闲。监听建立之前已经提交的更新，由这次权威读看见。通知丢失后，超时重查仍看见新 revision。默认超时 2 秒。

## 7. 错误

`ControlError.code` 闭集：

| code | 何时 | 是否写库 |
|---|---|---|
| `UnknownVerb` | 不在第 4.3 节的收进列表 | 否 |
| `Rejected` | 状态不允许、epoch 不匹配、缺输入、`input_kind` 与第 6.1 节不符、带了 artifact digest、父 session 不存在、cleanup 之后再 resume、pid 已死却对仍在 `running` 的 run 做 `claim_resume` | 否 |
| `RevisionConflict` | `expected_revision` 与当前 `runs.revision` 或 `sessions.revision` 不符 | 否 |
| `FenceRejected` | T2 的 owner generation 或 epoch 不是当前值，或 epoch 已关闭 | 只追加归档事件；若当时仍 `pending` 则该行改 `archived`。写完后抛出 |
| `AlreadyActive` | 活 owner 上的 `claim_resume`，或活 pid 上的 `recover_owner` | 否 |
| `IdempotencyConflict` | 同一 `request_id`，digest 或 verb 不同。只用于六个准入动词 | 否 |
| `WorkerContractError` | DTO 越界 | 否；还没有 T2 |

不使用 v13 的 `progressed|waiting|terminal|stale` 作为公开出口词。不使用 `CitationError`：alpha 没有 cite。

事务内如果调到了模型或文件读写，探针必须失败。实现上，`FakeWorker` 与 `echo` 在进入前断言 `Control.in_transaction()` 为假；为真则抛错，测试把这一抛错当成探针失败。

## 8. 边界

- 空 `input_message` 的 `start` 为 `Rejected`。
- `respond` 只接受 run 状态 `waiting_for_input`。其余状态 `Rejected`，不插 operation。
- 同一 epoch 两个 pending 工具：交叉回执只归档，两条仍 `pending`；各自正确的回执都能 `completed`。任何一条都不把 run 改成 `completed`。
- 更小的 `snapshot_seq` 不覆盖已发布预览。同一 `snapshot_seq` 重试不另写一份。
- 更小 `attempt_seq` 的迟到句柄写入 attempt 行，不覆盖 `v20_session_provider_handles` 的当前行。旧 epoch 的迟到句柄同样只写 attempt，不更新当前行。
- `record_provider_handle` 不另开 operation。operation 已 `completed` 时不改 `status` 与 `result`。
- `cleanup` 不减少事件行数，不删 transcript。`list_hidden = true` 的 session 不出现在默认列表读取里；alpha 的列表读取是一条 SQL，由 gate 直接查，不新增动词。
- 不实现配额、注意力、队列、pgmq、SKIP LOCKED 租约。工具没有第二个写者。
- 无工具 `progress` 在同一条 `expects_handle` operation 上只发布一次预览，并再 `admit_turn` 一次。第二次仍是无工具 `progress` 时，run 变为 `failed`。

## 10. 工作顺序

前一包的探针没绿，不写下一包的行为（设计五 `:533`）。它们仍然是一次提交（章程 `:996`，`AGENTS.md:16`）。

1. **W0** schema、角色、`setup_db`、`pg_read_all_stats`。证明：库可建，`run_id = session_id` 的 CHECK 存在，worker 角色不能登录，控制角色能看见其他后端 pid，没有 workflow 表。
2. **W1** `start`、`poll`、`steer` 的 CAS、`cancel`、`cleanup`、重放。还不调 Worker。`start` 不插入 `v20_turns`。
3. **W2** 第一个控制 turn 由 `admit_turn` 插入，`accept_turn_receipt` 在 `admit_tool` 之前，`publish_snapshot` 的进度与终态作用在 `expects_handle` 的 operation 上。FakeWorker 可以先不要工具，直接 `completed`。
4. **W3** `admit_tool` / `accept_tool_result` / `echo` / 下一轮看到工具结果。关联 turn 此时已经 `completed`。
5. **W4** `decide`、`Host.drive`、`wait`、`recover_owner`、`claim_resume`、`respond`。`claim_resume` 使用第 6.2 节的闭集。
6. **W5** `record_provider_handle` 与 `resolve_handle` 的四态。`depends_on_request_id` 计入 `archived` 与 `closed`。transcript 两行控制回执指向一个对话回合。
7. **W6** 把第 11 节探针收齐，写 README、覆盖矩阵、偏差台账。整个 gate 退出码 0。
