## 4. 冻结合同 C17–C23

### C17 `model_call` request envelope

**冻结形状**（`effects.request`，kind=`model_call`；所有 key 必须出现，除注明「仅某 cause」外）：

```json
{
  "v": 1,
  "cause": "start | steer | respond | continuation",
  "run_id": "<uuid>",
  "epoch_no": 1,
  "generation": 1,
  "input": {},
  "reserve": {"tokens": 0},
  "digests": {"policy": "<hex64>", "schema": "<hex64>", "toolset": "<hex64>"},
  "budget": {},                       // 仅 cause=start：start payload 的 budget 原样快照
  "instruction": "…",                 // 仅 cause=steer
  "response": {},                     // 仅 cause=respond
  "origin_effect_id": "<uuid>",       // 仅 cause=respond
  "batch_digest": "<hex64>",          // 仅 cause=continuation
  "state": {}                         // 仅 cause=continuation；canonical JSON ≤ 64 KiB
}
```

- `reserve.tokens` 是**准入时已从 `remaining_tokens` 预扣**的额度（F3=A，C23）：准入公式 `reserve = LEAST(remaining_tokens, 4096)`，`remaining_tokens IS NULL` 时 `reserve=0`（无上限）；`remaining_tokens=0` 时 `reserve=0` 但表示**已耗尽**，只有 start 的首个 model 例外（见下条 [S4-addendum]）。结算时按实际 usage 退差。
- **[S4-addendum] reserve 语义修正（W1）**：`remaining_tokens IS NULL` = **无上限**；`remaining_tokens = 0` = **已耗尽**（不是无上限）。`model_reserve` 对两者都返回 0，但只有 NULL 允许后续 model 准入；0 时 steer/respond MUST NOT 建 `reserve=0` 的 model（见 C23 addendum B）。start 仍按 C23 在 tokens=0 时准入首个 model，因此 0-token run 只允许一个 turn。
- `digests` 见 §5.1 `v24.model_digests`；同一 run 的所有 model_call 三者必须逐字节相同。**并且**结算必须从 run input、live run pins、`chat_tool_v1` 常量**独立重算** `v24.model_digests(run_id)` 并要求与 `request.digests` 全等（F1 裁决：防止「一致但错误」）。
- `state` 是 reducer 的持久 JSON（设计 §5.4「不能持 JS continuation」），上限 64 KiB（canonical text 字节数），超限 `invalid_outcome`。

**生产者迁移（无语义变化）**：

| 生产者 | 现状 request（行号） | S4 request | 语义差异 |
|---|---|---|---|
| start | `{run_id,epoch_no,generation,input,budget}`（40:1453-1456） | 原 5 key **全部保留**，追加 `v/cause="start"/reserve/digests` | 无。`budget` 继续是 start payload 快照，唯一读者是测试与审计 |
| steer | `{run_id,epoch_no,generation,input,instruction}`（40:1235-1242） | 原 5 key 保留，追加 `v/cause="steer"/reserve/digests` | 无。`input` 仍是 prior input，`instruction` 原样 |
| respond | `{run_id,epoch_no,generation,response,origin_effect_id}`（40:1309-1314） | 原 5 key 保留，追加 `v/cause="respond"/reserve/digests` | 无 |
| continuation | 不存在 | 新 cause | 新增，不影响旧生产者 |

迁移是**纯追加**：settlement 与 applier 的严格相等校验改为「旧 key 全等 + 新 key 全等」，不是放宽。旧行兼容规则（只用于同库升级窗口，gate 每次建新库）：

```
v24.model_cause(p_request jsonb) RETURNS text
  = coalesce(p_request->>'cause',
             CASE WHEN p_request ? 'instruction' THEN 'steer'
                  WHEN p_request ? 'response'    THEN 'respond'
                  ELSE 'start' END)
```
`v` 缺失视为 0；`digests`/`reserve` 缺失只影响新结算路径（旧行的 settlement 由 S3 之后的 S4 首次 settlement 处理，此时 run 仍 running，按 `cause` 分支即可）。

**禁止**：调用者自报 `cause` 与 effect 来源不符；applier 必须校验 `cause` 与该 effect 的父 effect / 命令种类一致（start→父 command_start，steer→父 command_steer，respond→父 command_respond，continuation→父 tool_call）。

**过期 lease 规则（D-S4-1）**：对 `model_call`/`tool_call`，若 `status='claimed'` 且 `lease_until <= now()`，claim 返回 W0 `stale_claim`，**不**做第二次 attempt（不递增 attempt/fence）。`host_prepare`/`host_release` 保持现状（过期可 re-claim），因此 G1 的 reclaim 断言不受影响。理由：`no_replay` 的第二次执行会重复计费；reclaim 属 S6 的 inspect/recovery 范围。`deferred` 仍用于租约有效期内。

打开后的完整 claim 判定（五个条件按序）：
1. `kind` 在阶段 allowlist 内，且 `status NOT IN ('succeeded','failed','unknown','cancelled')` → 否则 `invalid_args`；
2. **执行前结构闸门**（Oracle 补丁 3）：`model_call`/`tool_call` 的冻结 `request` 必须通过 C17/C20 的完整结构校验（key 闭集、`cause` 与父 effect 一致、确定性 id、run/epoch/generation 匹配、`pin_id` 绑定、`state` ≤64 KiB）；不通过 → `invalid_args`（W0，零写），**绝不把结构非法的 request 交给 host 执行**；
3. `status='claimed' AND lease_until > now()` → `deferred`（零写）；
4. `status='claimed' AND lease_until <= now()` 且 kind ∈ `('model_call','tool_call')` → `stale_claim`（零写）；
5. 否则 → `claimed`，`attempt_no+1`、`fence+1`、`claim_owner=session_user`、`lease_until=now()+lease_ms`，返回 token。

**结构类 W0 的重交与解锁（Oracle 风险 2，冻结）**：
- 结构类拒绝不写任何行：`attempt/fence/lease_until/remaining_*/turn_no` 全部不变，因此同一 receipt 重交不消耗预算、不推进 turn、不产生第二次外部执行（host 已执行一次，重交只是重新提交同一结果）。
- 重交窗口由既有 lease 界定：租约内 host 可用同一 token 重交（含改正后的同一 effect outcome）；租约过期后 claim 返回 `stale_claim`，但**合法 token 的 settlement 仍被接受**（30:273-278 只比对 attempt/fence/owner，不比 lease）。
- S4 内的唯一解锁路径：host 对该 effect 提交 `class='unknown'`（同一 token）→ effect=unknown、run=`blocked_unknown`、pin 保留，run 离开 claimed 悬挂态。S6 的 inspect/recovery 是另一条路径；S4 不新建计数表、不做半写入退避计数。
- **已知限制（D-S4-7）**：若 host 在租约过期后再也不提交任何结局，effect 永久 claimed 且 run 无法 terminal；这是 S4 有意留给 S6 的恢复面，矩阵 §4 标注「S4 不承诺自动 reclaim」。

### C19 settlement matrix

**输入 receipt**（三种 class 共用）：

```json
{"v":1, "class":"success|failure|unknown", "claim":{"attempt":N,"fence":N,"owner":"…"},
 "body":{"kind":"model_call|tool_call", "result":{…}}}
```
- `body.kind` 必须等于 DB 中的 `effects.kind`。
- `receipt_key` 可省略，且不参与 digest 比对（30:262 既有规则，保持）。

**C19.0 两类拒绝（F2=D 裁决，冻结）**

| 类 | 判据（全部先于任何 DML） | 写类 | effect 后态 | 重交 |
|---|---|---|---|---|
| **结构类** | envelope/body 形状；key 闭集；类型；result schema（含 tool 输出对 descriptor schema 不符）；互斥（`tool_calls`×`final`、`interaction`×`tool_calls`）；`tool_calls > 16`；ordinal/确定性 id 公式不符；重复 continuation id；`state > 64 KiB`；`turn_no/revision` 算术不符；`usage` 形状错误 | **W0 零写**，`invalid_outcome` | `claimed` 不变；`attempt/fence/lease_until` 不变；无 outcome、无事件 | 同一 token 可重交到租约结束；不消耗预算、不推进 turn |
| **语义类** | host 已执行且回执证明结果不可信：**(a)** model 的 `tool_calls[].key` ∉ live run pins（模型请求了未被 pin 的能力，无法绑定 `pin_id`）；**(b)** `reserve.tokens > 0 AND usage.tokens > reserve.tokens`（provider 突破声明上限） | **结算**（不是错误返回） | `unknown` + **原始 outcome 作首次 receipt** + `resource_quiesced_at=NULL` | 否，终态；同 digest 重交得 `replay`，异 digest 得 `receipt_conflict` |

结构类的「执行前闸门」已在 claim 完成（C18 条件 2），因此结构类 W0 发生时 host 至多执行过一次，重交不会触发第二次外部执行。语义类保留原始 receipt 是 B.4 的硬约束：`status='unknown'` 与 `outcome.class='success'` 并存合法（`c_effects_outcome` 只要求 outcome 非空，10:102）；审计读到的是「回执说成功，但被判定不可信」，而不是伪造一个 failed receipt。

**model result**：

```json
{"text": "…|null",
 "tool_calls": [{"key":"…","args":{}}],        // 0..16
 "interaction": {"schema_digest":"<hex>","prompt_digest":"<hex>","payload":{}} | null,
 "final": {"text":"…"} | null,
 "usage": {"tokens": 0, "wall_ms": 0} | null}
```
互斥：`tool_calls` 非空 ⇒ `final` 必须 null；`interaction` 非空 ⇒ `tool_calls` 必须空；`text` 可与任一者共存。

**tool result**：

```json
{"status":"ok|error", "output":{}, "usage":{"wall_ms":0}|null}
```
class=success ⇔ `status='ok'`；class=failure ⇔ `status='error'`；不一致属结构类。

**矩阵**（每格 = 一次 advance 的全部写入；「零写」= 该校验失败时十表逐字节不变）：

| 维度 | model × success（结构合法且无语义违约） | model × failure | model × unknown |
|---|---|---|---|
| effect | `succeeded`，`outcome=receipt`，`settled_at`，`claim_owner/lease_until=NULL`，`resource_quiesced_at=now()` | `failed`，同左 | `unknown`，`resource_quiesced_at=NULL` |
| run turn | `turn_no+1` | `turn_no+1` | `turn_no+1` |
| run 预算 | tokens 退 `reserve−actual`；wall−elapsed；steps/tool_calls 已在 admission 扣 | tokens 退 `reserve−coalesce(actual,0)`；wall−elapsed | tokens **不退**（uncertain）；wall−elapsed |
| run 状态 | waiting（有 interaction）／running／`completed`（final 或 budget） | `failed`（`close_intent.kind='abort'`） | `blocked_unknown` + `close_intent{kind:'unknown'}` |
| interaction | 有则写 `runs.interaction`（C19.1）；否则 NULL | 强制 NULL | 强制 NULL；清 `pending_steer` |
| successors | final→0；interaction→0；tool_calls→N；普通续链→1 continuation | 0 | 0 |
| pin 释放 | 仅当本次使 run terminal（C22） | 同左 | 该 effect 的 `pin_id` 因 unknown 未静默而保留；同 run 其余 pin 按 C22 释放 |
| receipt | 只写 `effects.outcome`；**不写 `requests`** | 同左 | 同左 |
| 事件 | `model_call_settled`（+`interaction_created`/`tool_batch_admitted`/`pending_steer_consumed`/`run_completed`/`budget_exhausted`） | `model_call_failed` + `run_failed` | `model_call_unknown` + `run_blocked_unknown` |

| 维度 | tool × success | tool × failure | tool × unknown |
|---|---|---|---|
| effect | 同 model success | 同 model failure | 同 model unknown |
| run turn | `turn_no+1` | `turn_no+1` | `turn_no+1` |
| run 预算 | wall−elapsed（steps 在 model admission、tool_calls 在 batch admission 已扣） | 同左 | 同左；tokens 不动 |
| run 状态 | running（不因单工具失败而 failed） | running | `blocked_unknown` |
| successors | 批次闭合观察者生成 1 continuation（C20）；否则 0 | 同左 | 0 |
| pin 释放 | 仅 run terminal 时（正常不会） | 同左 | 该 pin 保留，其余按 C22 |
| 事件 | `tool_call_settled`（+`tool_batch_completed`/`run_completed`/`budget_exhausted`） | `tool_call_failed` | `tool_call_unknown` + `run_blocked_unknown` |

| 维度 | 语义类（仅 model，tool 无此分支） |
|---|---|
| effect | `unknown`；`outcome=p_outcome`（class=success）原样；`resource_quiesced_at=NULL` |
| run | `turn_no+1`；tokens 不退；wall−elapsed；`blocked_unknown` + `close_intent{kind:'unknown',reason:'semantic_violation'}`；`pending_steer=NULL`；`interaction=NULL` |
| 事件 | `model_call_unknown`（payload 含 `reason/code/effect_id`）+ `run_blocked_unknown` |
| pin | 保留（effect 未静默） |

**`failed` 的唯一生产者**：`close_intent.kind='abort'`（provider 失败或显式 abort）。结构 invalid 保持 claimed、不进 `failed`；已执行后的语义 invalid 一律 `blocked_unknown`。这与 Oracle「S4 范围内 failed 实际仅由 abort 产生」一致。

**`turn_no` 语义（Oracle 风险 3，冻结）**：`turn_no` 只在**已提交的 business settlement**（success/failure/unknown，含语义类）时 `+1`；admission 不 `+1`；结构类 W0 不 `+1`；重交不 `+1`。`turn_no` **不得**用于续链、批次或审计排序（排序用 `(created_at, effect_id)`；批次身份用 ordinal），`result.turn_no` 只是终值快照。

**C19.1 interaction 对象**（`runs.interaction`，冻结）：

```json
{"interaction_id":"<model effect id>", "origin_effect_id":"<model effect id>",
 "generation": <settle 时 run.driving_generation>,
 "schema_digest":"<hex>", "prompt_digest":"<hex>", "created_at":"<timestamptz>"}
```
`interaction_id = origin_effect_id = source model effect_id`。一个 model outcome 至多一个 interaction（S3 respond 只读 `interaction_id` 与 `origin_effect_id`，见 40:1288-1295，兼容）。

**零写失败原子性**：所有结构校验必须在第一条 DML 之前完成；任一失败 `RETURN v24.error_v1('invalid_outcome')` 或 `{write:false,error}`，调用方事务不提交，十表 `state()` 与调用前逐字节相等。SQL 层未预期的约束/触发器错误按 30:512 的既有规则整事务回滚（不是协议错误）。

**不写 `requests`**：settlement 不是 command，没有 request_key。矩阵 I7 已指出这一限制；S4 不新建 receipt 表。语义类用 `effects.outcome` 承载首次 receipt，因此不需要 request 行。

### C20 批次屏障

- **上界**：一个 model effect 的后继最多 16 条 tool effect（`c_effects_ordinal` 0..15，10:101）；`validate_and_apply_loop_delta` 预检 `jsonb_array_length(successors) <= 16`，超限整份 `invalid_outcome`，不截断。
- **身份**（F5=A + Oracle 的 max-ordinal 修正）：
  - tool effect_id = `md5(model_effect_id::text || ':tool_call:' || ordinal)::uuid`（与既有 `md5(p_effect_id||':model_call:0')` 同风格，40:279/1158/1256）。
  - continuation effect_id = `md5(model_effect_id::text || ':continuation')::uuid`。
  - `(parent_effect_id, ordinal)`：tool 的 parent = model effect；continuation 的 parent = **该批次的 max-ordinal tool effect**（`max_ordinal = max(ordinal)`，`parent = tool_effect_id(model, max_ordinal)`），ordinal=0。`u_effects_successor`（10:108）与 applier 的 duplicate-ordinal 预检（40:246-250）共同保证唯一。
  - **创建者与身份解耦**：写 continuation 的事务 = 结算后观测到「同 `parent_effect_id`（=model）下再无 `ready|claimed` sibling」的那个 settlement（G 串行 ⇒ 恰好一个）；但写入的 `parent_effect_id` 恒为 max-ordinal tool，**不取决于墙钟结算顺序**。若 max-ordinal tool 先结算，后结算的某个 sibling 成为创建者，仍把 parent 指向 max-ordinal tool。
- **batch_digest** = `encode(sha256(convert_to(string_agg(tool_effect_id::text, ',' ORDER BY ordinal),'UTF8')),'hex')`；写入 batch 内每条 tool request 与 continuation request，便于审计与断言。
- **唯一 continuation 判定**（tool settlement 内，顺序固定）：
  1. 若存在同 `parent_effect_id`（model）、`effect_id <> p_effect_id`、`status IN ('ready','claimed')` 的 sibling → 批次未闭合，0 successor；
  2. 否则本 settlement 是闭合观察者 → 若 `continuation_effect_id(model)` 已存在 → `invalid_outcome`（零写）；
  3. 若 run 已 terminal 或 `e.generation <> run.driving_generation` → 0 successor（late，C21）；
  4. 若已存在同 run 的 `ready|claimed` model_call → `invalid_outcome`（**[W2.1]** 防御性预检；`u_effects_model_call` 保证公共 API 下不可达）；
  5. 否则生成 1 条 continuation，`parent_effect_id = tool_effect_id(model, max_ordinal)`（**不是** p_effect_id，除非 p_effect_id 恰为 max-ordinal）。
- **partial unique 兜底**：`u_effects_model_call(run_id) WHERE kind='model_call' AND status IN ('ready','claimed')`（10:110-111）**不改定义**。它保证同 run 同时最多一个在途 model_call；**[W2.1]** 第 4 步不是可达的干净错误，索引才是实际网（直接撞索引会 23505 回滚，不可作为协议路径）。
- **并行 claim**：同批两个不同 tool 可各自 claim 成功（G 串行但都拿 token，`attempt_no` 各自 +1）；对**同一个** tool 的两个并发 claim，一个拿 token、另一个在同租约内得 `deferred`，`attempt_no` 仍为 1；settle 后再 claim → `invalid_args`。
- **continuation 的预算**：steps 在该 continuation **准入时** −1（C23），因此生成前检查 `run.remaining_steps > 0`；不足则写 `close_intent{kind:'budget'}` 并 seal（completed），不建 continuation。

### C20.1 [S4-addendum] W1 plain-text continuation staging

W1 没有 tool settlement，因此 G2b-A 在 W1 是 **model-only** 脊柱：`start → claim model → settle 非 final 纯文本 → 恰好一条 continuation → claim → settle final → completed`。对**无 `tool_calls` 且无 `final`** 的 model settlement：

- continuation 的 `parent_effect_id` = **settling model effect**（不是 tool），`ordinal=0`；
- `effect_id = v24.continuation_effect_id(model)`（`md5(parent::text || ':continuation')::uuid`）；
- `request.batch_digest = sha256('')`（空批次：`encode(sha256(convert_to('','UTF8')),'hex')`）；
- `request.state = {}`；`request.input` = settling model 的 `input`；`reserve/digests` 按 C17/C23 计算。

C20 正文的「continuation parent = 批次 max-ordinal tool」**只适用于 tool-batch closure**；W1 的 model-only 续链不得套用该规则（否则 parent 不存在）。W2 起两种形态共存：model settlement 直接续链用 settling model 作 parent，tool batch 闭合用 max-ordinal tool 作 parent。

### C21 `pending_steer` 消费

- steer 现状（40:1208-1228）：任一 claimed business effect ⇒ 写 `pending_steer={instruction,generation,epoch}` 且 0 successor；否则立即建 model_call。S4 不改这一写入面，只补**消费面**。
- **可消费条件**（在 model/tool settlement 的解释器内计算，全部满足）：
  1. `run.pending_steer IS NOT NULL`；
  2. 本次结算的 effect 属于**旧代**：`e.epoch_no < run.epoch_no OR e.generation < run.driving_generation`；
  3. 结算后不存在其他**旧代**、`status IN ('ready','claimed')` 的 business effect（`effect_id <> p_effect_id` 视同已结算）；
  4. 本次 class ≠ `unknown`；
  5. run 非 terminal（未被 cancel 抢先）。
- **消费动作**（同一次 advance）：清 `pending_steer`；建**恰好一条** model_call，`cause='steer'`、`epoch_no = pending_steer.epoch`、`generation = max(run.driving_generation, pending_steer.generation)`、`instruction = pending_steer.instruction`、`input = 该 run 最近一条 model_call 的 input`、`reserve/digests` 重算；事件 `pending_steer_consumed`；**不发布旧代继承者**（该次 settlement 的 successors 只有这一条）。
- **latest wins**：多次 steer 依次覆盖 `pending_steer`；消费只读最后一次写入值；消费同一次 advance 只能产生一条 model_call（`u_effects_model_call` + 确定性 id 双保）。
- **unknown**：旧代结算为 unknown ⇒ `blocked_unknown`，清 `pending_steer`（`c_runs_steer` 要求 terminal 时 pending_steer IS NULL，10:56），0 successor，不自动续链。
- **cancel 抢先**：run 已 cancelled ⇒ 结算只记事实/成本，0 successor，`close_intent.kind='cancel'` 不被改写，pending_steer 由 cancel 清空。
- **[S4-addendum A] steer 立即归档的退款（W1）**：本节开头的立即路径在任一 `claimed` business effect 存在时只写 `pending_steer`，否则立即建 model；两条路径都会把同 run 的 `ready` model_call 归档为 `cancelled`。该归档未执行，MUST 在同一 delta 内把每条被归档 model 的 `request.reserve.tokens` 全额退回 `remaining_tokens`（NULL 保持 NULL），并计入 expected-delta 全等；随后按 post-refund 余额准入或封口（见 C23 addendum A/B）。

### C22 run-pin 释放（terminal / 静默结算）

**精确谓词**（结算路径的唯一版本；cancel 路径 40:969-978 是同形状的既有实现，对同 delta 内被取消的 ready effect 做同样的排除）：

```sql
UPDATE v24.pins p
   SET released_at = now(), released_by_effect = :settling_effect_id
 WHERE p.consumer_run_id = :run_id
   AND p.released_at IS NULL
   AND :run_status IN ('completed','failed','cancelled','blocked_unknown')
   AND NOT EXISTS (
         SELECT 1 FROM v24.effects e
          WHERE e.pin_id = p.pin_id
            AND (e.status IN ('ready','claimed')
                 OR (e.status = 'unknown' AND e.resource_quiesced_at IS NULL)));
```

- **绑定**：tool effect 的 `pin_id` = 该 tool key 对应的 live run pin（`pins.consumer_run_id=run AND pins.key=tool.key AND released_at IS NULL`）；model_call 的 `pin_id` 恒 NULL（设计 §5.6：只有 tool 绑定 slot/descriptor/pin）。缺 pin 或 descriptor 不匹配 ⇒ `invalid_outcome`（W0），不建 tool successor。
- **执行点**：cancel（现状 40:969-978，谓词一致，不改）、model/tool settlement 使 run terminal 的那次 advance（新增，W5）、`blocked_unknown` 转换。非 terminal 的结算不释放任何 pin。
- **顺序**：先更新 effects（本次 effect 离开 ready/claimed），再更新 run 为 terminal，最后 update pins。否则本次 effect 会把自己的 pin 挡住。
- **保守性**：`unknown` 且 `resource_quiesced_at IS NULL` 的 effect 永远挡住其 pin，直到 S5 的 inspect 置位；这正是 G3b-2 留下的未验证半部，S4 用 G2b-S 补上。
- **不新增列、不删行**；只写 `released_at`/`released_by_effect`。

### C23 turn / 预算 / seal

- **turn（Oracle 风险 3，冻结）**：`turn_no` 只在**已提交的 business settlement**（success/failure/unknown，含语义类）时 `+1`。admission 不 `+1`、结构类 W0 不 `+1`、重交不 `+1`。`turn_no` 不参与任何排序或续链判定；`result.turn_no` 是快照。
- **steps（F3=A）**：每准入一个 `model_call`（start/steer/respond/continuation 四条生产者）−1，下限 0，**不退**（一个 turn 已发生）。准入前检查 `remaining_steps >= 1`，否则不建该 model effect 并写 budget seal。`start` 的首个 model_call 在 start 同一 advance 内扣，因此 `start` 落库的 `remaining_steps = budget.steps − 1`。
- **tokens（F3=A）**：准入时预扣 `reserve = LEAST(剩余 tokens, 4096)`，落库 `remaining_tokens -= reserve`；结算退差：success/failure 退 `reserve − coalesce(usage.tokens,0)`，unknown 与语义类**不退**。`reserve=0` 仅在 `remaining_tokens IS NULL` 时表示无上限；`remaining_tokens=0` 表示已耗尽（见 [S4-addendum B]），语义上限检查不再适用。扣减/退款与 effect 状态跃迁同事务，靠状态跃迁（claimed→settled 一次）保证重试不重复扣退。
- **[S4-addendum A] reserve 守恒（W1）**：任何「移除 `ready` model_call 但未执行」的跃迁（steer archive、cancel）MUST 在同一 delta 内把该 model `request.reserve.tokens` **全额退回** `remaining_tokens`（run 的 tokens 为 NULL 时保持 NULL），并把退款金额计入该命令的 expected-delta 全等校验。`success`/`failure` 结算后 MUST 保持不变量：`initial_tokens = spent_tokens + SUM(active ready|claimed model reserve.tokens) + remaining_tokens`（NULL budget 豁免），其中 `spent_tokens` = success/failure 的 `usage.tokens`，或 unknown/语义类的**全额 reserve**（unknown 不退）。结算退差用 `greatest(0, remaining + reserve − usage)` 防止 0-token start 的 usage 把余额压成负数。
- **[S4-addendum B] `remaining_tokens=0` 是耗尽，只有 NULL 是无上限**：steer/respond MUST NOT 在 post-refund 余额为 0 时创建 `reserve=0` 的 model_call。若无法准入：当 `v24.loop_sealable` 谓词成立时写**最小 budget seal**（`status='completed'`、`close_intent={kind:'budget'}`、`result={v:1,close_reason:'budget_exhausted',...}`、`ended_at`），否则不建 model、0 successor（仍完成 archive/退款/账务写入）。continuation 保持既有 `(remaining_tokens IS NULL OR remaining_tokens > 0)` guard；start 仍在 tokens=0 时准入首个 model（C23：0-token run 只允许一个 turn）。
- **tool_calls（F3=A）**：在 model settlement 准入 N 条 tool 时 −N；`N > remaining_tool_calls` ⇒ 不建 tool、写 budget seal（completed），**不**返回错误。设计 §5.2「预算耗尽生成一次封口命令」。
- **wall_ms**：每次结算 `remaining_wall_ms = greatest(0, remaining_wall_ms − elapsed_ms)`，`elapsed_ms = extract(epoch from (now()−e.created_at))*1000`。
- **seal 谓词**（`v24.loop_sealable(p_run, p_effect_id, p_close_intent, p_interaction, p_pending_steer)`，冻结；三个「拟写入值」参数是必须的——解释器在 DML 前读不到自己本事务尚未落库的写入）：

```sql
SELECT r.status = 'running'
   AND p_close_intent IS NOT NULL
   AND p_interaction IS NULL
   AND p_pending_steer IS NULL
   AND NOT EXISTS (
         SELECT 1 FROM v24.effects e
          WHERE e.run_id = r.run_id
            AND e.kind IN ('model_call','tool_call')
            AND e.effect_id <> p_effect_id
            AND (e.status IN ('ready','claimed')
                 OR (e.status = 'unknown' AND e.resource_quiesced_at IS NULL)))
  FROM v24.runs r WHERE r.run_id = p_run;
```
**Oracle 风险 1 已覆盖**：第三条 `NOT EXISTS` 分支显式挡住「未静默 unknown business effect」，因此含未静默 unknown 的 run 永远不会被 `completed`/`failed` 封口（S3 的 `cancel` 是唯一允许带 unknown 封口的路径，由 cancel interpreter 负责，不在 S4 的 writer 内）。

- **[S4-addendum] C23-seal：同 delta 归档与 waiting 封口（W1）**：`v24.loop_sealable` 的签名为 `(p_run uuid, p_effect_id uuid, p_close_intent jsonb, p_interaction jsonb, p_pending_steer jsonb, p_excluded uuid[] DEFAULT '{}', p_from_waiting boolean DEFAULT false)`。封口谓词的首条改为 `(r.status = 'running' OR (p_from_waiting AND r.status = 'waiting'))`；`NOT EXISTS` 在排除 `p_effect_id` 之外，还必须排除 `p_excluded` 中的每个 effect id，并保留 `unknown` 且 `resource_quiesced_at IS NULL` 的挡板分支。默认值使 model settlement 的既有调用语义不变。**steer** 在同一 delta 归档 ready business effects（model/tool）后，若 post-refund 余额不能准入，必须把被归档的 id 传入 `p_excluded` 并写 budget seal（`completed`、`close_intent={kind:'budget'}`、`result={v:1,close_reason:'budget_exhausted',...}`、`ended_at`、`pending_steer/interaction=NULL`），archive+refund 仍在同一 delta。**respond** 在 token-0 余额时消费 interaction，并传 `p_from_waiting => true`（拟写入 interaction/pending 均为 NULL），写同样的 budget seal，而不是把 run 留成无 effect 的 `running`。
- **terminal 三态**：
  - `completed`：`close_intent.kind IN ('final','budget')` 且 seal 谓词真。`result` 冻结为
    `{"v":1,"close_reason":"final|budget_exhausted","final_text":"…|null","turn_no":N,"budget":{"steps":S,"tokens":T,"tool_calls":C,"wall_ms":W}}`。
  - `failed`：**唯一**由 `close_intent.kind='abort'` 产生（provider 失败或显式 abort），`result={"v":1,"close_reason":"provider_failure|abort","turn_no":N}`。
  - `blocked_unknown`：class=unknown 或语义类的任一 business settlement。`close_intent={kind:'unknown',reason:'outcome_unknown|semantic_violation',effect_id:…}`，`result={"v":1,"close_reason":"unknown","turn_no":N}`，`pending_steer=NULL`，`interaction=NULL`。
- **禁止**：有 `ready|claimed` business effect、有 `pending_steer`、有非空 `interaction`、或有未静默 unknown 时写 `completed`/`failed`。`cancelled` 由 cancel 负责，S4 不改写其 `close_intent`。
- **终态 writer 的唯一性（Oracle 补丁 4）**：S4 的 seal 是 `runs.result` 的首个写入者（现状无写入者，见台账 I7 与矩阵 §4）；该 writer 只写 `result`/`close_intent`/`ended_at`/`status`，**不得改写 `effects.outcome` 的首次 receipt**。
- **幂等**：seal 只在本次 advance 内发生一次；重复 settlement 由 30:263-269 的 receipt replay/conflict 拦截，不重复写 terminal 事件。

SET search_path = pg_catalog, v24

-- C23 seal 谓词。p_close_intent / p_interaction / p_pending_steer 是本 advance
-- **将要写入**的终值（不是当前行值），因为解释器在 DML 之前就无法读到自己的写入；

CREATE FUNCTION v24.loop_sealable(p_run uuid, p_effect_id uuid,
  p_close_intent jsonb, p_interaction jsonb, p_pending_steer jsonb)
RETURNS boolean LANGUAGE sql STABLE SET search_path = pg_catalog, v24 AS $$
  SELECT r.status = 'running'
     AND p_close_intent IS NOT NULL
     AND p_interaction IS NULL
     AND p_pending_steer IS NULL
     AND NOT EXISTS (
           SELECT 1 FROM v24.effects e
            WHERE e.run_id = r.run_id
              AND e.kind IN ('model_call','tool_call')
              AND e.effect_id <> p_effect_id
              AND (e.status IN ('ready','claimed')
                   OR (e.status = 'unknown' AND e.resource_quiesced_at IS NULL)))
    FROM v24.runs r WHERE r.run_id = p_run;
$$;

-- C22 结算路径的 pin 释放集（applier 用同一函数重算并逐项比对）
CREATE FUNCTION v24.run_pin_release_set(p_run uuid, p_effect_id uuid,
  p_status text, p_by_effect uuid) RETURNS jsonb
LANGUAGE sql STABLE SET search_path = pg_catalog, v24 AS $$
  SELECT coalesce(jsonb_agg(jsonb_build_object(
           'key',jsonb_build_object('pin_id',p.pin_id),
           'set',jsonb_build_object('released_at',now(),
                                    'released_by_effect',p_by_effect))
           ORDER BY p.pin_id),'[]'::jsonb)
    FROM v24.pins p
   WHERE p.consumer_run_id = p_run AND p.released_at IS NULL
     AND p_status IN ('completed','failed','cancelled','blocked_unknown')
     AND NOT EXISTS (
           SELECT 1 FROM v24.effects e
            WHERE e.pin_id = p.pin_id AND e.effect_id <> p_effect_id
              AND (e.status IN ('ready','claimed')
                   OR (e.status = 'unknown' AND e.resource_quiesced_at IS NULL)));
$$;

### 5.2 `v24.interpret_model_settlement`（NEW）

签名：`(p_effect_id uuid, p_principal uuid, p_outcome jsonb, p_closure jsonb) RETURNS jsonb`。

处理顺序（全部在解释器内、无 DML）：

1. 读 effect（advance 已锁）；`kind <> 'model_call'` ⇒ `{write:false,error:invalid_outcome}`。
2. 读 run；`status='blocked_unknown'` ⇒ `{write:false,error:blocked_unknown}`；其余 terminal ⇒ `already_terminal`。
3. **结构类校验（C19.0）**：`body.kind='model_call'`；result 形状、互斥；`usage` 形状；`tool_calls ≤ 16`；`state ≤ 64 KiB`；`cause` 与父 effect 一致；`turn_no/revision` 算术。任一失败 ⇒ `{write:false,error:invalid_outcome}`（零写）。
4. 计算 `late = (e.generation <> r.driving_generation OR e.epoch_no <> r.epoch_no)`。
5. class=unknown ⇒ 构造 `blocked_unknown` delta（§C19），结束。
6. **语义类校验（C19.0）**：若 `tool_calls` 中存在 key ∉ live run pins，或 `reserve.tokens > 0 AND usage.tokens > reserve.tokens` ⇒ 构造「语义类」delta：`effect.status='unknown'`、`outcome=p_outcome` 原样、`resource_quiesced=false`、`run=blocked_unknown`、`close_intent{kind:'unknown',reason:'semantic_violation'}`、tokens 不退、turn+1、0 successor、pin 保留；结束。
7. 计算新 `turn_no`（+1）、token 退款 `reserve − coalesce(usage.tokens,0)`、wall 扣减；构造 run set。
8. `late` ⇒ 只写事实/成本 + 事件 `model_call_settled(late=true)`，0 successor，结束。
9. `final` ⇒ `close_intent{kind:'final'}`；若 `loop_sealable` ⇒ completed + result + pins（C22）。
10. `interaction` ⇒ 写 interaction、`status='waiting'`、0 successor、事件 `interaction_created`。
11. `tool_calls` 非空 ⇒ 逐项绑定 `pin_id`（key 已在第 6 步保证存在），检查 `N <= remaining_tool_calls`：足够则 `remaining_tool_calls -= N` 并建 N 条 tool successor（pin_id、batch_digest）；不足则 budget seal（completed），0 tool successor。
12. 否则（纯文本、非 final）⇒ 用**第 7 步退款后**的余额判定：`remaining_steps >= 1 AND remaining_wall_ms > 0 AND (remaining_tokens IS NULL OR remaining_tokens > 0)` 时建 1 条 continuation，准入再扣 `remaining_steps -= 1`、`remaining_tokens -= model_reserve(remaining_tokens)`，request 写入新的 `reserve.tokens`；否则 budget seal（`tokens=0` 的 run 只能跑首轮，符合 §5.2）。
13. 返回 delta（键闭集与 §5.4 一致）：

```json
{"write": true,
 "domain": {"update": {
    "runs": [{"key": {"run_id": "<uuid>"}, "set": {<§5.4 的 13 列闭集>}}],
    "pins": [{"key": {"pin_id": "<uuid>"},
              "set": {"released_at": "<ts>", "released_by_effect": "<uuid>"}}]}},
 "effect": {"status": "succeeded|failed|unknown",
            "outcome": <p_outcome 原样>,
            "resource_quiesced": true},
 "events": [{"entity_type": "run", "entity_id": "<uuid>", "event_kind": "<§4.6>",
             "payload": {}, "payload_digest": "<bytea 可省略>"}],
 "successors": [{"effect_id": "<uuid>", "ordinal": 0, "kind": "model_call|tool_call",
                 "run_id": "<uuid>", "fiber_id": "<uuid|null>", "episode_id": "<uuid|null>",
                 "epoch_no": 1, "generation": 1, "pin_id": "<uuid|null>",
                 "request": {<C17 或 C20 的 request>}}]}
```
`pins` 为空时省略该键或给 `[]`（两者等价，applier 以 `[]` 处理）。

### 5.3 `v24.interpret_tool_settlement`（NEW）

1. 读 effect/run；terminal 处理同 model。
2. **结构类校验**：`body.kind='tool_call'`、result 形状（含 output 对 descriptor schema）、class/status 一致、usage 形状。失败 ⇒ `{write:false,error:invalid_outcome}`（零写）。
3. class=unknown ⇒ `blocked_unknown`（该 effect 的 pin 因未静默保留）+ 事件；结束。
4. 否则：`turn_no+1`、wall debit、effect settle、事件 `tool_call_settled`。tool_calls 与 steps 已在 admission 扣，本步不动。
5. 批次屏障（C20 五步）：不是闭合观察者 → 0 successor；是闭合观察者且无在途 model → continuation（`parent = tool_effect_id(model,max_ordinal)`；准入时扣 steps/reserve，不足则 budget seal）；run terminal 或 late → 0 successor。
6. 若 settlement 使 run terminal（只可能来自取消后的 late 结算或 blocked_unknown）→ C22 pin 集。
