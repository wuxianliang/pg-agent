### 已实证的 PostgreSQL 18.4 事实（本机 pgembed 实测，2026-10-23）

这十条直接决定 DDL 形状，S1 计划不得再当作「待查」：

1. **partial unique index 不能 DEFERRABLE**：`CREATE UNIQUE INDEX ... WHERE ... DEFERRABLE` 语法错误；表级 `UNIQUE (a) WHERE ...` 也不存在（`syntax error at or near "WHERE"`）。⇒ 所有「至多一个未释放」类基数只能用非延迟唯一索引表达，且**同事务内顺序敏感**。
2. **实测顺序敏感**：`UNIQUE INDEX ON ep(fiber) WHERE closed_at IS NULL` 下，E1 未关闭时插 E2 立即 `23505`；先 `UPDATE` E1 置 `closed_at` 再插 E2 则通过。⇒ O5 的「先关旧代再插新代」不是风格建议，是硬约束。
3. **DEFERRABLE 唯一约束不能作为 FK 目标**：`cannot use a deferrable unique constraint for referenced table`。⇒ `episodes(fiber_id,episode_id)` 的 `UNIQUE` 必须非延迟（它同时是 `installs`/`fibers` 复合 FK 的目标）；`requests.effect_id` 之所以能 DEFERRABLE，是因为目标是 `effects.effect_id` 主键（非延迟）。实测「先插 request 后插 effect、COMMIT 时闭合」可行。
4. **CHECK 不能含子查询**（`cannot use subquery in check constraint`）⇒ 任何跨行不变量（`route_path = parent.route_path || scope_id`、`closed_at` 需子 scope 全闭）**不能**用 CHECK 表达，只能由 advance 校验或延迟约束触发器。同列 array `||` 的 CHECK 合法。
5. **复合 FK 要求目标存在列序完全匹配的唯一约束**（`there is no unique constraint matching given keys`）。
6. **`DEFERRABLE INITIALLY DEFERRED` 的 CONSTRAINT TRIGGER 在 COMMIT 时求值且能中止事务**（实测抛出并回滚），是唯一能跨行、跨表、覆盖同事务全部写入的强制机制。
7. **G 的可观测形态**：`pg_advisory_xact_lock(24,1)` 在 `pg_locks` 中为 `(locktype='advisory', classid=24, objid=1, objsubid=2)`；bigint 形式 `(24<<32)|1` 映射到同一行。断言 G 被持有必须用 `objsubid=2`，用 `objsubid=1` 查会得到 0 行。
8. **`INSERT ... ON CONFLICT DO NOTHING RETURNING`**：键已存在时返回空结果集，键不存在时返回新行 ⇒ 可作为 O2「查无→插入」的原子探测原语。
9. **append-only 需两个 statement 级触发器**：`BEFORE UPDATE OR DELETE` 与 `BEFORE TRUNCATE` 分开建（TRUNCATE 无法被行级触发器拦截），两者均以 `23514` 拒绝；实测三语句全部被拦。
10. `max(seq)` 由 `UNIQUE(entity_type,entity_id,seq)` 索引支撑为 `Index Only Scan Backward`，O3 的「同事务内取 MAX+1」无需计数器表或全表扫描。

**S1 结项**：W1–W6 全部完成，G1-A…G1-R 全部有生产者并实跑通过；按 AGENTS.md 以一次里程碑提交收尾。

**实现顺序**：W1 → W2 → W3 → W4 → W5 → W6，严格串行。pre-plan §5.2 冻结「同一时间只允许一个 stage 修改 `v24/` 下的 SQL/Python」，并行只发生在读、评审与用例设计。

**每步停手条件**：某工项的 Done when 有一条不绿即停，不进入下一工项；不得以「下工项修」结项（AGENTS.md）。

S1 是 1 个里程碑 = 1 次提交。若实施中确需拆分，先回写 pre-plan 并新增显式子 gate，不得静默拆 commit。

## 2. 定位与边界

### 2.1 在设计稿中的位置

S1 是 v24 的**内核**：它不实现任何业务动词的语义，只建立「谁能写、按什么顺序写、写什么算成功」的权威。三个使用面（agent loop、六动词、Cordis 生命周期）都将在后续阶段把各自的解释器挂到这个入口上，因此 S1 的 ABI 一旦冻结，C4/C10/C11 的消费方全部按它实现。

### 2.2 发布合同（后续阶段消费）

| 合同 | 内容 | 冻结位置 |
|---|---|---|
| C1 | 十表 DDL/FK/索引/约束 | §4.1–§4.11 |

### 2.3 明确不做

- 不实现 `resolve`、`poll`、`wait_check`（S2/S3）；本阶段不建任何读函数，也不建 reader 角色。
- 不实现 `fiber_control`、`dispose` 的领域行为；十表里 `pins/episodes/fibers/slots` 只有 DDL 与约束，没有任何 S1 写入路径。

- 不调用真实 provider/工具/网络；FakeHost 只在事务外被调用，且不打开套接字。
- 不修改 `v99/` 或任何既有 stage 的 SQL、loader、gate。
- 不宣称任何 gate 已绿：本文件是计划，不是执行记录。

加载器约定（镜像 `v99/core/load.py:6–37`，不复用其常量）：显式有序 tuple 而非 glob；拒绝非前缀清单、symlink、`sql/` 下未登记文件；`load_stage(conn)` 拒绝 `autocommit`、**从不 commit**，原子性由调用方事务持有。后续阶段只能向 tuple **尾部追加**新文件（`60_*.sql`…），不得重命名或重排既有文件。

**不引入 pgcrypto**：`gen_random_uuid()` 与 `sha256(bytea)` 在 PostgreSQL 18 均为核心函数。因此 `00_schema.sql` 只建 schema 并断言「本库不存在非 `v24` schema 的扩展依赖」；这比 v99 少一个扩展与一条 `digest()` 依赖。记为 D7。

### 4.4 `pins`

设计稿 §3.1.4 只给 `consumer_id uuid`，但 §3.2 L189 要求「消费者 XOR CHECK」。单列无法既做 XOR 又保留同名语义，因此以**生成列**实现：

```sql
CREATE TABLE v24.pins (
  pin_id               uuid PRIMARY KEY,
  consumer_type        text NOT NULL,
  consumer_episode_id  uuid,
  consumer_run_id      uuid,
  consumer_id          uuid GENERATED ALWAYS AS (coalesce(consumer_episode_id, consumer_run_id)) STORED,
  consumer_epoch       bigint NOT NULL,
  key                  text NOT NULL,
  slot_id              uuid NOT NULL,
  provider_fiber_id    uuid NOT NULL,
  provider_episode_id  uuid NOT NULL,
  descriptor_digest    bytea NOT NULL,
  created_by_effect    uuid NOT NULL,
  released_by_effect   uuid,
  released_at          timestamptz,
  CONSTRAINT c_pins_type CHECK (consumer_type IN ('activation','run')),
  CONSTRAINT c_pins_xor CHECK (
       (consumer_type = 'activation' AND consumer_episode_id IS NOT NULL AND consumer_run_id IS NULL)
    OR (consumer_type = 'run'        AND consumer_run_id IS NOT NULL AND consumer_episode_id IS NULL)),
  CONSTRAINT c_pins_epoch CHECK (consumer_epoch >= 0),
  CONSTRAINT c_pins_release CHECK ((released_at IS NULL) = (released_by_effect IS NULL))
);
CREATE UNIQUE INDEX u_pins_live ON v24.pins (consumer_type, consumer_id, consumer_epoch, key)
  WHERE released_at IS NULL;
CREATE INDEX i_pins_slot ON v24.pins (slot_id) WHERE released_at IS NULL;
```

该形状已实测可编译，且 XOR CHECK 在违例时确实以 `23505` 之外的 `c_pins_xor` 拒绝。「pin provider epoch 必须等于 slot episode」「release 前无活 pin」是跨行不变量，归 advance 与 S2。

### 4.11 跨表外键、索引、触发器与插入顺序

**冻结的插入顺序规则**（每个写事务内）：

1. 领域行按普通 FK 的拓扑序插入：
   `scopes` → `installs`（root，owner 两列为 NULL）→ `fibers` → `episodes` → `slots` → `pins` → `runs`；
   带 owner 的 **child install** 例外：它的 `(owner_fiber_id,owner_episode_id)` 指向的 episode 必须已存在，因此只能在 owner episode 之后插入（跨事务即已存在，同事务则后置）。
2. `effects` 行（command effect 一次性 settled，或后继为 ready）；
3. `requests` 行；
4. `events`；
5. 后继 effects。

该顺序由普通 FK 强制（不是可选风格）：`fibers.install_id → installs` 要求 installs 先；`episodes.fiber_id → fibers` 要求 fibers 先；`runs.owner_episode_id → episodes` 要求 episodes 先；`effects.{scope,run,fiber,episode,pin}_id` 要求全部先。

### 4.12 列/约束 → 写入阶段归属表

因为十表在 S1 一次落地，**大部分列在 S1 没有任何写入路径**。不处理这一点，G1 会出现 vacuous 断言（评审口径：每个断言要有生产者）。归属如下：

| 表 | S1 有写入者的列/约束 | S1 仅 DDL、写入者在后续阶段 | S1 的对应验证方式 |
|---|---|---|---|
| `scopes` | 全部创建列、`close_requested_at` | `closed_at`（S5） | 创建/关闭意图由 G1-J2 实测；`closed_at` 仅断言 CHECK 拒绝无 intent 的写入（owner DML 反例） |
| `runs` | 无 | 全部（S3 状态机、S4 预算/回合） | **不做行为断言**；只在 G1-N/O 断言表存在、CHECK/索引存在、以 owner DML 打穿 3 条 CHECK |
| `effects` | 全部 | `resource_quiesced_at` 的 `unknown` 分支（S2/S6） | G1-B…G1-H 全部实测 |
| `pins` | 无 | 全部（S2 激活、S3 run pin） | owner DML 打穿 XOR CHECK 与 live-pin 唯一索引 |
| `episodes` | 无 | 全部（S2） | owner DML 打穿 `u_episodes_ident` 非延迟 + `u_episodes_open` 顺序敏感 |
| `fibers` | 无 | 全部（S2） | owner DML 打穿 owner pair / tombstone CHECK |
| `slots` | 无 | 全部（S2） | owner DML 打穿 `u_slots_live` 与 release 单调 |
| `installs` | 创建列 + `preparing/installed/prepare_failed/prepare_unknown` | `owner_*`（S2）、`dispose_pending/disposed/dispose_effect/disposed_at`（S2 叶子、S5 闭包） | G1-I/J 实测四态；owner DML 打穿 `c_installs_disposed` |

### 4.13 `outcome_v1` 与 `advance` ABI

```sql
CREATE FUNCTION v24.advance(p_effect_id uuid, p_outcome jsonb)
RETURNS jsonb LANGUAGE plpgsql SECURITY DEFINER
SET search_path = pg_catalog, v24;
```

`outcome_v1` 外形（§2.1 L70）：

```json
{"v": 1,
 "class": "command | claim | success | failure | unknown",
 "claim": {"attempt": 0, "fence": 0, "owner": "<role>"} | null,
 "body":  { ... },
 "receipt_key": "<text>"}
```

**class 取 5 值，不是 4 值**（记为 D1，理由见 §7）。规则：

- `class = "command"` ⇒ `claim` 必须 null；`body.op` ∈ `{admit_and_apply}`；`body.kind` ∈ command kind 闭集。
- `class = "claim"` ⇒ `claim` 必须 null；`body` **恰为** `{lease_ms: int}`，出现其他键即 `invalid_args`；owner 不经 body 传递，提交时冻结为 `claim_owner := session_user::text`（设计 §B.4 L562）。
- `receipt_key` 在所有 class 均可省略，且**不参与任何匹配**；receipt 身份 = `effect_id` + outcome digest（设计 §2.1 L70）。
- `class ∈ {success, failure, unknown}` ⇒ `claim` 必须非 null 且 `owner` 必须等于该 effect 当前 `claim_owner`；`unknown` 的 `body` 不得含可执行后继。

**canonical_bytes 归属**（D10）：wrapper 用共享的 `v24.canonical_json(payload) → text → bytea` 计算 `request_bytes` 并传入 `body.canonical_bytes`（base64）；`advance` 重算后比对，不等则 `invalid_args`。这样既保留 §2.1 的字段，又使幂等摘要以服务端为准，客户端无法声明一段与 payload 不一致的「规范化字节」。

返回封套（§2.1 L72）：

```json
{"v": 1, "disposition": "committed | replay | deferred",
 "effect_id": "<uuid>", "emitted": ["<uuid>", ...], "revision": 0, "claim": null}
```

`claim` 成员**仅当** `class=claim` 且 `disposition=committed` 时非 null，形为 `{"attempt":N,"fence":N,"owner":"<session_user>"}`；command / settlement / 任何 `deferred` 均为 null（设计 §2.1 L72，记为 D12）。这是 host 取得执行资格的唯一返回通道；claim 为 `deferred` 时调用方不得猜测 token。

`revision` 在 S1 恒为 `0`：S1 不写 `runs`，而 `runs.revision` 是 poll 游标；S3 接管后改为返回提交后的 `runs.revision`。这是 C2 的一个已知空洞，必须在 S3 开工前回写 C2（否则 S3 会以为它已经是 run 语义）。

错误封套：

```sql
CREATE FUNCTION v24.error_v1(p_code text, p_detail jsonb DEFAULT '{}'::jsonb)
RETURNS jsonb LANGUAGE plpgsql IMMUTABLE;
-- 码不在 §4.16 闭集 => RAISE invalid_args（闭集只在一处实现）
```

```json
{"v": 1, "error": {"code": "request_conflict", "detail": {...}}}
```

**`effect_id` 的派生**（D8）：§B.3 L548–550 的 wrapper 签名**没有 `effect_id` 参数**，但 command 的幂等与 receipt 锚点需要一个稳定 effect 身份。因此 wrapper 必须确定性地派生：

```sql
CREATE FUNCTION v24.effect_id_for(p_principal uuid, p_request_key text, p_kind text)
RETURNS uuid LANGUAGE sql IMMUTABLE AS $$
  SELECT (substr(h,1,8)||'-'||substr(h,9,4)||'-'||substr(h,13,4)||'-'||
          substr(h,17,4)||'-'||substr(h,21,12))::uuid
  FROM (SELECT encode(sha256((p_principal::text||':'||p_kind||':'||p_request_key)::bytea),'hex') AS h) s;
$$;
```

`advance` 在 command 分支断言 `p_effect_id = v24.effect_id_for(principal, body.request_key, body.kind)`，不等则 `effect_id_conflict`。这样：重试同一 request_key 必然得到同一 effect_id（replay 成立）；不同 request_key 必然得到不同 effect_id（不会误碰撞）；host 侧的 claim/settlement 仍用显式 `effect_id`，ABI 不变。

#### 4.13.4 优先级与会话次序

固定次序，任一步失败即止，后续检查不再执行。这是 C4（`§2.2`）指向的权威表。

| # | 检查 | 失败返回 | 有写 |
|---|---|---|---|
| 1 | 形状 / 字节上限 / class 闭集 / 逐 class body 形状 | `invalid_args` | 无 |
| 2 | `session_user → principal` 与三行角色矩阵 | `unauthorized` | 无 |
| 3 | **G 首锁** `pg_advisory_xact_lock(24,1)` | — | — |
| 4 | `class=command` ⇒ `p_effect_id = effect_id_for(principal, request_key, kind)` | `effect_id_conflict` | 无 |
| 5 | request 身份行 `(principal_id,request_key)` 加锁与读取 | — | — |
| 6 | replay：同键同 bytes | `disposition=replay` | 无 |
| 7 | replay 冲突：同键异 bytes | `request_conflict` | 无 |
| 8 | receipt/token：已结算同 digest ⇒ `replay`；异 digest ⇒ `receipt_conflict`；token 不符 ⇒ `stale_claim`；已结算再 claim ⇒ `invalid_args` | 见左 | 无 |
| 9 | 闭包发现 + 按 B.1 一次性全序加锁 | `retry_with_closure` | 无 |
| 10 | 解释器（command/settlement）或资格签发（claim） | 业务码 | 有 |
| 11 | delta 足迹校验 | `invalid_outcome` / `cleanup_cycle` | 无 |
| 12 | 提交 | — | 有 |

两条不可交换的顺序规则：

- **4 先于 6**：`effect_id` 派生校验在 replay 之前。否则客户端可拿旧 request 换回 replay，而 effect_id 错配被掩盖（设计 §A.3 L631）。
- **8 内部先结算后 token**：先判是否已结算（同 digest ⇒ replay），再判 token。否则「已成功但重发」会因 lease 过期被误判为 `stale_claim`。

`class=claim` 只走 1→2→3→9→10（签发资格），不经过 4、5、6、7、11；claim 也不写 events、不插后继。

### 4.14 `advance` 执行序

```text
advance(p_effect_id, p_outcome):
 A. 形状校验（不取任何锁）
    A1. jsonb_typeof(p_outcome)='object'；v=1；class 在 5 值内
    A2. body 字节数 <= 1 MiB；嵌套深度 <= 32；键数 <= 200
    A3. class=command => body.op='admit_and_apply'、kind 是 command kind、body.request_key 与 body.canonical_bytes 必填
        class=claim   => body 恰为 {lease_ms}，lease_ms 在 1..300000
        class=success|failure|unknown => claim 非 null 且字段类型正确
        class=unknown 额外要求 body 不含 successors/intents 类可执行后继键
    A4. class=command => base64_decode(body.canonical_bytes) = v24.canonical_json(body.payload)，
        且 sha256(该 bytea) 即后续用于 request_digest；不等 => invalid_args（D10 的落地位置：
        否则客户端可固定 canonical_bytes 而只改 payload，C2 会误返 replay）
    A5. 以上任一失败 => RETURN error_v1('invalid_args', ...)     -- 零写
 B. 身份（不取 G）
    principal := v24.principal_id(session_user)                  -- §4.19
    权限：按 class/kind 查静态 service-role 矩阵（§4.19）；不通过 => unauthorized（零写）
 C. G —— 全事务第一把锁
    PERFORM pg_advisory_xact_lock(24, 1);
 D. 分岔：command | claim | settlement（三者互斥）
 E1. 三条分支的公共前半：闭包发现 -> 按 B.1 全序锁行 -> 验证
 E2. command 与 settlement：解释器返回 delta -> 足迹校验（§4.14.3）
     -> 应用 -> 写 events -> 插后继
 E3. claim：只写 effects 的 attempt_no/fence/claim_owner/lease_until/status，
     不调解释器、不产 delta、不写 events、不插后继
 E4. 三条分支均 RETURN 统一封套；claim 成员仅 claim 分支且 disposition=committed 时非 null
 F. 任何未预期的 SQL 错误 => 不吞；RAISE，事务回滚（写类 W2）
```

#### 4.14.1 command 分支（`admit_and_apply`）

```text
C0. 断言 p_effect_id = v24.effect_id_for(principal, body.request_key, body.kind)
      不等 => effect_id_conflict（零写）
C1. SELECT effect_id, request_digest, response FROM v24.requests
      WHERE principal_id = principal AND request_key = body.request_key
      FOR UPDATE;
C2. FOUND:
      若 requests.request_digest <> sha256(canonical_bytes) => request_conflict  零写
      否则 RETURN requests.response **原样**（不写任何行、不改写 disposition）
      设计 §2.3 L87 / §A.2 L621 要求「返回首次响应」，因此 command 重放是 byte-equal；
      调用方以「同一主键得同一 response」作为幂等证据。`disposition='replay'` 不在此处产生。
C3. NOT FOUND: 此时**不**对 effects 取 FOR UPDATE（§B.1 把 effect 排在第 5 层，晚于 scope/run）
C4. 取闭包并按 B.1 全序加锁：scope(root→leaf) -> run -> effect -> install -> fiber -> episode -> slot -> pin
C4.1 在已锁定的 effect 行上判定：FOUND => 身份碰撞（应由 C0 排除）=> effect_id_conflict 零写
C5. 调对应解释器（§4.17 / §4.18）得 delta（只返回，不写表）
C6. 足迹校验（§4.14.3）
C7. 应用 delta：领域行 -> effect(settled) -> request -> events -> successor effects
C8. disposition='committed'
```

#### 4.14.2 claim 与 settlement 分支

```text
K0. 无锁读 effects 取 scope_id/run_id 关联，再按 B.1 全序锁：
    scope(root→leaf) -> run -> effect -> install -> fiber -> episode -> slot -> pin
    （禁止先对 effects 取 FOR UPDATE——§B.1 把 effect 排在 scope/run 之后）
K1. 在已锁 effect 行上判定；NOT FOUND 在 K0 阶段即返回 effect_id_conflict（零写）
K2. claim：
      kind LIKE 'command\_%'                    => invalid_args（command 不取 claim）
      status='ready'                            => attempt = attempt+1, fence = fence+1
      status='claimed' AND lease_until <= now() => attempt = attempt+1, fence = fence+1  （真正替代旧 claim）
      status='claimed' AND lease_until >  now() => disposition='deferred'（零写，不抢）
      其他 status（succeeded/failed/unknown/cancelled）=> invalid_args（已结算/已取消不可 claim）
      SET status='claimed', claim_owner=session_user::text, lease_until=now()+lease_ms
      RETURN 统一封套，claim = {attempt, fence, owner: session_user::text}
S1. 同 K0/K1（effect 已在闭包内锁定）
S2. 已结算：
      若 outcome digest 与已存 receipt 相同 => disposition='replay'（不写行）
      — 这是 `replay` 的唯一生产者：结算没有 request 行可原样返回，
        设计 §B.4 L564 明确要求该 disposition
      否则                              => receipt_conflict（不覆盖首次 receipt）
      status='cancelled'                 => receipt_conflict
S3. token 校验：body.claim.attempt/fence/owner 必须与当前行完全一致；否则 stale_claim（零写）
S4. 取闭包并加锁；调 kind 对应解释器得 delta；足迹校验
S5. 应用 delta；status = succeeded|failed|unknown；settled_at=now()
       claim_owner := NULL, lease_until := NULL      （否则违反 c_effects_claim_ck）
       attempt_no / fence 保留为历史，不回退
       success|failure => resource_quiesced_at = now()     （回执即证明 IO 已返回）
       unknown         => resource_quiesced_at 保持 NULL   （只有 inspect_resource 可置位）
S6. 后继：success/failure 按解释器约束生成；unknown 不得生成业务后继
```

#### 4.14.3 delta 足迹校验

解释器返回的 delta 是以 `{table: [rows]}` 表达的封闭集合，**不直接写表**。`advance` 在应用前校验：

1. 每个 table 都在 `effect.kind` 声明的可写表集合内；未声明的表出现即 `invalid_outcome`。
2. 清理类 delta 的有向边无环，有环即 `cleanup_cycle`（零写）。
3. 后继 effect 数 ≤ 16，且 `(parent_effect_id, ordinal)` 互不重复（DB 唯一约束再兜底）。
4. 预算 delta 不得为负（S1 不产生预算，校验先存在）。
5. 事件数 ≤ 64，且 `(entity_type, entity_id, event_kind)` 在本 delta 内不重复。

任何一条不过 ⇒ 零写返回；**不部分应用**（§2.3 L91）。

#### 4.14.4 delta 形状

W4 冻结解释器与通用应用器之间的 JSONB 合同。顶层对象只允许以下成员：`domain`, `effect`, `request`, `events`, `successors`, `error`。缺省 `domain.insert/update`、`events`、`successors` 分别按空对象/空数组解释；其它未知顶层成员为 `invalid_outcome`。解释器只构造此值，不直接写任何表。

```json
{
  "domain": {
    "insert": {"scopes": [{"scope_id":"uuid", "parent_id":null, "root_id":"uuid",
      "route_path":["uuid"], "realm_routes":{}, "default_realm":null,
      "owner_principal":"uuid", "created_by_effect":"uuid"}]},
    "update": {"scopes": [{"key":{"scope_id":"uuid"},
      "set":{"close_requested_at":"2026-10-23T00:00:00Z"}}]}
  },
  "effect": {"status":"succeeded", "outcome":{}},
  "request": {"response":{"v":1,"disposition":"committed","effect_id":"uuid",
    "emitted":[],"revision":0,"claim":null}},
  "events": [{"entity_type":"scope", "entity_id":"uuid", "event_kind":"scope_created",
    "payload":{}, "payload_digest":"\x..."}],
  "successors": [{"effect_id":"uuid", "ordinal":0, "kind":"host_prepare", "request":{}}]
}
```

`domain.insert` / `domain.update` 是 table-name → row-array 的对象。每条 insert row 是完整的可插入列映射；每条 update row 恰含 `key`（主键列映射）与 `set`（要赋值的列映射），不得设置不可变身份列。表足迹按 `effect.kind` 静态白名单校验；本 W4 白名单仅 `command_scope_control → scopes`。effect 字段是新增 effect 的列补丁，`effect.status` 必为 `succeeded|failed`，`effect.outcome` 必非空并形成 receipt。request 的 response 是首次原样返回并持久化的 JSONB；`error` 若存在则是 `error_v1` 封套，仍写 settled failure effect 与 request。

事件项字段为 `entity_type`, `entity_id`, `event_kind`, `payload`, `payload_digest`；digest 是 payload UTF-8 canonical JSON 的 SHA-256 bytea 表示。apply 忽略任何调用方 seq，按同事务 `max(seq)+1` 分配。后继项字段为 `effect_id`（可省略则生成）、`ordinal`（0–15）、`kind`, `request`；它们继承 principal 与 scope 并以 `ready`, `attempt_no=0` 插入。全量预检必须发生在首个 DML 前：仅声明表、最多 16 条 insert+update row、64 events、16 successors；事件三元组与 successor ordinal 各自唯一，字段/主键/闭集/数值范围合法。任何拒绝不得部分应用。应用顺序固定为领域 insert/update → command effect → request → events → successors；领域行的 `created_by_effect` 为当前 effect，依靠延迟 FK 闭合。业务错误 `scope_closed` / `unauthorized` 使用 `error` 字段，按 W1 同事务写 failure receipt 与 request。

### 4.15 锁闭包与 `retry_with_closure`

取得 G 后，用普通 MVCC 查询发现闭包（G 已排除并发 writer，闭包不会被改写），然后**一次性**按 B.1 全序加锁：

```text
G -> request -> scope(root→leaf) -> run -> effect -> install -> fiber -> episode -> slot -> pin -> event/projection
```

- scope 从 root 到 leaf，同层按 `scope_id` 字节序；同一层多个对象按稳定 UUID 升序。
- run 涉 parent+child 时按 `run_id` 排序，不得用 parent-first 树遍历（B.2 反例三）。
- 需要锁未预见的新对象 ⇒ 抛 `retry_with_closure`，**不得持低层锁再补锁**。注意它必须在任何 DML 前发生，才能满足「零写 + 可重交」；因此闭包发现与加锁全部完成之后才进入解释器。
- 普通 reader / resolve / poll / wait 不取 G、不锁写行（S2/S3 实现）。

G 的可观测形态（实测）：`pg_locks` 中 `locktype='advisory' AND classid=24 AND objid=1 AND objsubid=2`。**用 `objsubid=1` 查会得到 0 行**，这是 G1-L 的实现陷阱。

### 4.17 解释器：`scope_control`

```sql
CREATE FUNCTION v24.scope_control(p_action text, p_parent_scope_id uuid,
  p_realm_routes jsonb, p_default_realm text, p_request_key text) RETURNS jsonb
LANGUAGE plpgsql SECURITY INVOKER;   -- 只构造 outcome 并调用 advance
```

`p_action` 闭集 `create_root | create_child | close`（§B.3 L550）。

| action | 权限 | 行为 | 错误 |
|---|---|---|---|
| `create_root` | 仅 system-admin（`pg_has_role(session_user,'v24_admin','USAGE')`） | `scope_id := gen_random_uuid()`；`parent_id=NULL`；`root_id=scope_id`；`route_path=[scope_id]` | `unauthorized` |
| `create_child` | parent.owner_principal 或 admin | 锁 parent；校验 `close_requested_at IS NULL`；`root_id=parent.root_id`；`route_path = parent.route_path || new_id` | `scope_closed`、`unauthorized` |
| `close` | parent.owner_principal 或 admin | 仅写 `close_requested_at=now()`；**不写 `closed_at`**；不级联、不排空 | 幂等：已有 intent 则 `committed` 零差异 |

`close` 在 S1 只落地§3.1.1 L130 的**第一步**（写意图 + 立即拒绝新 child/install），完整排空属 S5（D6）。因此 `closed_at` 在 S1 永远为 NULL，`c_scopes_close_pair` 与 `c_scopes_close_order` 在 S1 只能以 owner DML 反例验证（§4.12）。

禁止的行为（写进解释器注释并在 G1-O 断言）：不得用 CHECK 或触发器代替 advance 校验 parent 环/跨 root；不得接受调用者自报 `root_id`/`route_path`。

### 4.18 解释器：`install` 与 `host_prepare`

```sql
CREATE FUNCTION v24.install(p_scope_id uuid, p_owner_fiber_id uuid,
  p_manifest_bytes bytea, p_artifact_digest bytea, p_request_key text) RETURNS jsonb
LANGUAGE plpgsql SECURITY INVOKER;
```

**admission**（同一 advance 内）：

1. 锁 scope；`close_requested_at IS NOT NULL` ⇒ `scope_closed`。
2. **S1 只接受 `p_owner_fiber_id IS NULL`（root install）**；非空 ⇒ `invalid_args`（child admission 是 S2，`owner_closing` 也归 S2）。
3. 解析 `p_manifest_bytes → jsonb`：必须为 object，且含 `identity,version,requires,provides,adapter_digest`；`requires/provides` 为数组。
4. 查 `u_installs_ident`：同 `(scope,identity,version)` 已存在 → 比对 `manifest_digest`/`artifact_digest`；相同则**返回既有 install_id**（不新建行，但本次 command 仍写自己的 receipt）；不同 ⇒ `install_identity_conflict`。
5. 新建时：`state = 'preparing'`（若 `provides` 非空或 host 需预制）/ `'installed'`（纯声明、无外部制品）；`preparing` 时同事务生成一个 `ready` 的 `host_prepare` effect，`request = {"install_id":..., "reservation": "<确定性绑定 effect_id>"}`。

**`host_prepare` settlement**（CAS on `state='preparing'`）：

| class | `installs.state` | `effects.status` | `resource_quiesced_at` |
|---|---|---|---|
| `success` | `installed` | `succeeded` | `now()` |
| `failure` | `prepare_failed` | `failed` | `now()` |
| `unknown` | `prepare_unknown` | `unknown` | **NULL**（必须 inspect 才能置位） |

若 settlement 时 install 已不是 `preparing`（重复回执/竞态）⇒ `receipt_conflict` 或 `deferred`，不重复迁移。

**FakeHost 契约**（`v24/s1/fake_host.py`）：

- 纯进程内，不开套接字；调用发生在 `advance(claim)` COMMIT **之后**、`advance(settlement)` **之前**。
- 持久化 IO journal 落在**独立的 `v24_fake` schema**（由 fixture 创建，不属十表，不计入 catalog 断言），列：`id bigserial, effect_id uuid, attempt bigint, fence bigint, op text, payload jsonb, result jsonb, started_at, finished_at`。
- 脚本化响应计划：`succeed` / `fail` / `unknown` / `crash_before_journal` / `crash_after_journal`。
- G1 断言：claim 事务 COMMIT 前 journal 里没有该 `(effect_id,attempt)` 记录；`unknown` 路径的 `resource_quiesced_at` 保持 NULL。

### 4.20 开放项裁决

**O2 — 首次请求行不存在的锁机制。**

唯一采用：G 之下 `SELECT ... FOR UPDATE` 查无 ⇒ 直接 `INSERT`；`pk_requests` 是兜底。若 INSERT 报 `23505`，说明有 writer 绕过了 G，属于协议违约，**抛错回滚**，不得吞掉或改写。明确不做：不建占位行、不建 per-request advisory lock、不做 insert-then-update 两阶段、不新增「冲突槽」对象（§B.1 L498 的「唯一键冲突槽」由 `pk_requests` 承担）。

**O3 — `events.seq` 统一分配。**

```sql
v_seq := coalesce((SELECT max(seq) FROM v24.events
                    WHERE entity_type = v_et AND entity_id = v_eid), 0) + 1;
```

规则：

1. 分配在 G 内、与事件插入同一事务；同事务多条事件先按 `(entity_type, entity_id, event_kind)` 排序，再依次 `+1`，结果确定。
2. 回滚丢弃已插事件行，下次事务重用该号：**seq 不承诺无空洞**，它是游标不是计数。
3. replay 不重新分配：`u_events_once` 挡重复，且 advance 在 replay 分支直接返回首次 response，不进入事件写入。
4. `max(seq)` 由 `u_events_cursor` 的 `(entity_type,entity_id,seq)` 索引支撑为 `Index Only Scan Backward`（实测），不需要计数器表或全表扫描。
5. `runs.revision` 与 seq 无关：revision 是 poll 游标，由写 run 的 advance 递增（S3/S4）。

**O5 — `fibers.current_episode_id ↔ episodes` 的 DDL 编排。**

冻结四条：

1. **插入顺序**：fiber 先插且 `current_episode_id = NULL` → episode 后插 → 再 `UPDATE fibers SET current_episode_id`。「可空 + 后置 UPDATE」解开了环，**不需要任何 DEFERRABLE**。
2. `u_episodes_ident (fiber_id, episode_id)` **必须非延迟**：实测 `cannot use a deferrable unique constraint for referenced table`，而它是 `fibers`/`installs`/`slots`/`pins`/`runs` 复合外键的共同目标。
3. `u_episodes_open` 与 `u_slots_live` 是 partial unique index，**不可延迟且同事务顺序敏感**（实测 E1 未关时插 E2 立即 `23505`）。因此 E1→E2 必须：先 `UPDATE episodes SET state='closed', closed_at=now() WHERE episode_id=E1`，再 `INSERT e2`，最后切 `fibers.current_episode_id`。provider 切换同理：先置旧 slot 的 `released_at` 再插新 slot。
4. 不用 deferrable 换顺序自由度：延迟会把「同事务两个 open episode」的检测推到 COMMIT，错误定位变差，且对 partial unique index 根本不可用。

**O7 — T1/T2 术语（已因 R5 关闭）。** 设计稿 §7.1 已定义，下列为 S1 的执行口径，不再是待裁决项：

- **T1 = 执行资格提交**：`ready → claimed` 的那次 advance（写入 `attempt_no`/`fence`/`claim_owner`/`lease_until`）。
- **T2 = 外部结果接纳**：`class ∈ {success, failure, unknown}` 的那次 advance。
- 三段固定为 **T1 → 事务外 IO → T2**；`host_prepare`/`host_release` 回执同样适用（R5 已将其纳入 T2，O9 关闭）。
- §9 L435 的「T1 前 IO 失败」因此读作：**T1 未提交前不得有任何 IO 记录**（G1-I 断言）。
- §9 L439 的「7 个 kill 点」与 §8 的十行窗口不一致，属 S6 的 G5 验收清单；**S1 只冻术语，不裁决点数**。术语已由 R5 冻入设计稿，此处只保留 S6 的 kill 点数销项。

### 4.21 W3 判据与分支归属

**归属规则**：W3 = 解释器之前的一切。因此 `claim` 整个归 W3（它没有解释器、不产 delta），W5 只做 settlement。

| 分支 | W3 负责 | 后续工项 |
|---|---|---|
| `command` | C0–C3：effect_id 校验、request 身份与加锁、replay/conflict、闭包与 B.1 加锁 | C4–C8（解释器与提交）→ W4 |
| `claim` | 全部分支 K0–K2 | — |
| `settlement` | S1–S3：加锁、replay 与 `receipt_conflict`、token 校验 | S4–S6（解释器、结算列、后继）→ W5 |

**W3 的 Done when**（每条可证伪）：

1. `class` 闭集恰为 5 值；6 个非闭集输入（含大小写变体、`null`、`settle`）各返回 `invalid_args` 且零写。
2. 8 类非法形状各零写 `invalid_args`：class 非闭集 / command 或 claim 携非 null claim / body > 1 MiB / 深度 > 32 / 键数 > 200 / 未知 kind / claim 的 `lease_ms` ∉ [1,300000] / unknown 携后继键。
3. 每个 class 到达唯一分支且可观测：command → C0 的 `effect_id_conflict`；claim → 封套 `claim={attempt:1,fence:1,owner=session_user}`；settlement → `stale_claim` / `replay` / `receipt_conflict` 三选一。
4. **C0 先于 replay**：fixture 预置 request 行后伪造 effect_id，得 `effect_id_conflict`，不得得 `replay` 或 `request_conflict`（设计 §A.3 L631）。
5. 三条优先序各一条：已结算同 digest ⇒ `replay`；异 digest ⇒ `receipt_conflict`；claimed 错 token ⇒ `stale_claim`；均零写。
6. claim 对已结算 effect ⇒ `invalid_args`（**不是** `already_terminal`）。
7. `retry_with_closure` 在闭包不足时零写返回。
8. `pg_locks` 命中 `(advisory,24,1,objsubid=2)`；且阻塞期间该 backend 在 `v24.*` 上无任何 granted 行锁——证「G 是首锁」，不只是「在等 G」。

C4–C8 与 S4–S6 的绿**不在** W3 判据内；G1-B/D 归 W4，G1-C/G 归 W5。

## 6. 风险与回退

| 风险 | 最脆弱之处 | 缓解 | 停手条件 |
|---|---|---|---|
| R1 G 不是真首锁 | 设计自述「一处遗漏即使其余单入口成立也是假原生」（L489） | G1-A/G1-L/G1-P 三重断言；十表零 GRANT；所有 wrapper 为 INVOKER | 任一应用角色能直接 DML 成功，或某函数在 G 前取行锁 ⇒ 停工修 ACL/顺序 |
| R2 十表 vacuous 断言 | S1 无写入者的列很多（§4.12） | 归属表 + 只做 catalog/DML 反例，不冒充行为覆盖 | 任一 G1 断言指不出生产者 ⇒ 删除或降级并在 matrix 标未验证 |
| R3 DEFERRABLE FK 把错误推到 COMMIT | 错误到「哪条命令失败」的映射变差 | 断言 SQLSTATE + 约束名，不只看错误文本；命令封套保留 `detail.constraint` | 同一约束名在两条命令间不可区分 ⇒ 补 delta 校验前置 |
| R4 advance 退化成决策树 | 设计 L102–104 的反面教训（v13 `v13_advance`） | 解释器只返回 delta；advance 只做足迹校验与应用 | advance 内出现第二处「按 kind 分支做业务判断」⇒ 停工重构 |
| R5 fixture 成本与泄漏 | pgembed 每次起库；库/角色清理不彻底会累积 | OID 复核后 FORCE DROP，先库后角色；自检断言清理后无残留 | 单次 gate > 60s ⇒ 先查清理泄漏，不加超时 |
| R6 无第十一表的边界被侵蚀 | 后续阶段想加「方便表」 | G1-N 的 catalog 闭集断言在每个后续 stage 的 setup 里复用 | 任何新表出现 ⇒ 回到设计稿修订，不在 stage 内消化 |
| R7 S1 的 `revision=0` 被误解为 run 语义 | C2 空洞 | §4.13 明写空洞 + S3 开工前回写 C2 | S3 第一份 plan 未回写 C2 ⇒ 不启动 |
